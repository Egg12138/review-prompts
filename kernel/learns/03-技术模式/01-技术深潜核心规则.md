# 技术深潜核心规则

## 概述

本文件整理 Linux 内核代码审查中的核心技术规则。与表面的 "应该这样做" 不同，每条规则都解释了 **为什么** 这条规则存在、违反它会带来什么后果，以及如何在实践中正确应用。

---

## 一、完整执行流追踪：不要跳跃式结论

**规则**：在判断代码正确性之前，必须沿着调用链追踪完整的执行路径，收集足够上下文。

**为什么重要**：

- 内核代码充满条件编译 (`#ifdef`)、特性开关 (`IS_ENABLED()`)、以及多层函数包装。只看某一行代码的函数签名或返回值类型就下结论，几乎一定会误判。
- 举例：一个函数注释写着 "返回 X"，但其实际实现可能根据内核配置走不同的分支。如果只看注释不看实现，就会漏掉条件分支中的 bug 或误报不存在的 bug。
- 注释和文档可能过时、误导或被复制粘贴到语义不同的实现上。

**实践方法**：

1. 遇到任何函数调用，读它的 **实际实现**，不只是注释
2. 检查 `#ifdef`/`#else` 分支——同一段注释可能被复制到多个语义不同的实现中
3. 如果函数注释说 "返回 X" 但代码显示有基于配置的 conditional 行为，验证当前分析场景适用哪个配置
4. **绝不**只因为发现某个步骤有 bug 就跳过后续步骤——完整分析比快速结论更重要

---

## 二、WARN_ON/BUG_ON 不改变函数语义

**规则**：`WARN_ON()` 和 `BUG_ON()` 只影响控制台输出什么信息，**不改变**函数能接受什么参数、能处理什么错误条件。

**为什么重要**：

- 初学者常犯的错误：看到 `WARN_ON(!ptr)` 就认为调用方保证 `ptr` 不为 NULL。不对——`WARN_ON` 只是打印一个警告，**代码会继续执行**，`ptr` 仍然可能是 NULL。
- `BUG_ON()` 略有不同（触发后内核崩溃），但同样不应依赖它来保证前置条件——它只是 "防御性编程" 的一种粗暴形式，不代表调用方真的检查过条件。
- 不要因为代码中有 `WARN_ON()` 或 `BUG_ON()` 就假设某个条件永远不会发生。你需要 **具体的调用链和代码证据** 来证明该条件在实际路径中不可能出现。

---

## 三、不要把防御性检查当成推荐方案

**规则**：除非你能证明数据来源不受信任，否则永远不要建议添加多余的边界检查或防御性代码。

**为什么重要**：

- 内核是一个性能敏感的系统。每多一次不必要的 NULL 检查、边界判断或分支预测，都在消耗 CPU 周期。
- "防御性编程" 的理念在应用层开发中常见，但在内核中，真正的做法是 **确保正确性，而不是到处加检查**。
- 如果你发现一个指针没有做 NULL 检查，正确的做法是：**证明这条路径上它不可能为 NULL**，或者 **证明它确实可能为 NULL 并导致 bug**。而不是简单地说 "加个 if 检查"。
- 同理：不要建议添加防御性的边界检查（bounds check），除非你能证明数据来源不受信任。

## 四、NULL 指针解引用的本质：读字段不等于解引用

这是内核代码审查中最容易被误解的概念之一。很多人把 "读取一个指针的字段" 等同于 "解引用这个指针"，从而导致大量误报。

### 4.1 区分 "读取指针" 和 "解引用指针"

```c
// 读取 foo 的 bar 字段
ptr = foo->bar;

// 解引用 ptr（即使用 ptr 指向的内存）
*ptr
ptr->field
ptr[0]
```

- `ptr = foo->bar` —— **解引用 foo**（因为需要读 foo 指向的内存才能拿到 bar），但 **没有解引用 bar**（只是读取了 bar 这个指针值）
- `*ptr` 或 `ptr->field` —— **解引用 ptr**

### 4.2 各模式分析

| 代码 | 解引用情况 | 安全条件 |
|------|-----------|---------|
| `val = *foo` | 解引用 `foo` | `if (foo)` 保护 |
| `val = foo[var]` | 解引用 `foo`，仅读取 `var` 不解引用 | `if (foo)` 保护 |
| `val = foo->ptr` | 解引用 `foo`，仅读取 `ptr` 不解引用 | `if (foo)` 保护 |
| `val = *foo->ptr` | 解引用 `foo` **和** `ptr` | `if (foo && foo->ptr)` 保护 |
| `val = (*foo)->ptr` | 解引用 `foo`，再解引用 `*foo` 指向的对象，仅读取 `ptr` | `if (foo && *foo)` 保护 |
| `val = foo->ptr->something` | 解引用 `foo` 和 `ptr`，仅读取 `something` | `if (foo && foo->ptr)` 保护 |

### 4.3 关键要点

1. **读取指针字段不等同于解引用该指针**
   - `ptr = foo->bar` 解引用 `foo`，读取 `bar`，**不** 解引用 `bar`
   - 对 `bar` 的解引用发生在 **后续使用 `ptr`** 时（如 `ptr->field`）

2. **检查指针真正被使用的地方**
   - 如果 `ptr = foo->bar` 且 `bar` 可能为 NULL，问题发生在 `ptr` 被解引用时
   - 例如：`ptr->field`、`*ptr`、`ptr[0]`、或将 `ptr` 传递给一个会解引用它的函数

3. **NULL 检查保护的是被检查的指针本身**
   - `if (foo)` 保护解引用 `foo`
   - `if (foo && foo->bar)` 同时保护解引用 `foo` 和 `foo->bar`

## 五、RCU 顺序强制规则

**规则**：使用 `call_rcu()`、`synchronize_rcu()` 或 `kfree_rcu()` 时，必须确保对象 **先从数据结构中移除**，再调用回收机制。

**为什么重要**：

- `call_rcu()` 只等待调用时已存在的读者完成——它 **不阻止** 在 grace period 开始后 **新找到该对象** 的读者访问它。
- 如果对象仍链接在数据结构中就调用 `call_rcu()`，新读者可以在 grace period 之后、callback 执行之前找到该对象——此时对象已释放，造成 use-after-free。

**正确的顺序**：

```c
// 正确：先移除，再延迟回收
hlist_del_rcu(&obj->node);         // 1. 新读者无法再找到该对象
call_rcu(&obj->rcu, free_callback); // 2. 等待已有读者完成

void free_callback(struct rcu_head *rhp) {
    struct obj *obj = container_of(rhp, struct obj, rcu);
    kfree(obj);                    // 3. 安全：所有已有读者已完成
}
```

**危险的错误模式**：

```c
call_rcu(&obj->rcu, callback);
// 在 callback 中：
void callback(...) {
    remove_from_structure(obj);  // 错误！为时已晚！
    kfree(obj);
}
```

**四步检查法**：
1. 遇到 `call_rcu()`、`synchronize_rcu()`、`kfree_rcu()` 时立即警觉
2. 检查：从数据结构的移除发生在 `call_rcu()` **之前** 还是 **之后**（或在 callback 中）
3. 如果移除在 callback 中 → 错误模式，应标记为 use-after-free bug
4. 使用适当的 RCU 感知移除辅助函数：`hlist_del_rcu()`、`list_del_rcu()`、`rhashtable_remove_fast()` 等

## 六、资源生命周期管理

**规则**：每个资源必须有平衡的生命周期：分配→初始化→使用→清理→释放。

### 6.1 核心原则

- **所有权追踪**：不要只看 "某处是否释放了该资源"，要追踪 **所有权链**——谁分配、谁拥有、谁负责释放
- **引用计数**：`refcount_t` 计数器在降到零后不会再增加；`refcount_dec_and_test()` 仅当到达零时返回 true
- **`css_get()`** 增加额外引用
- **点后置零**：释放由结构体字段引用的资源后，如果结构体本身不立即释放，应将指针字段设为 NULL，防止重用时 use-after-free
- **全局/静态变量** 会自动零填充

### 6.2 资源切换检测

- 检查函数返回与预期修改的资源不同的每一条路径
- 确保适当的锁被持有或释放

### 6.3 调用者期望追踪

- 调用者将资源传递给函数时，期望发生什么？
- 函数返回后，哪些锁已被获取、哪些已被释放？

### 6.4 结构体字段迁移时的注意事项

- 字段被子结构体包含时，搜索父结构体的所有静态实例（如 `init_mm`、`init_task`）并验证其初始化器已更新
- 锁需要显式初始化宏（如 `__RAW_SPIN_LOCK_UNLOCKED`），而非零填充

## 七、ERR_PTR 与 NULL 的区别

**规则**：`ERR_PTR()` 将错误码转换为指针，但它 **不是有效指针**。

```c
foo = ERR_PTR(-ENOMEM);
if (foo) → TRUE       // 但 *foo 会崩溃！
```

详见 [03-ERR_PTR与NULL辨析.md](./03-ERR_PTR与NULL辨析.md)。

## 八、for 循环语义

**规则**：`for(init; condition; advance) { body }`

- `condition` 在 **每次执行 body 之前** 检查
- `advance` 在 **每次 body 执行之后** 运行

确保在分析循环逻辑时理解这一点——内核对 `for_each` 宏的实现高度依赖这个精确的语义。

## 九、call_rcu() 顺序保证

（参见第五节 RCU 顺序强制规则，此处做补充说明）

`call_rcu()` 的 ordering 保证是整个 RCU 机制的基石：

1. 先完成 `call_rcu()` 调用之前的所有内存写入（包括从数据结构中移除对象）
2. 等待所有已存在的 RCU 读侧临界区完成（grace period）
3. 然后才执行 callback

反过来理解：如果你在 callback 中才做移除操作，那么步骤 2 发生时对象仍在数据结构中——新读者在步骤 2 之后、步骤 3 之前可以找到并使用该对象，而此时对象尚未被释放（还没执行到 kfree），但这个窗口本身就是 **设计错误的信号**。更严重的是：如果读者在 callback 执行 **之后** 才查找该对象，而对象已经在 callback 中被 kfree 了，问题就出现了。

**正确保证的关键**：让这一步成立——"在 `call_rcu()` 之前，没有新读者能再找到这个对象"。

## 十、其他重要规则

### 10.1 不要只因为返回类型就做假设

- 不要基于返回类型、检查逻辑、`WARN_ON()`、`BUG_ON()`、注释或错误处理模式做假设——通过追踪具体执行路径来验证代码正确性

### 10.2 必须证明 bug 在实际路径中可发生

- 某些调用路径可能在解引用前始终检查 `IS_ENABLED(feature)`
- 特性对应的实际实现可能不需要这些检查，因为它们只在特性开启时才被调用
- API 约定不清楚是不够的——你必须证明 bug 在实践中确实能发生

### 10.3 内核上下文规则速查

| 上下文 | 含义 | 可以做什么 | 注意事项 |
|--------|------|-----------|---------|
| 禁止抢占（Preemption disabled） | 不会调度出去 | 使用 per-CPU 变量 | 仍可被 IRQ 中断 |
| 禁止迁移（Migration disabled） | 保持在当前 CPU | per-CPU 访问不需要原子性 | 仍可被抢占 |
| `typeof()` 安全性 | 可在 init 前用于 `container_of()` | 类型安全操作 | — |
| 自测（Self-tests） | 测试代码 | 内存泄漏/FD 泄漏可接受 | 除非会导致系统崩溃 |
| `likely()`/`unlikely()` | 编译器分支提示 | 不改除非引入更大逻辑 bug | — |
| `READ_ONCE()` | 防止合并读取 | 锁保护下的数据结构不需要 | 已持锁时不需要 |

### 10.4 list_head API

- `list_add(new, head)` 会通过写入来初始化 `new`，但 `head` 必须已被初始化
- 对象从链表中移除后，确保它们被返回、释放或以其他方式善后，不被遗失

### 10.5 内存分配 API 注意事项

- slab 和 vmalloc API 有能自动零填充的变体，`__GFP_ZERO` GFP 掩码也能零填充
- `kmem_cache_create()` 可以使用 `init_once()` 函数初始化 slab 对象——这仅在首次分配时发生，防止结构体中的垃圾数据

### 10.6 常见陷阱

- `strscpy()` 可在编译器能找到类型时自动检测数组大小
- `char *s = "";` 时 `strlen(s)` 返回 0，但 `s[0]` 可安全访问
- `memcpy(dst + (offset & mask), src, size)` 通常在其他地方做了对齐验证
- 有 `MAX_FOO` 的全局数组：检查是否可能创建超过 `MAX_FOO` 个元素
- 指针大小相同：`char *foo` 和 `int *foo` 占用相同内存空间——但为代码清晰，分配指针数组并用 `sizeof(type *)` 计算大小时，应使用正确的类型
