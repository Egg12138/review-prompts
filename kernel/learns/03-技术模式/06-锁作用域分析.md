# 锁作用域分析

## 核心原则：作用域而非存在性

内核锁分析中最常见的误判是 "这里有锁操作，所以是安全的"。

正确的分析应该关注 **锁的作用域（scope）是否覆盖了整个临界区**，而非仅仅检查锁是否存在。一把锁即使被正确获取和释放，如果它的作用域没有覆盖所有并发访问路径、或者没有覆盖临界区中的每一步操作，竞态仍然会发生。

**关键问题**不是 "函数 X 是否持有锁 L"，而是：

- 锁 L 在访问共享状态前是否已被获取？
- 锁 L 在共享状态使用完毕后是否才被释放？
- 在锁的作用域内，是否存在提前返回路径导致锁丢失？
- 所有访问同一共享状态的代码路径是否都持有了同一把锁？
- 锁的类型是否足够强（是否考虑了中断上下文？）

---

## 一、核心思维模型：并行时间线

竞态条件的本质是：**两个 CPU 以特定的交错顺序执行指令，产生了错误的结果**。

### 始终问一个问题

> 在当前 CPU 执行每一条指令时，**另一个 CPU 此刻可能在干什么？**

答案永远是：另一个 CPU 在执行它自己代码路径中的任何指令——除非有同步机制强制了顺序。

### 一个直观的例子

```c
// 路径 A（删除）:                     路径 B（添加）:
//   if (list_empty(&list))              spin_lock(&lock);
//       → 决定跳过删除                    list_add(new, &list);
//   return                              spin_unlock(&lock);
//   → 实际上 list 上有元素没被删除！
```

这个 TOCTOU（Time-Of-Check-Time-Of-Use，检查时刻与使用时刻的竞态）的关键：
- 检查（`list_empty`）和操作（删除）不在同一个原子区域内
- 在检查和操作之间，另一个 CPU 修改了共享状态

## 二、系统化追踪竞态的五步法

### 第一步：识别共享数据

共享数据包括：
- 全局变量或静态变量
- 全局可达对象中的字段（如 `inode->i_size`）
- 引用计数
- 状态标志
- 链表、哈希表、树中的元素
- 链表指针本身

**判断标准**：任何被多个代码路径访问的结构体成员都可能是共享的。

### 第二步：枚举所有代码路径

对每个共享变量，列出所有读写它的代码路径：

| 路径类型 | 例子 |
|---------|------|
| 系统调用处理函数 | `sys_read()`、`sys_ioctl()` |
| 中断处理程序 | hardirq、softirq |
| workqueue 回调 | `work_handler()` |
| 定时器函数 | `timer_callback()` |
| tasklet | `tasklet_handler()` |
| 模块 init/exit | `module_init()` / `module_exit()` |
| 网络接收路径 | NAPI poll |

每对路径都是一个潜在的竞态分析对象。

### 第三步：构建交错时间线

取两条代码路径，把它们并排放置，找到能产生错误结果的交错执行顺序。

```
CPU 0 (查找)                    CPU 1 (删除)
──────────────                  ──────────────
lock → find item → unlock
                                 lock → list_del → unlock → kfree(item)
item->data ← USE-AFTER-FREE
```

### 第四步：锁集合分析（Lockset Analysis）

对每个共享变量 V：

1. 找出所有访问 V 的路径在访问时持有的锁集合
2. 求这些集合的 **交集**
3. 如果交集为空 → **没有一把锁在所有路径上都保护 V** → 可能存在竞态

```c
路径 A: spin_lock(&obj->lock); obj->counter++; spin_unlock(&obj->lock);
路径 B: obj->counter--;  // 没拿锁

L(A) = {obj->lock}, L(B) = {}
C(obj->counter) = {obj->lock} ∩ {} = {} → RACE（竞态！）
```

**注意**：锁不仅需要存在，还需要 **类型正确**——见第四节。

### 第五步：检查对象生命周期

在以下每个点都要问："另一个路径是否仍持有指向此对象的原始指针？"

- 路径释放锁时
- 路径释放引用时
- 路径返回前

## 三、四个关键问题

在每一行读写共享变量的代码处，问这 **四个问题**：

### Q1：当前持有什么锁？

逆向追溯调用链。寻找：
- `lockdep_assert_held()` 断言
- 以 `__` 开头的函数（约定：调用者已持锁）
- 调用链上方的直接锁调用

### Q2：此刻还有什么其他路径能访问这个数据？

- 另一个 CPU 上运行同一个系统调用（处理不同对象时可能共享全局结构）
- 当前 CPU 上的中断（硬件中断或软件中断）
- 定时器 / workqueue
- 并发的 `close()` 或模块卸载

### Q3：锁的类型足够强吗？

`spin_lock()` 保护同时被 IRQ 处理程序访问的数据是不够的——见第四节。

### Q4：对象还活着吗？

- 指针是在持锁或 RCU 读侧临界区内获取的吗？这个锁/临界区是否还在持有？
- 引用计数被获取了吗？
- 如果两者都不是 → 对象可能已被释放

---

## 四、锁上下文兼容性

### 4.1 锁类型速查表

| 锁变体 | 等待类型 | 对进程 | 对 Softirq | 对 Hardirq | 可睡眠？ |
|--------|---------|--------|-----------|-----------|---------|
| `raw_spin_lock` | LD_WAIT_SPIN | 是 | 否 | 否 | 否 |
| `raw_spin_lock_irqsave` | LD_WAIT_SPIN | 是 | 是 | 是 | 否 |
| `spin_lock` | LD_WAIT_CONFIG | 是 | 否 | 否 | 非RT:否 / RT:是 |
| `spin_lock_bh` | LD_WAIT_CONFIG | 是 | 是 | 否 | 非RT:否 / RT:是 |
| `spin_lock_irq` | LD_WAIT_CONFIG | 是 | 是 | 是 | 非RT:否 / RT:是 |
| `spin_lock_irqsave` | LD_WAIT_CONFIG | 是 | 是 | 是 | 非RT:否 / RT:是 |
| `local_lock` | LD_WAIT_CONFIG | Per-CPU | 否 | 否 | 非RT:否 / RT:是 |
| `local_trylock` | LD_WAIT_CONFIG | Per-CPU | 否 | 否 | 非RT:否 / RT:是 |
| `mutex` / `rwsem` | LD_WAIT_SLEEP | 是 | 否 | 否 | 是 |

### 4.2 为什么用错锁类型会出问题

**场景一：spin_lock 没有关 IRQ，但数据也被 IRQ 处理程序访问**

```
CPU 0 (进程上下文)                CPU 0 (中断处理程序)
    spin_lock(&data_lock)              ← IRQ 在此 CPU 上触发
      ← 被 IRQ 抢占                   spin_lock(&data_lock)
      → deadlock！                     我们持有 data_lock 但无法继续
```

**修复**：所有进程上下文获取该锁时必须用 `spin_lock_irqsave()`。

**场景二：共享锁但只有部分路径关中断**

如果同一个锁既在进程上下文使用也在 hardirq 中使用，**所有** 进程上下文的获取必须禁用 IRQ。裸 `spin_lock()` 只有在调用路径确保 IRQ 已关闭时才安全。

**场景三：softirq 共享**

如果数据在进程上下文和 softirq 之间共享，使用 `spin_lock_bh()`——它在加锁时禁用 softirq，防止当前 CPU 上的 softirq 抢占。

### 4.3 IRQ 安全锁变体

- `spin_lock_irq()` / `spin_unlock_irq()`：加锁时关 IRQ，解锁时开 IRQ。仅当调用者 **确定** IRQ 当前已开启时才安全。
- `spin_lock_irqsave(lock, flags)` / `spin_unlock_irqrestore(lock, flags)`：保存/恢复 IRQ 状态。**推荐使用**，因为无论当前 IRQ 状态如何都安全。
- `spin_trylock()`：避免死锁——死锁仅在当前 CPU 已持有锁的情况下调用 `spin_lock()` 且 IRQ 关闭时发生。

## 五、锁嵌套兼容性

Lockdep 强制嵌套规则：**内层锁的等待类型必须小于等于外层锁的等待类型**。

| 外层锁 | 可嵌套 | 不可嵌套（lockdep BUG） |
|--------|-------|----------------------|
| `raw_spinlock_t` | `raw_spinlock_t` | `spinlock_t`、`local_lock`、`local_trylock`、`mutex`、`rwsem` |
| `spinlock_t` | `raw_spinlock_t`、`spinlock_t`、`local_lock`、`local_trylock` | `mutex`、`rwsem` |
| `local_lock` / `local_trylock` | `raw_spinlock_t`、`spinlock_t`、`local_lock`、`local_trylock` | `mutex`、`rwsem` |
| `mutex` / `rwsem` | 全部 | — |

**关键**：`CONFIG_PROVE_RAW_LOCK_NESTING`（默认 y）在非 RT 内核上也强制执行这些检查。`!IS_ENABLED(CONFIG_PREEMPT_RT)` 编译时守卫 **不能阻止** 这些检查。

分析方法：
1. 如果代码获取 `spinlock_t`、`local_lock` 或 `local_trylock`，检查是否有 **任何调用者** 持有 `raw_spinlock_t`
2. 如果代码持有 `raw_spinlock_t`，检查是否有 **任何被调用者** 获取 `spinlock_t`、`local_lock` 或 `local_trylock`

## 六、多变量竞态

最微妙的竞态涉及必须 **原子性地同时更新** 的多个变量。每个单独的访问可能都加了锁，但 **变量之间的关系** 没有保护。

```c
CPU 0                                CPU 1
──────                               ──────
lock → set state=ACTIVE → unlock
                                      lock → read state=ACTIVE
                                              call handler → OLD handler！
                                      unlock
lock → set handler=new → unlock
```

**问题**：`state` 和 `handler` 必须在同一个临界区中更新。分开更新时，CPU 1 可能看到 ACTIVE 状态但使用旧的 handler。

**教训**：当你发现一个共享变量在没有锁保护的情况下被访问时，不要以 "窗口很小" 为由放过。如果顺序违反可能发生，那就是 bug。

## 七、Lockdep 基础

### 7.1 检测能力

Lockdep（`CONFIG_PROVE_LOCKING`）是内核中的锁依赖验证器，能在运行时检测：

| 检测类型 | 说明 |
|---------|------|
| 死锁（ABBA） | 两个锁以不同顺序获取 |
| 锁嵌套违规 | 内层锁的等待类型大于外层 |
| IRQ 上下文冲突 | 在可被 IRQ 抢占的上下文中使用不安全的锁组合 |
| 锁递归获取 | 同一线程重复获取同一锁（非递归锁） |

Lockdep 发现警告时通常会打印详细的锁依赖关系图（splat），**不应轻易忽略**。

### 7.2 注解工具

- `lockdep_assert_held(lock)` —— 断言当前持有指定锁
- `mutex_lock_nested(lock, subclass)` / `spin_lock_nested(lock, subclass)` —— 区分同一类型锁在不同嵌套层级的使用（如父/子 inode 锁），最多 8 层
- `__must_hold(lock)` / `__acquires(lock)` / `__releases(lock)` —— Sparse 静态分析注解

### 7.3 Lockdep Pin Lock 的陷阱

`lockdep_pin_lock()` 找到当前任务锁栈中的 `held_lock` 条目并增加 `pin_count`。当任何已持锁被释放时，lockdep 检查 `pin_count`。

对于 `ww_mutex` 类型的锁（如 `dma_resv`），多个实例可能共享一个 `held_lock` 条目（通过引用计数）。固定该条目后，如果 **任何** 折叠实例被解锁，会触发警告。

```c
// 错误：固定 ww_mutex 类型锁，区域内可能解锁其他实例
lockdep_pin_lock(&vm->resv->lock.base);
ttm_bo_validate(...);  // 可能锁定/解锁其他 bo 的 dma_resv 锁
lockdep_unpin_lock(&vm->resv->lock.base);  // Lockdep 警告！
```

安全做法：固定区域内只操作该特定实例，不调用可能释放它或其他共享实例的回调。

## 八、内存顺序（Memory Ordering）

### 8.1 发布-获取模式

即使使用 `READ_ONCE()`/`WRITE_ONCE()`，CPU 仍可能重排 store 和 load。

```c
// 错误：Store 2 可能在 Store 1 之前变得可见
data->field = 42;                      // Store 1
WRITE_ONCE(global_ptr, data);          // Store 2

// 正确：release barrier 保证 Store 1 在 Store 2 之前完成
data->field = 42;
smp_store_release(&global_ptr, data);

// 消费者必须用 acquire：
p = smp_load_acquire(&global_ptr);
if (p) x = p->field;                  // 保证看到 42
```

`rcu_assign_pointer()` 和 `rcu_dereference()` 包含这些 barrier。

### 8.2 屏障类型速查

| 屏障 | 效果 | 注解 |
|------|------|------|
| `smp_mb()` | 全屏障 | 对所有 load/store 排序 |
| `smp_rmb()` | 读屏障 | 仅对 load 排序 |
| `smp_wmb()` | 写屏障 | 仅对 store 排序 |
| `smp_store_release()` | 释放语义 | 之前的 store 不会被重排到之后 |
| `smp_load_acquire()` | 获取语义 | 之后的 load 不会被重排到之前 |

- 屏障必须 **配对**：生产者的 `smp_wmb()` 与消费者的 `smp_rmb()` 配对
- `atomic_read()`/`atomic_set()` 是 relaxed 的——**不提供顺序保证**
- 返回值的 RMW 操作（`atomic_add_return()`、`atomic_cmpxchg()`）提供全排序
- Barrier 强制顺序，不是等待完成——它们阻止 CPU 和编译器在 barrier 点两侧重排

## 九、中断时间线

中断在单个 CPU 上制造并发：处理程序抢占正在运行的代码。

```
CPU 0（进程上下文）
──────────────────────
spin_lock(&data_lock)        ← 已获取，IRQ 未禁用
shared_counter++
  ← IRQ 在此 CPU 上触发
  ├─ IRQ handler: spin_lock(&data_lock) → DEADLOCK
  │   （我们持有锁，但无法继续运行）
  └─ 永不会返回
```

如果同一个锁在进程上下文和 hardirq 中使用，所有进程上下文的获取必须用 `spin_lock_irqsave()`。如果与 softirq 共享，用 `spin_lock_bh()`。

## 十、PREEMPT_RT 的差异

在 PREEMPT_RT 内核上，`spinlock_t` 被实现为 rt_mutex（可睡眠、可抢占）：

| 项目 | 非 RT | PREEMPT_RT |
|------|-------|-----------|
| `spin_lock()` | 禁用抢占（自旋） | 可睡眠，持有者可被抢占 |
| `spin_lock_irq()` | 关 IRQ | **不关 IRQ**，只获取 rt_mutex |
| `raw_spin_lock()` | 始终自旋 | 始终自旋 |
| `local_lock` | 禁用抢占 | 变为 `spinlock_t` + `migrate_disable()` |

### RT 上的上下文检查

使用 `!preemptible()` 而不是 `in_nmi() || in_hardirq()`：

- `preemptible()` 检查 `preempt_count() == 0 && !irqs_disabled()`
- `in_hardirq()` 只检测硬件中断上下文，**漏掉** `preempt_disable()` 区域和其他不可抢占上下文（如 BPF tracepoint callback）

## 十一、竞态追踪算法速查

### 完整算法

1. 找出所有共享数据——被多个代码路径访问的变量
2. 对每个共享变量，列出所有路径和执行上下文
3. 对每对路径，计算锁集合交集——为空则可能竞态
4. 构建交错时间线——找到具体的错误结果
5. 检查锁上下文兼容性
6. 检查对象生命周期——锁释放后引用或 RCU 是否仍持有？
7. 检查内存顺序——发布模式需要 acquire/release
8. 检查 TOCTOU——条件和操作是否在同一原子区域内？

### 关键警示

- **锁释放后重新获取**：之前的所有验证结果都已过期。重新检查指针、引用计数、条件。
- **函数返回时锁状态变化**：验证调用者知道返回时持有哪个锁，并正确释放。
- **重新赋值加锁对象**：释放旧对象的锁后，再获取新对象的锁。
- **`raw_spinlock_t` 用于硬中断**：在 RT 上，`spinlock_t` 在 IRQ handler 中触发 lockdep splat。
- **回收可到达的锁顺序**：持有 `GFP_KERNEL` 分配相关的锁时，顺序必须在所有回收路径锁之上（如 `->writepages`、shrinkers、`folio_lock()`）。使用 `memalloc_nofs_save()` 保护。
- **不要因为窗口小就放过**：如果顺序违反可能发生，那就是 bug。
- **检查在排除点之前就是没有保护的**：如果代码先检查共享状态再获取互斥，这个检查是 TOCTOU——并发路径可以在检查和互斥之间修改/释放数据。
- **单条恢复路径不保证竞态安全**：必须追踪从竞态窗口到恢复点之间的每条指令。如果任何中间指令解引用、锁定或依赖有争议的资源，竞态会导致崩溃，恢复代码永远不会执行。
