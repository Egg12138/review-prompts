# 资源生命周期与所有权链

## 概述

Linux 内核中，资源（内存、引用计数对象、文件描述符等）的 **生命周期管理** 是大多数 bug 的根源。理解 "谁分配、谁拥有、谁释放" 这三部曲，比单纯检查 "某处是否调用了 kfree" 重要得多。

**核心思想**：不要只问 "这个资源是否被释放了？"，而要问 **"这个资源的所有权链是什么？"**

---

## 一、所有权链的概念

每个内核资源都有明确的生命周期：

```
分配 → 初始化 → 使用 → 清理 → 释放
  ↑        ↑       ↑       ↑       ↑
谁 malloc   谁设置    谁引用    谁解除    谁 free
```

### 所有权链的例子

```c
struct buffer {
    char *data;
    size_t size;
    struct kref refcount;
};

struct buffer *alloc_buffer(size_t sz)
{
    struct buffer *buf = kmalloc(sizeof(*buf), GFP_KERNEL);
    if (!buf)
        return NULL;
    buf->data = kmalloc(sz, GFP_KERNEL);
    if (!buf->data) {
        kfree(buf);          // 内部分配失败→释放外部资源
        return NULL;
    }
    buf->size = sz;
    kref_init(&buf->refcount); // 引用计数从 1 开始
    return buf;                // 所有权转移给调用者
}
```

**所有权分析**：
- `alloc_buffer` 是 `buf` 和 `buf->data` 的创建者
- 返回后，所有权转移给调用者
- 调用者获取第一个引用（来自 `kref_init`），有义务最终释放它

## 二、资源生命周期各阶段的关键问题

### 2.1 分配阶段

| 问题 | 需要检查什么 |
|------|------------|
| 分配会失败吗？ | 是否有 NULL 检查？错误处理路径完整吗？ |
| 子资源分配失败时，已分配的资源是否被正确清理？ | 每个失败路径是否释放了之前分配的资源？ |
| 是否有内存泄漏？ | 分配后是不是所有路径最终都释放了该资源？ |

### 2.2 初始化阶段

- 使用 `kmem_cache_create()` 的 `init_once()` 回调：**只在首次分配时触发**，保护结构体免受垃圾数据污染
- slab 和 vmalloc API 有零填充变体，`__GFP_ZERO` 掩码也能零填充
- **结构体字段迁移时特别注意**：当字段移入子结构体时，搜索父结构体的所有静态实例（如 `init_mm`、`init_task`）并验证它们的初始化器已更新——尤其是锁，需要显式初始化宏（如 `__RAW_SPIN_LOCK_UNLOCKED`），不能依赖零填充

### 2.3 使用阶段

- **引用计数**：`refcount_t` 计数器降到零后不会再增加
  - `refcount_dec_and_test()` 仅在到达零时返回 true
  - 不要假设 `refcount_inc()` 在零之后还能工作
- `css_get()` 增加额外引用
- **锁保护**：使用资源时必须持有适当的锁，确保一致性

### 2.4 清理与释放阶段

- **点后置零**：释放由结构体字段引用的资源后，如果结构体本身不立即释放，应将指针字段设为 NULL
  ```c
  // 危险：释放后不置 NULL
  unregister_foo() {
      foo->dead = 1;
      free(foo->ptr);
      list_add(foo, &free_list);   // foo 仍在 free_list 上
  }
  register_foo() {
      foo = list_entry(...);
      // 没有重新分配 foo->ptr，直接使用 → USE-AFTER-FREE！
      foo->ptr->data = 42;
  }
  ```
  ```c
  // 安全：同时释放 foo
  kfree(foo->ptr);
  ...
  kfree(foo);
  // nobody 能找到 foo，因为 foo 已经不存在
  ```

## 三、引用计数与所有权

### 3.1 基本规则

- 引用计数（`refcount_t`、`kref`）追踪资源的 **活跃引用数量**
- 每个 "获取引用"（get/ref）的操作必须对应一个 "释放引用"（put/unref）的操作
- 当引用计数降到零时，资源被释放（通常通过一个 release 回调）

### 3.2 常见陷阱

```
CPU 0                           CPU 1
─────────────────               ──────────────────
lock → find item                lock → list_del
       take ref                         unlock
       unlock                           
                                  kref_put → release → kfree(item)
item->data ← USE-AFTER-FREE
```

**问题**：在锁保护下获取引用后，随后的锁释放不能保证对象仍然存活。因为另一个 CPU 可能在锁释放后删除了该对象并释放了它。

**修复**：在锁保护下 **同时** 获取引用（ref + unlock），而不是先 unlock 再获取引用。

### 3.3 调用者期望追踪

- 调用者将资源传递给函数时，期望发生什么？
  - 函数会修改资源吗？
  - 函数会获取自己的引用吗？
  - 函数会释放资源吗？
- 函数返回后，哪些锁已被获取、哪些已被释放？
- 函数返回时，资源的所有权是否发生了变化？

## 四、资源切换与锁完整性

### 4.1 资源切换检测

检查每条函数返回路径，确认它没有返回与预期不同的资源：

- 函数被调用来修改资源 A，但在某个路径上却返回了资源 B → 这通常是一个 bug
- 确保在切换资源时，适当的锁被持有或正确释放

### 4.2 锁释放后的资源安全性

当函数释放一个锁然后重新获取它时：

> **所有之前已验证的检查结果都是过期的！**

- 锁释放后，另一个 CPU 可能修改了共享状态
- 重新获取锁后，必须重新验证指针、引用计数、条件等
- 这包括：重新检查 NULL、重新检查引用计数、重新验证条件

## 五、全局与静态变量

### 5.1 自动零填充

- 全局变量和静态变量 **自动零填充**
- 这意味着它们初始时所有字段都是 0/NULL
- 但 **不要依赖于此** 用于锁的初始化——锁需要显式初始化宏

### 5.2 结构体静态实例

当结构体字段布局变化时（如字段移入子结构体）：

```c
// 假设 struct mm_struct 的某个字段移入了子结构体
// 必须检查所有静态实例：
//   extern struct mm_struct init_mm;
//   struct task_struct init_task = { ... };
// 验证它们的初始化器已更新为新布局
```

## 六、实用速查

### 可用的 API 变体

| 目的 | 函数/宏 |
|------|---------|
| 零填充分配 | `kzalloc()`、`kcalloc()`、`__GFP_ZERO` 标志 |
| slab 分配器 | `kmem_cache_create()` + `init_once()` 回调 |
| 引用计数 | `refcount_t` API、`kref` API |
| RCU 保护释放 | `kfree_rcu()`、`call_rcu()` |
| 保证所有 callback 完成 | `rcu_barrier()`（模块卸载时） |

### 所有权追踪清单

分析一个资源时，追踪以下问题：

1. **创建**：谁分配了这个资源？使用什么 API？
2. **传递**：所有权如何传递？通过返回值？通过参数？
3. **共享**：多个组件共享该资源吗？引用计数如何管理？
4. **退出路径**：所有可能退出函数的路径是否都正确处理了资源？（错误路径、提前返回、正常返回）
5. **生命周期匹配**：资源的创建和销毁是否配对？是否存在创建了资源但未销毁的路径？
6. **释放后使用**：资源释放后，是否还有指针指向它？这些指针是否可能被解引用？

### 结构性风险场景

- **栈上的指针指向堆上数据**：函数返回后栈帧消失，堆上的数据如果被其他路径释放 → 悬挂指针
- **释放后未置 NULL 的结构体字段**：结构体重用时，旧指针仍是有效的地址 → 双重释放或 use-after-free
- **中断上下文与进程上下文共享资源**：生命周期管理必须考虑两者
- **模块卸载**：模块卸载前，必须确保模块分配的所有资源已被释放，所有异步操作（如 RCU callback）已完成
