# 调试理论验证与推翻

调试过程中会形成多个关于 bug 原因的理论。本文档描述了如何系统化地验证和推翻这些理论。

## 撤销规则 (Retraction Rule)

如果在分析过程中得出了某个结论是 bug，但后来推翻了该结论，必须以极端的怀疑态度对待这次推翻。

### 正确处理方式

1. **明确陈述撤销** — 记录下你最初认为什么，以及现在为什么改变看法
2. **重新检查驳回推理** — 检查你的驳回理由中是否存在逻辑错误
3. **提高举证标准** — 不要接受模糊的理由

### 不充分的驳回理由

以下理由不足以推翻一个结论：

- "调用者应该阻止这种情况发生"
  - 你必须证明调用者在所有路径上确实阻止了它
- "正常情况下会被处理"
  - 你必须证明在所有代码路径上它都会被处理
- "这种输入在实践中很少见"
  - 可达性就是可达性，不需要高频触发

### 充分的证明要求

要推翻一个结论，必须用**具体的代码引用**证明触发条件在结构上不可能发生——即代码在逻辑上无法到达该状态，无论时序、内存压力或并发操作如何。

## 推断方向

在分析崩溃时，不仅要检查正向规则遵循，还要检查**反向推断**。

### 正向检查 (Forward)

崩溃路径中的代码是否遵守了子系统指南中描述的规则？

### 反向检查 (Reverse)

崩溃是否暗示某条规则的不变量被崩溃路径**之外**的代码违反了？

反向方向最容易捕获最危险的 bug。

**示例：**
- 如果指南说"函数 X 需要锁 L"
- 崩溃路径显示 X 在没有 L 的情况下运行
- 那么 bug 可能不在于 X，而在于本应获取 L 的调用者

### 如何执行反向检查

1. 对于每条加载的指南规则，检查崩溃是否暗示该规则被违反
2. 如果崩溃涉及意外的状态，指南的规则会告诉你其他代码对该状态做了何种假设
3. 加载并检查那些假定了该状态的代码

## 可达性规则 (Reachability)

一条代码路径如果可以崩溃、死锁、破坏数据或无限循环，那么它就是一个 bug——即使你认为前置条件使它不太可能发生。

### 不可接受的驳回理由

| 理由 | 问题 |
|------|------|
| "调用者通常不会传入这种输入" | 不能依赖惯例，必须有结构性保证 |
| "这只在[上游函数]失败时才会发生" | 上游函数失败是正常执行路径之一 |
| "旧代码在同一条路径上有更严重的 bug" | 旧的 bug 不排除新的 bug |
| "实际中极其罕见" | 可靠性要求所有可达路径都是正确的 |

### 可接受的唯一标准

只有当触发条件在结构上不可能发生时才能驳回——这意味着**无论时序、内存压力或并发操作如何，代码都无法到达该状态**。
