# 内核崩溃调试协议

调试 Linux 内核的崩溃 (crash) 或警告 (warning) 时，需要一套系统化的方法来定位根因。本文档描述了完整的七阶段调试协议。

## Phase 1: 提取崩溃信息

从输入中找出所有内核消息，逐条判断其与崩溃的相关性。

### 操作步骤

1. **提取所有时间戳** — 不跳过任何消息中的时间戳
2. **识别事件序列**
   - 单事件崩溃 vs 多阶段故障
   - 启用/禁用/再启用的模式
   - 进程/PID 在不同事件间的变化
3. **将每个时间戳映射到具体操作**
4. **从崩溃跟踪中提取所有函数名**
5. **提取所有数据结构名、错误码和地址**

### 输出格式

```
Crash type: <oops/warning/BUG/RCU stall/lockdep/hung task/other>
Functions in trace: <list>
Data structures mentioned: <list>
Event sequence: <single event / multi-stage, describe>
```

## Phase 2: 收集上下文信息

使用代码分析工具构建崩溃涉及代码的完整图景。这是读取函数定义、类型和调用关系的首选方式。

### 核心工具操作

- 读取函数定义 — 返回完整的函数体
- 读取类型定义 — 返回完整的类型/结构体定义
- 查找调用者 — 找出所有调用某个函数的函数
- 查找被调用者 — 找出某个函数调用的所有函数
- 跟踪调用链 — 向上和向下跟踪调用关系

### 关键原则

**永远不要用 Grep 或 Read 来查找函数定义。** Grep 带有上下文标志会返回截断的输出，遗漏关键的代码路径。只有在代码分析工具不可用时才回退到 Grep/Read，并记录回退日志。

注意：某些宏、常量和全局变量可能不被代码分析工具索引，此时需要使用 Grep。

### 批量调用

每次 API 轮次都会重新发送对话历史。将所有查询批量发送以最小化轮次：

```
正确的做法：一次调用中同时查找 A、B、C 三个函数
错误的做法：分三次依次查找 A、B、C
```

### 需要加载的内容

基于 Phase 1 提取的函数名：

1. 加载崩溃跟踪中每个函数的完整定义
2. 加载崩溃中提到的所有数据结构的类型定义
3. 加载崩溃点函数的调用者和被调用者
4. 按需向两个方向跟踪 2-3 层深度

### 输出格式

```
Functions loaded: <list, with a random line from each to prove you read it>
Types loaded: <list>
Callers of crash function: <list>
Callees of crash function: <list>
```

## Phase 3: 加载子系统指南

使用子系统触发表，将每一行触发条件与崩溃跟踪中的函数、类型、文件路径和符号进行比对。只要有任意触发条件匹配，该子系统即为匹配。

### 子系统交叉分析

加载指南后，逐条分析每条规则与崩溃路径的关系。每个规则需要检查两个方向：

1. **正向 (Forward)**：崩溃路径中的代码是否遵守这条规则？
2. **反向 (Reverse)**：崩溃是否暗示这条规则的不变量被崩溃路径外的代码违反了？如果指南说"函数 X 需要锁 L"，崩溃路径显示 X 在没有 L 的情况下运行，那么 bug 可能在于应该获取 L 的代码。

反向方向最容易捕获最危险的 bug。当崩溃涉及意外的状态时，指南的规则告诉你其他代码对该状态做了何种假设。加载并检查那些代码。

提取指南文本中所有明确命名的函数（规则中的函数、"See X()"、"REPORT as bugs" 指令、示例）。对每个函数，判断它是否出现在崩溃路径中，或者与崩溃路径中的代码交互。如果是，则加载其定义。

### 输出格式

```
Subsystem rule analysis:
  [guide]: [rule summary]
    Forward: [checked/not-applicable] -- [evidence]
    Reverse: [checked/not-applicable] -- [evidence]
    Functions to load: [list or none]

Guide-named functions loaded: [list]
```

## Phase 4: 分析崩溃

在加载所有上下文后进行系统化分析。Phase 1 的崩溃函数是入口点。

### 4a. 应用子系统和技朮模式知识

使用 Phase 3 的子系统交叉分析结果，在开始调用栈分析前，检查崩溃路径是否违反了子系统特定的不变量、API 契约和已知的 bug 模式。

子系统指南的指令具有权威性。当指南说"不要忽视 X"或"将 Y 报告为 bug"时，必须遵循该指令。

### 4b. 调用栈分析

使用崩溃跟踪函数作为入口点进行调用栈分析。完成调用栈分析的所有任务（被调用者遍历、调用者遍历、锁分析、资源分析、RCU 顺序检查、循环分析、初始化检查）。即使认为已经找到了 bug，也不要跳过任何任务。

### 4c. 撤销规则

如果在分析过程中得出了某个结论是 bug，但后来推翻了该结论，则必须以极端的怀疑态度对待这次推翻。明确陈述撤销的理由，重新检查你的驳回推理是否存在逻辑错误，并提高举证标准。"调用者应该防止这种情况"或"正常情况下会被处理"这类理由不充分——必须以具体的代码引用证明触发条件在结构上不可能发生。

### 4d. 可达性

即使你相信前置条件使某个代码路径不太可能发生，只要它可能崩溃、死锁、破坏数据或无限循环，它就是一个 bug。不要用以下理由驳回：

- "调用者通常不会传入这种输入"
- "这只在[上游函数]失败时才会发生"
- "旧代码在同一条路径上有更严重的 bug"
- "实际中极其罕见"

只有当触发条件在结构上不可能发生——即无论时序、内存压力或并发操作如何，代码都**无法**到达该状态——才能驳回。

## Phase 5: 证明 bug

调试时应假定代码是错误的，直到被证明为正确。但 bug 仍然必须用代码片段和调用跟踪来证明。

### 各类 bug 的证据要求

**竞态条件 (Race condition)：**
- 确定具体的数据结构名和定义
- 确定应该保护它们的锁
- 构建一个具体的竞态时间线展示交错执行：
  ```
  CPU 0                              CPU 1
  ----                               ----
  获取锁A
  访问共享数据
                                     获取锁B（不是锁A！）
                                     访问共享数据  <- 未保护
  ```
- 说明后果（数据损坏、释放后使用、脏数据等）

**释放后使用 (Use-after-free)：**
- 精确的数据结构名称和定义
- 释放该结构的精确函数
- 释放后使用该结构的精确函数
- 展示释放和使用的代码片段
- 证明此序列可以发生的调用跟踪

**死锁 (Deadlock)：**
- 涉及的精确锁
- 获取这些锁的精确代码路径
- 展示锁顺序违反（ABBA 模式）或自死锁
- 双方的代码片段

**空指针解引用 (NULL pointer dereference)：**
- 哪个指针是 NULL
- 它应该在何处被设置
- 什么路径导致它为 NULL
- 展示解引用的代码片段

**如果无法证明 bug**，明确说明。提供已有的部分证据并解释缺少什么。

## Phase 6: 识别嫌疑提交

如果已识别出 bug，搜索引入它的提交。

使用代码分析工具搜索 git 历史，查找涉及相关函数或数据结构的提交。也可以使用语义搜索查找相似提交。

### 注意事项

- 如果找到嫌疑提交，必须证明该提交导致了 bug。否则标记为"可能嫌疑"并解释理由
- 如果无法识别嫌疑提交，明确说明
- 除非特别指示，不要尝试运行 addr2line 或检查工作目录中的二进制文件——工作目录的目标文件很可能与崩溃的二进制文件不匹配

在扫描嫌疑提交时，对 bug 的理解可能会改变。如果学到新信息，可以重新开始分析。

## Phase 7: 编写调试报告

### 格式规则

调试报告是纯文本格式，适用于发送到 Linux 内核邮件列表 (LKML)，供内核专家阅读。

- 纯文本，无 markdown 格式
- 使用纯文本缩进、短横线和空格来组织结构
- 代码片段使用简单缩进，不用反引号
- 代码按原样重现，绝不换行
- 代码片段外的长行在 78 字符处换行
- 不使用行号。使用 `文件名:函数名()`、调用链和代码片段提供上下文
- 不要用全大写作强调或章节标题
- 不要使用戏剧化的措辞
- 只给出事实性的解释
- 不要提及本协议中的阶段编号或任务编号
- 使用确定性的陈述，而不是疑问句

### 段落结构

不要编写冗长密集的段落。使用由代码片段或调用链支持的简短确定性陈述。将一系列事实性句子按逻辑分组，组间用空行分隔。

### 报告结构

报告应包含：

1. 被调查问题的摘要
2. 内核版本（如果有）
3. 机器类型（如果有）
4. 清理后的 oops 或栈跟踪副本
5. 其他相关的内核消息
6. 如果找到了嫌疑提交：
   - 提交 SHA 和主题
   - 提交的作者信息
   - 该提交的简要摘要（最多 3 句）
   - 提交头部的任何 Link: 标签
   - 嫌疑提交的引用 diff，附在漏洞代码旁边的分析（行内引用格式）
7. 如果未找到嫌疑提交：
   - 问题说明
   - 与问题相关的函数、代码片段和调用跟踪
   - 可能与问题相关的提交列表
   - 建议的修复或嫌疑代码，附代码片段和解释

### 行内引用格式（用于嫌疑提交）

引用嫌疑提交的 diff 时，如同在邮件列表上回复它：

- 使用代码分析工具或 git log 重新生成 diff
- 每行用 `> ` 前缀引用 diff
- 将分析放在引入 bug 的代码旁
- 分析文本前不要加 `> `
- 分析尽量靠近漏洞代码
- 积极剪裁与 bug 无关的 diff 部分：
  - 用 `[ ... ]` 替换剪裁内容
  - 剪裁整个无关文件
  - 剪裁无关的整个 hunk
  - 保留保留文件的 diff 头部
  - 从不包含完全剪裁文件的 diff 头部

示例格式：

```
commit 06e4fcc91a224c6b7119e87fc1ecc7c533af5aed
Author: Some Developer <dev@example.com>

subsystem: fix the things

<对该提交的简要描述>

> diff --git a/path/to/file.c b/path/to/file.c
> --- a/path/to/file.c
> +++ b/path/to/file.c

[ ... ]

> @@ -100,10 +100,8 @@ static int frobulate(struct device *dev)
>       foo = get_resource(dev);
> -     if (!foo)
> -             return -ENOMEM;
> +     bar = transform(foo);

对 get_resource() 的空值检查被移除了。当 get_resource() 返回 NULL 时，transform() 解引用它：

path/to/file.c:transform() {
    ...
    result = foo->field;   <-- NULL dereference
    ...
}

>       return process(bar);
```

### 验证报告

写完调试报告后，验证：
- 文件存在于文件系统中
- 不包含 markdown 格式
- 不包含全大写标题
- 使用纯文本缩进和短横线，而非 markdown 列表
- 代码片段使用缩进而非反引号
- 长行（代码除外）在 78 字符处换行
- 如果引用了提交 diff，引用部分与原提交完全一致
