# 调试报告生成

调试报告 (`debug-report.txt`) 是用于发送到 Linux 内核邮件列表 (LKML) 的纯文本文档。本文档描述了如何编写高质量的内核调试报告。

## 核心格式规则

调试报告是纯文本，供 Linux 内核专家阅读。

| 规则 | 说明 |
|------|------|
| 纯文本 | 不使用 markdown 格式（不用 \`\`\`、\*\*、[] 等） |
| 缩进 | 使用纯文本缩进、短横线和空格组织结构 |
| 代码片段 | 使用简单缩进，不用反引号包裹 |
| 代码保真 | 按原样重现代码，绝不换行 |
| 换行 | 非代码行在 78 字符处换行 |
| 行号 | 从不使用行号。使用 `文件名:函数名()`、调用链和代码片段提供上下文 |
| 大小写 | 不要使用全大写作强调或标题 |
| 语气 | 不用戏剧化措辞，如"this is a classic example of..." |
| 阶段编号 | 不提及调试协议中的阶段编号或任务编号 |

### 确定性陈述

使用确定性的陈述，而非疑问句：

| 不要写 | 要写 |
|--------|------|
| "this code path can corrupt memory?" | "this code path corrupts memory because..." |
| "does this code leak the folio?" | "this code leaks the folio when..." |
| "can this cause a double-free?" | "this causes a double-free because..." |

### 精确命名

指出具体涉及的资源、结构和函数名。不要使用模糊描述：

| 不要写 | 要写 |
|--------|------|
| "resource leak" | "folio leak" 或 "sk_buff leak" |
| "memory issue" | "use-after-free in foo_struct" |
| "locking problem" | "ABBA deadlock between lock_a and lock_b" |

## 段落结构

- 不要使用冗长密集的段落
- 使用由代码片段或调用链支持的简短确定性陈述
- 将一系列事实性句子按逻辑分组，组间用空行分隔

## 报告结构

### 基本信息

1. **问题摘要** — 简要描述被调查的问题
2. **内核版本** — 如果有则提供
3. **机器类型** — 如果有则提供
4. **清理后的 oops 或栈跟踪** — 从原始输出中清理不必要的噪音
5. **其他相关内核消息** — 你认为相关的其他内核消息

### 找到嫌疑提交时

- 提交 SHA 和主题行
- 提交的 Author 信息
- 提交的简要摘要（最多 3 句）
- 提交头部的任何 Link: 标签
- 嫌疑提交的引用 diff，附分析（见行内引用格式）

### 未找到嫌疑提交时

- 问题的详细解释
- 函数、代码片段和调用跟踪
- 可能与问题相关的提交列表
- 建议的修复方向或嫌疑代码，附解释

## 行内引用格式

引用嫌疑提交的 diff 时，如同在邮件列表上回复它：

1. 使用代码分析工具或 git log 重新生成 diff，不要使用记忆中的片段
2. 每行用 `> ` 前缀引用 diff
3. 将分析放在引入 bug 的代码旁
4. 分析文本前不加 `> `
5. 积极剪裁与 bug 无关的 diff 部分：
   - 剪裁内容用 `[ ... ]` 替换
   - 剪裁整个无关文件
   - 剪裁无关的整个 hunk
   - 保留保留文件的 diff 头部
   - 从不包含完全剪裁文件的 diff 头部

### 示例

```
commit 06e4fcc91a224c6b7119e87fc1ecc7c533af5aed
Author: Some Developer <dev@example.com>

subsystem: fix the things

<对该提交的简要描述>

> diff --git a/path/to/file.c b/path/to/file.c
> --- a/path/to/file.c
> +++ b/path/to/file.c

[ ... ]

> @@ -100,10 +100,8 @@ static int frobulate(struct device *dev)
>       foo = get_resource(dev);
> -     if (!foo)
> -             return -ENOMEM;
> +     bar = transform(foo);

对 get_resource() 的空值检查被移除了。当 get_resource() 返回 NULL 时，transform() 解引用它：

path/to/file.c:transform() {
    ...
    result = foo->field;   <-- NULL dereference
    ...
}

>       return process(bar);
```

## 验证清单

写完调试报告后，逐项验证：

- [ ] 文件存在于文件系统中
- [ ] 不包含 markdown 格式
- [ ] 不包含全大写标题
- [ ] 使用纯文本缩进和短横线，而非 markdown 列表
- [ ] 代码片段使用缩进而非反引号
- [ ] 长行（代码片段除外）在 78 字符处换行
- [ ] 如果引用了提交 diff，引用部分与原提交完全一致
