# 补丁追溯与嫌疑人定位

当你已经识别出 bug，下一步是找到引入该 bug 的提交 (commit)。本文档描述了如何搜索 git 历史来定位"嫌疑提交"。

## 搜索策略

### 使用代码分析工具搜索

代码分析工具提供了多种搜索 git 历史的模式：

- **符号模式** — 搜索涉及特定函数或数据结构的提交
- **主题模式** — 搜索提交消息主题中包含特定关键词的提交
- **正则表达式模式** — 使用正则表达式搜索提交内容
- **语义搜索** — 查找语义相似的提交

## 迭代理解

在扫描嫌疑提交的过程中，对 bug 的理解可能会发生变化。这是正常的，应该：

- 当学习到新信息时，**重新开始分析**
- 新的信息可能来自：
  - 在嫌疑提交中发现的额外上下文
  - 发现 bug 的根源比最初认为的更深
  - 发现多个提交共同导致了 bug

## 证明要求

### 明确的嫌疑提交

如果找到一个嫌疑提交，**必须证明**该提交确实导致了 bug：

- 展示该提交的 diff 中引入的代码如何导致崩溃
- 使用代码片段和调用跟踪建立因果链
- 在调试报告中以行内引用格式呈现分析

### 不确定的嫌疑提交

如果不能确切证明，则标记为"可能嫌疑"并说明理由：

- 解释为什么认为该提交可能相关
- 说明缺少哪些证据
- 建议需要进一步检查的方向

### 找不到嫌疑提交

如果无法识别嫌疑提交，明确说明。在调试报告中：

- 提供问题的详细解释
- 列出可能与问题相关的函数和代码路径
- 建议可能的修复方向

## 工具限制说明

除非特别指示，不需要运行 addr2line 或检查工作目录中的二进制文件。原因是工作目录中的目标文件很可能与崩溃的二进制文件不匹配，这样做会产生误导。

## 向前与向后追溯

### 向后追溯（找引入者）

从当前 bug 出发，回溯 git 历史找到引入 bug 的提交：

1. 确定涉及的具体函数和数据结构
2. 搜索这些符号的历史变更
3. 评估每次变更是否可能引入当前 bug

### 向前追溯（找修复者）

从已知的旧 bug 出发，检查它是否在后续版本中被修复：

1. 确定疑似存在 bug 的旧提交
2. 搜索其后续的修复提交
3. 验证修复是否完整、正确
