# 主观代码质量评估

## 概述

代码审查不仅仅是发现漏洞，还包括对代码可读性、可维护性和设计质量的**主观评估**。本章提供一套结构化 checklist，帮助评估代码的"软质量"维度。

> 注意：不要对单个低级的语法问题（如 `its` vs `it's`）单独标记，除非这些问题累积到影响理解的程度。

---

## 代码清晰度与复杂度

### 可读性判断

代码是否整洁且易于理解？内核中充斥着复杂和晦涩的代码，因此在评判时应将新代码与附近既有代码进行比较：

- 新代码是否与周围代码保持了相同的可读性水平？
- 是否存在不必要的抽象或间接层？

### 是否有更简单的方案

当前实现是否存在更简单的替代方案？思考时需考虑内核的性能约束：

- 更简单的方案是否仍满足性能要求？
- 是否有内核惯用写法（kernel idiom）可以替代自定义实现？

---

## 代码重复分析

### 变动内部的重复

检查当前 diff 内部是否存在重复代码：

- 同一 commit 内是否有逻辑相同、仅参数不同的代码块？
- 是否可以提取公共函数？

### 与既有代码的重复

检查 diff 是否重复了已有的相关函数：

- 内核中是否已有实现相同功能的函数？
- 是否可以通过参数化或回调复用现有函数？

---

## API 分析

### 新增 API

当引入新的 API 时，评估以下方面：

- **结构一致性**：新 API 的结构和预期是否与既有 API 一致？
- **命名与参数顺序**：函数命名和参数顺序是否一致？
- **锁与生命周期**：加锁（locking）、分配（allocation）和释放（free）的预期是否清晰且文档化？

### 使用既有 API

当使用既有 API 时，检查：

- 使用方式是否访问了不该暴露的内部/私有字段（internal/private fields）？
- 是否存在绕过 API 抽象层的做法？

---

## Commit 信息验证

### 标题与内容一致性

比较 commit title 和 message 与实际代码变更：

- title 是否准确概括了变更？
- message 是否与代码逻辑一致？

### 变更日志完整性

- 是否描述所有重要变更？（changlog 应记录每处有意义的变化）
- 是否过于冗长？（避免不必要的细节）
- 是否解释了"为什么"（why）而不仅仅是"做了什么"（what）？

### 上下文提供

- 是否提供了有助于 reviewer/maintainer 理解变更的背景信息？
- 是否缺少关键的上下文（如相关讨论、设计决策、已知限制）？

---

### Commit 上下文

- 是否提供了有助于 reviewer/maintainer 理解变更的背景信息？
- 是否缺少关键的上下文（如相关讨论、设计决策、已知限制）？
