# 锁与竞态 —— 系统化竞态追踪指南

## 1. 核心思维模型

竞态条件（race condition）是两个 CPU 以特定交叉顺序执行指令产生错误结果的场景。要找到竞态，需要显式地构建这些时间线。

在每个代码路径的每个点上问：**"另一个 CPU 此刻可能在做什么？"** 答案：该 CPU 在其自身代码路径上的任何点都可能在做任何事情，除非有同步机制强制了顺序。

---

## 2. 逐步追踪方法

### Step 1：识别共享数据

共享数据包括全局变量、全局可访问对象内的字段（如 `inode->i_size`）、引用计数、状态标志和链表指针。从多个代码路径访问的任何 struct 成员都可能是共享的。

### Step 2：枚举所有代码路径

对于每个共享变量，列出所有读取或写入它的代码路径：syscall handlers, interrupt handlers (hardirq, softirq), workqueue callbacks, timer functions, tasklets, module init/exit, network receive paths (NAPI poll)。每对路径都是需要分析的潜在竞态。

### Step 3：构建时间线

取两个代码路径并排放置。找到产生错误结果的交叉执行。

例子 —— 链表上的 TOCTOU 竞态：
```
CPU 0 (delete)                    CPU 1 (add)
──────────────                    ──────────
list_empty() returns TRUE
  → decides to skip delete
                                  spin_lock_bh(&lock)
                                  list_add(&rt->rt6i_uncached, &list)
                                  spin_unlock_bh(&lock)
return (skips deletion!)
→ rt is on the list but should have been removed → use-after-free on free
```
检查（`list_empty`）和动作（`list_del_init`）不在同一个原子区域内。

### Step 4：Lockset 分析

对每个共享变量 V，计算所有线程访问它的锁集合的交集。如果交集为空，则没有单个锁在所有访问路径上保护 V —— 潜在竞态。

```
Path A: spin_lock(&obj->lock); obj->counter++; spin_unlock(&obj->lock);
Path B: obj->counter--;  // no lock held

L(A) = {obj->lock}, L(B) = {}
C(obj->counter) = {obj->lock} ∩ {} = {} → RACE
```

锁还必须是适用于执行上下文的正确**类型** —— 见锁上下文兼容性（§4）。

### Step 5：检查对象生命周期

在每个路径释放锁或放弃引用的点上，问："另一个路径可能仍持有指向此对象的原始指针吗？"

```
CPU 0 (lookup)                    CPU 1 (remove)
──────────────                    ──────────────
lock → find item → unlock
                                  lock → list_del → unlock → kfree(item)
item->data ← USE-AFTER-FREE
```

修复：在锁下释放前获取引用计数。

---

## 3. 每个访问点的四个问题

在每个读取或写入共享变量的代码行上：

**Q1：持有什么锁？** 向后追溯调用链。查找 `lockdep_assert_held()`、`__` 前缀函数（约定：调用者持有锁）、调用链上游的直接锁调用。

**Q2：现在什么其他路径可能访问此数据？** 另一个 CPU 运行同一个 syscall（不同对象）、此 CPU 上的中断、timer/workqueue、并发的 `close()` 或模块卸载。

**Q3：锁类型是否足够强？** 一个也从中断处理程序访问的数据仅用 `spin_lock()` 保护是不够的 —— 见 §4。

**Q4：对象是否仍然活着？** 指针是在仍持有的锁或 RCU 读侧临界区内获取的吗？获取了引用计数吗？如果都不是，对象可能已被释放。

## 4. 锁上下文兼容性

使用错误类型的锁会导致死锁（在原子上下文中睡眠）、错过唤醒或优先级反转。

| 锁变体 | 等待类型 | vs 进程 | vs Softirq | vs Hardirq | 可睡眠？ |
|-------|---------|---------|-----------|-----------|---------|
| `raw_spin_lock` | LD_WAIT_SPIN | 是 | 否 | 否 | 否 |
| `raw_spin_lock_irqsave` | LD_WAIT_SPIN | 是 | 是 | 是 | 否 |
| `spin_lock` | LD_WAIT_CONFIG | 是 | 否 | 否 | 非RT: 否 / RT: 是 |
| `spin_lock_bh` | LD_WAIT_CONFIG | 是 | 是 | 否 | 非RT: 否 / RT: 是 |
| `spin_lock_irq` | LD_WAIT_CONFIG | 是 | 是 | 是 | 非RT: 否 / RT: 是 |
| `spin_lock_irqsave` | LD_WAIT_CONFIG | 是 | 是 | 是 | 非RT: 否 / RT: 是 |
| `local_lock` | LD_WAIT_CONFIG | Per-CPU | 否 | 否 | 非RT: 否 / RT: 是 |
| `local_trylock` | LD_WAIT_CONFIG | Per-CPU | 否 | 否 | 非RT: 否 / RT: 是 |
| `mutex` / `rwsem` | LD_WAIT_SLEEP | 是 | 否 | 否 | 是 |

### 关键规则

- `spin_lock` 不会屏蔽 softirq 或 hardirq
- `spin_lock_bh` 禁用 softirq；在进程和 softirq 上下文之间共享时使用
- `mutex`/`rwsem` 仅在进程上下文可用（它们会睡眠）；绝不在持有 spinlock 时获取 mutex/rwsem
- 在 `spin_lock_irq`/`_bh`/`_irqsave(A)` 内嵌套 `spin_lock(B)` 会保持 A 的屏蔽状态到 B 持有期间；锁必须保持嵌套

## 5. 锁嵌套兼容性

Lockdep 强制等待类型嵌套：内层锁等待类型必须 ≤ 外层（`CONFIG_PROVE_RAW_LOCK_NESTING` 默认 `y`，即使在非 RT 内核上也强制执行）。`!IS_ENABLED(CONFIG_PREEMPT_RT)` 守卫不会抑制这些检查。任何违规都是 bug。

| 外层持有的锁 | 可嵌套 | 不可嵌套（lockdep BUG） |
|------------|--------|---------------------|
| `raw_spinlock_t` | `raw_spinlock_t` | `spinlock_t`, `local_lock`, `local_trylock`, `mutex`, `rwsem` |
| `spinlock_t` | `raw_spinlock_t`, `spinlock_t`, `local_lock`, `local_trylock` | `mutex`, `rwsem` |
| `local_lock` / `local_trylock` | `raw_spinlock_t`, `spinlock_t`, `local_lock`, `local_trylock` | `mutex`, `rwsem` |
| `mutex` / `rwsem` | 全部 | — |

有意违规的修复：`DEFINE_WAIT_OVERRIDE_MAP(map, LD_WAIT_CONFIG)` 配合 `lock_map_acquire_try(&map)` / `lock_map_release(&map)`。这告诉 lockdep 嵌套是故意的。

检查方法：如果代码获取 `spinlock_t`、`local_lock` 或 `local_trylock`，检查任何调用者是否持有 `raw_spinlock_t`。如果代码持有 `raw_spinlock_t`，检查任何被调用者是否获取 `spinlock_t`、`local_lock` 或 `local_trylock`。

## 6. 多变量竞态

最微妙的竞态涉及多个必须一起原子更新的变量。每个单独的访问可能有锁，但变量之间的关系未受保护。

```
CPU 0                                CPU 1
──────                               ──────
lock → set state=ACTIVE → unlock
                                     lock → read state=ACTIVE
                                             call handler → OLD handler!
                                     unlock
lock → set handler=new → unlock
```

两个变量必须在同一个临界区更新。

**不要因为"窗口很小"就认为未锁定的共享变量访问是安全的。** 如果顺序违规可能发生，那就是 bug。

## 7. 内存顺序（Memory Ordering）

即使使用 `READ_ONCE()`/`WRITE_ONCE()`，CPU 也可能重排 store 和 load。发布指向已初始化数据的指针时：

```c
// 错误 —— Store 2 可能在 Store 1 之前可见：
data->field = 42;                      // Store 1
WRITE_ONCE(global_ptr, data);          // Store 2

// 正确 —— release barrier 确保 Store 1 在 Store 2 之前完成：
data->field = 42;
smp_store_release(&global_ptr, data);

// 消费者必须使用 acquire：
p = smp_load_acquire(&global_ptr);
if (p) x = p->field;                  // 保证看到 42
```

`rcu_assign_pointer()` 和 `rcu_dereference()` 包含这些 barrier。

### Barrier 类型

- `smp_mb()`：完整 barrier，排序所有 load 和 store
- `smp_rmb()`：读 barrier，仅排序 load
- `smp_wmb()`：写 barrier，仅排序 store
- Barrier 强制顺序，而非完成：它们阻止 CPU 和编译器跨越 barrier 点重排
- Barrier 必须在 CPU 之间成对：生产者的 `smp_wmb()` 与消费者的 `smp_rmb()` 配对
- 常见模式：
  ```
  producer:                       consumer:
    my_data = value;                if (event_indicated) {
    smp_wmb();                          smp_rmb();
    event_indicated = 1;                do_something(my_data);
                                    }
  ```
- `atomic_read()`/`atomic_set()` 是 relaxed 的 —— 无顺序保证。返回值型 RMW 操作（`atomic_add_return()`, `atomic_cmpxchg()`）提供完整顺序。对于需要顺序的普通 load/store，使用 `smp_load_acquire()`/`smp_store_release()` 或 `_acquire`/`_release` 原子变体。

## 8. 中断时间线

中断在单个 CPU 上创建并发。处理程序抢占正在运行的代码。

```
CPU 0 (process context)
──────────────────────
spin_lock(&data_lock)        ← acquired, IRQs not disabled
shared_counter++
  ← IRQ fires on THIS CPU
  ├─ IRQ handler: spin_lock(&data_lock) → DEADLOCK
  │   (we hold the lock but can't continue)
  └─ Never returns
```

如果从进程和 hardirq 上下文使用同一个锁，所有进程上下文的锁获取必须使用 `spin_lock_irqsave()`。如果仅与 softirq 共享，进程上下文必须使用 `spin_lock_bh()`。

## 9. RCU 关键点

### 读侧临界区

- `rcu_read_lock()` 标记 RCU 读侧临界区；内部不能睡眠。需要在读侧睡眠时使用 SRCU（`srcu_read_lock()`/`srcu_read_unlock()` 配合 domain-specific `struct srcu_struct`）
- 持有 `spin_lock()` 或 `raw_spin_lock()` 隐式提供 RCU 读侧保护（在非 RT 上禁用抢占；在 PREEMPT_RT 上，`spin_lock()` 内部调用 `rcu_read_lock()`）

### 写侧生命周期

`rcu_assign_pointer()` 替换指针后，旧指针必须通过 `call_rcu()`, `kfree_rcu()` 或在 `synchronize_rcu()` 之后释放。直接 `kfree()` 总是 bug。

使用 `call_rcu(&old->rcu_head, free_fn)` —— 回调仅在所有已存在的 RCU 读侧临界区完成后运行。

- `synchronize_rcu()`：阻塞直到所有已存在的 RCU 读侧临界区完成（一个完整的 grace period）
- `call_rcu(head, callback)`：延迟回调到 grace period 之后；不阻塞

---

## 10. 抢占、迁移、中断和 CPU 热插拔

### 概念辨析

- **抢占禁用**（`preempt_disable()`/`preempt_enable()`）：任务留在此 CPU 上，不会被调度出去。IRQ 仍可发生。对 per-CPU 数据访问是安全的。`spin_lock()` 在非 RT 上隐式禁用抢占。
- **迁移禁用**（`migrate_disable()`）：任务可被抢占但返回同一 CPU。当 per-CPU 访问不需要原子性但必须保持在同一 CPU 时使用。
- **IRQ 禁用**（`local_irq_disable()`/`local_irq_save()`）：此 CPU 上无硬件中断。隐式意味着抢占禁用（调度器的 timer tick 是一个 IRQ）。
- **CPU 热插拔**（`cpus_read_lock()`/`cpus_read_unlock()`）：阻止 CPU 上线/下线。使用已分配在 hotplug 回调（`cpuhp_setup_state()`）中的 per-CPU 资源时需要。抢占禁用和迁移禁用都不阻止 hotunplug —— 它们只固定任务。`cpus_read_lock()` 获取 `cpu_hotplug_lock` 作为 `percpu_rw_semaphore` —— 它会睡眠，不能在原子上下文中持有。

**Invariants**：抢占、迁移和 IRQ 禁用**都不能阻止 CPU 热插拔**。当代码从 `get_cpu_ptr()` 切换到 `raw_cpu_ptr()` 以适应可睡眠 API 时，验证 CPU 热插拔拆除仍然安全。

---

## 11. IRQ 安全的锁变体

- `spin_lock_irq()`/`spin_unlock_irq()`：锁定时禁用 IRQ，解锁时重新启用。仅当调用者知道 IRQ 已启用时才安全。
- `spin_lock_irqsave(lock, flags)`/`spin_unlock_irqrestore(lock, flags)`：保存/恢复 IRQ 状态。无论当前状态如何都安全。当调用上下文未知时使用。
- 所有与 IRQ 上下文共享的锁的持有者必须禁用 IRQ 才能安全地获取它。仅从 IRQ 已关闭时可达的代码路径使用普通 `spin_lock()`（无 IRQ 屏蔽）是安全的。

---

## 12. PREEMPT_RT 差异

- **`spinlock_t` on RT** 变成可睡眠的 rt_mutex。持有者可以被抢占。仍不能在其内嵌套 `mutex`/`rwsem`。不能在 hardirq 上下文中或明确禁用抢占/IRQ 时持有。
- **`raw_spinlock_t`**：即使在 RT 上也是真正的自旋锁。用于 hardirq 上下文、调度器、中断控制器、底层定时器代码。
- **`local_lock` / `local_lock_irqsave()`**：非 RT 上禁用抢占或 IRQ（没有实际的锁）。RT 上映射到 `spinlock_t` + `migrate_disable()`，因此可以睡眠。使用 `!preemptible()` 守卫，而非 `in_nmi() || in_hardirq()` —— 后者遗漏了 `preempt_disable()` 段。
- **`spin_lock_irq()` on `spinlock_t`** 在 RT 上不会禁用 IRQ（它在不屏蔽中断的情况下获取底层 rt_mutex）。
- **`local_irq_disable()`** 在 RT 上仍然禁用 IRQ。
- **`raw_spinlock_t` 代码不能获取 `spinlock_t`, `local_lock` 或 `local_trylock`** —— 见锁嵌套（§5）。

## 13. Seqlocks

用于读重写轻数据的读者-写者机制。读者从不阻塞写者（无写者饥饿）。读者投机性地读取数据，然后检查序列计数器；如果写者活动则重试。

### 读侧

`read_seqbegin()` 和 `read_seqretry()` 之间的所有代码可能重新执行。临界区必须没有副作用（无分配、无共享状态写入、无 I/O），并且不能解引用写者可能释放的指针；使用 `rcu_dereference()`。

### 写侧

`write_seqcount_begin()`/`write_seqcount_end()` 必须正确配对。不匹配的计数会导致无限读者重试（缺少 end）或错过重试（缺少 begin）。

### 变体

`seqlock_t` 将 `seqcount_spinlock_t` 与 `spinlock_t` 捆绑以进行写者序列化。当写者序列化由外部锁提供时使用裸 `seqcount_t`。

`raw_write_seqcount_begin()`/`raw_write_seqcount_end()` 跳过 lockdep 断言；仅在序列化由不同机制提供时有效。

## 14. 锁注释

- **嵌套子类**：`mutex_lock_nested(lock, subclass)` 或 `spin_lock_nested(lock, subclass)` 用于区分不同嵌套级别的同类型锁（如父/子 inode 锁）。最多 `MAX_LOCKDEP_SUBCLASSES` (8) 级。子类 0 是默认值。
- **Sparse 注释**：`__must_hold(lock)`, `__acquires(lock)`, `__releases(lock)`。不匹配的注释会导致 sparse 上下文不平衡警告。验证注释与实际的锁行为匹配。

---

## 15. Lockdep 锁钉（Lock Pinning）

`lockdep_pin_lock(lock)` 在当前任务的锁栈中查找 `lock` 的 `held_lock` 条目并增加其 `pin_count`。当任何持有的锁被释放时，lockdep 通过 `find_held_lock()` 检查 `hlock->pin_count` 并在非零时警告。

对于基于 `ww_mutex` 的锁（如 `dma_resv`），其中多个实例共享一个 `held_lock` 条目（通过引用计数 `references > 0`），锁定该条目然后解锁任何折叠的实例会触发"releasing a pinned lock"警告。

```c
// 错误：锁定 ww_mutex 基锁时，其他实例可能被解锁
lockdep_pin_lock(&vm->resv->lock.base);
ttm_bo_validate(...);  // 可能锁定/解锁其他 bos' dma_resv locks
lockdep_unpin_lock(&vm->resv->lock.base);  // Lockdep 在 validate() 中警告了！
```

安全条件：锁定区域只操作特定的固定实例，不调用可能释放该实例或共享该 `held_lock` 条目的回调，也不遍历共享该锁类的对象列表。

钉锁不安全时的替代方案：使用标志或指针变量来跟踪锁定本应强制执行的状态（如 `vm->validating = current`），或在关键点使用 `lockdep_assert_held()` 而不是连续钉锁。

## 16. 完整的工作示例

```c
static LIST_HEAD(conn_list);
static DEFINE_SPINLOCK(list_lock);

// Path A: add_connection (process context)
//   spin_lock(&list_lock); list_add(&c->list, &conn_list); spin_unlock();
// Path B: receive_data (softirq context)
//   list_for_each_entry(c, &conn_list, list) { ... }  ← NO LOCK
// Path C: remove_connection (process context)
//   spin_lock(&list_lock); list_del(&c->list); spin_unlock(); kfree(c);
```

**Lockset 分析** Path B vs Path C：
- Path B 访问 `conn_list`：L(B) = {}（无锁）
- Path C 访问 `conn_list`：L(C) = {list_lock}
- C(conn_list) = {} → RACE

**时间线（B vs C）**：
```
CPU 0 (Path B: softirq)           CPU 1 (Path C: process)
────────────────────               ────────────────────
c = first entry, no match
next_c = c->list.next
                                   lock → list_del(c) → unlock → kfree(c)
c = next_c ← FREED MEMORY
```

**发现的四个 bug**：
1. Path B 没有链表锁 → 与 Path C 在链表遍历上竞态
2. Path C 使用 `spin_lock()` 但 Path B 在 softirq 运行 → 必须使用 `spin_lock_bh()` 阻止同 CPU 上的 softirq 抢占
3. Path B 需要 `rcu_read_lock()` + `list_for_each_entry_rcu()`，或者 `spin_lock_bh(&list_lock)`
4. RCU 修复后，Path C 的 `kfree(c)` 必须变成 `kfree_rcu(c, rcu_head)` 或跟随 `synchronize_rcu()`

## 17. Invariants / Failure Modes / Quick Checks

### Invariants

- **锁释放后重新获取**：所有先前的验证都失效。重新获取后重新检查指针、引用计数和条件。
- **函数返回时持有不同锁**：验证调用者知道返回时持有哪个锁，并释放正确的那个。
- **重新分配锁定对象**：验证在获取新对象锁之前释放了旧对象的锁。
- **`raw_spinlock_t` for hardirq on RT**：IRQ 处理程序中的 `spinlock_t` 会在 RT 上触发 lockdep splat。
- **RT 上的上下文守卫**：使用 `!preemptible()`，而非 `in_nmi() || in_hardirq()` —— 后者遗漏了 `preempt_disable()` 段。
- **Completion 变量**：使用 `wait_for_completion()`/`complete()` 而不是开放的 spinlock 轮询循环。
- **`percpu_rw_semaphore`**：适用于读远超写的读重模式，避免缓存行 bouncing。
- **回收可达的锁顺序**：`GFP_KERNEL` 分配期间持有的锁必须排在所有回收路径锁（`->writepages`, shrinkers, `folio_lock()`）之上。Lockdep 通过 `__GFP_FS` / `__GFP_IO` / `__GFP_RECLAIM` 标志和 `memalloc_nofs` / `memalloc_noio` 作用域注释检测。持有与 filesystem 回收冲突的锁时使用 `memalloc_nofs_save()`。

### Failure Modes

- **验证检查在排除点之前不是保护**：如果代码检查共享状态然后获取排他权，检查是 TOCTOU —— 并发路径可以在检查和排他权获取之间修改/释放数据。不要以"检查会发现它"为由 dismiss。
- **单个中止路径不能使竞态安全**：评估竞态是否"已处理"时，你会找到一个恢复点并停止查找。这是错误的。你必须跟踪从竞态窗口到恢复点之间的每条指令。如果任何中间指令解引用、锁定或依赖有争议的资源，竞态会在恢复执行之前导致 crash。
- **子系统指南指令具有权威性**：当指南说"Do NOT dismiss X"或"REPORT as bugs"时，不要用自己的推理覆盖它。

### Quick Checks

1. 找到所有共享数据 —— 从多个代码路径访问的变量
2. 对每个变量，列出所有路径及其执行上下文
3. 对每对路径，计算 lockset 交集 —— 空 = 潜在竞态
4. 构建交叉时间线 —— 找到具体的错误结果
5. 检查锁上下文兼容性（§4）
6. 检查对象生命周期 —— 锁释放后引用或 RCU 仍持有？
7. 检查内存顺序 —— 发布模式需要 acquire/release
8. 检查 TOCTOU —— 条件和动作在同一个原子区域？
