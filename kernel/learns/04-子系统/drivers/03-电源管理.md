# 电源管理（Power Management）子系统

## 概述

Linux 电源管理子系统包含系统级 PM（suspend/resume/hibernate）和运行时 PM（Runtime PM）。本文聚焦运行时 PM 返回值契约、并发控制、休眠模式处理以及 PM 回调的条件编译等关键细节。

---

## 运行时 PM 返回值契约

### 关键知识点

三个基础运行时 PM 函数具有不同的返回语义，调用者必须正确区分：

#### `__pm_runtime_suspend()` — 挂起路径

被 `pm_runtime_suspend()`、`pm_runtime_autosuspend()`、`pm_runtime_put_sync_suspend()`、`pm_runtime_put_sync_autosuspend()` 和 `__pm_runtime_put_autosuspend()` 使用。

- 返回 **1**：设备已经是 `RPM_SUSPENDED` 状态
- 返回 **0**：挂起成功或异步请求已排队
- 返回负 errno：失败（`-EAGAIN`、`-EBUSY`、`-EACCES` 等）

**1 是成功情况，不是错误**。

#### `__pm_runtime_idle()` — 空闲路径

被 `pm_runtime_idle()`、`pm_request_idle()`、`pm_runtime_put()` 和 `pm_runtime_put_sync()` 使用。

- `pm_runtime_idle()` 和 `pm_request_idle()`（不使用 `RPM_GET_PUT` 调用时）**不能**返回 1——当设备已是 `RPM_SUSPENDED` 时，`rpm_idle()` 返回 `-EAGAIN`，因为状态不是 `RPM_ACTIVE`
- `pm_runtime_put()` 和 `pm_runtime_put_sync()`（使用 `RPM_GET_PUT` 调用时）**可以**返回 1——当设备已是 `RPM_SUSPENDED` 时，`rpm_idle()` 中有一个特殊情况允许 put 路径成功
- 返回 **0**：空闲检查通过，auto-suspend 已调度或挂起完成

#### `__pm_runtime_resume()` — 恢复路径

被 `pm_runtime_resume()`、`pm_request_resume()`、`pm_runtime_get_sync()` 和 `pm_runtime_get()` 使用。

- 返回 **1**：设备已经是 `RPM_ACTIVE` 状态
- 返回 **0**：恢复成功或异步请求已排队
- 返回负 errno：失败

### 故障模式

对每个 API 可能返回的值理解错误会导致：
- 将返回 1 误认为失败（实际上 1 表示"已经是目标状态"，属于成功）
- 错误处理不正确
- 遗漏唤醒事件
- 将成功当作失败处理

## 并发与锁

### 不变式

所有运行时 PM 状态转换由每个设备独立的 spinlock 串行化：`dev->power.lock`（定义在 `struct dev_pm_info` 中，位于 `include/linux/pm.h`）。

### 竞态场景

**使用计数器竞态**：`pm_runtime_put()` 可能将使用计数器降到零，但另一个线程可能在 `rpm_idle()` 运行前调用 `pm_runtime_get()`。随后的空闲检查看到非零使用计数器，返回 `-EAGAIN`。这是预期行为，不是 bug。

**子设备计数竞态**：`rpm_check_suspend_allowed()` 在 `child_count` 非零且未设置 `ignore_children` 时返回 `-EBUSY`。子设备可能并发恢复，在调用者进行初始 eligibility 检查后增加父设备的子计数。

**状态转换竞态**：当一个线程已在挂起或恢复设备时，并发尝试返回 `-EINPROGRESS`（异步调用者）或 `-EAGAIN`（某些状态下的同步调用者），或阻塞直到正在进行中的操作完成。

### 故障模式

调用者必须预期这些竞态返回值，不要将它们视为错误。

## 休眠模式处理

### 关键知识点

在 `thaw()` 回调中仅基于 `pm_hibernate_is_recovering()` 跳过设备恢复会破坏 hybrid sleep（混合睡眠）模式，导致系统看似唤醒但设备功能异常。

### hibernation 的三种 `thaw()` 场景

| 场景 | `pm_transition` 值 | `pm_hibernate_is_recovering()` | `pm_hibernation_mode_is_suspend()` | 是否需要完全恢复设备 |
|------|-------------------|-------------------------------|-----------------------------------|-------------------|
| 镜像创建成功（正常路径） | `PMSG_THAW` | false | false | 否 |
| 镜像创建失败（错误恢复） | `PMSG_RECOVER` | **true** | false | **是** |
| Hybrid sleep 唤醒 | 触发了 suspend 而非关机 | false | **true** | **是** |

`pm_hibernate_is_recovering()` 在 `pm_transition.event == PM_EVENT_RECOVER` 时返回 true，表示系统正在创建 hibernation 镜像但**过程失败**，设备需要恢复到活跃状态。它**不**表示从保存的镜像正常恢复。

### 正确的 `thaw()` 回调模式

```c
// 错误：仅用 pm_hibernate_is_recovering() 检查会破坏 hybrid sleep
if (!pm_hibernate_is_recovering())
    return 0;

// 正确：仅当镜像成功创建且系统不在 hybrid sleep 模式时才跳过恢复
if (!pm_hibernate_is_recovering() && !pm_hibernation_mode_is_suspend())
    return 0;
```

参考实现：`amdgpu_pmops_thaw()` 在 `drivers/gpu/drm/amd/amdgpu/amdgpu_drv.c`。

### 故障模式

在 `thaw()` 回调中仅使用 `pm_hibernate_is_recovering()` 来决定跳过恢复，但未同时检查 `pm_hibernation_mode_is_suspend()`。

## PM 回调条件编译

### 不变式

在 `dev_pm_ops` 中无条件分配 PM 回调会产生死代码——当 `CONFIG_PM_SLEEP=n` 或 `CONFIG_PM=n` 时，回调函数及其所有引用被链接到内核中，但永远不会执行。

### 正确的包装宏

| 宏 | 在以下条件展开为非 NULL | 用途 |
|----|----------------------|------|
| `pm_sleep_ptr()` | `CONFIG_PM_SLEEP=y` | 睡眠回调（suspend/resume/freeze/thaw/poweroff/restore） |
| `pm_ptr()` | `CONFIG_PM=y` | 运行时 PM 回调和 `dev_pm_ops` 结构体指针 |

```c
// 错误：CONFIG_PM_SLEEP=n 时产生死代码
static const struct dev_pm_ops foo_pm_ops = {
    .thaw = foo_thaw,
};
.driver.pm = &foo_pm_ops,

// 正确：用 pm_sleep_ptr/pm_ptr 包装
static const struct dev_pm_ops foo_pm_ops = {
    .thaw = pm_sleep_ptr(foo_thaw),
    .runtime_suspend = foo_runtime_suspend,
};
.driver.pm = pm_ptr(&foo_pm_ops),
```

### 故障模式

在 PM 回调中添加 PM sleep API 后，未使用 `pm_sleep_ptr()` 包装相应回调，也未使用 `pm_ptr()` 包装结构体指针。

## 异步 vs 同步运行时 PM Put

### 关键知识点

在需要同步挂起的地方使用异步 `pm_runtime_put()` 会导致竞态条件：挂起的异步空闲/挂起工作可能被 `pm_runtime_disable()`（在设备移除时通过 `__pm_runtime_barrier()` 调用）取消，使硬件处于不正确的电源状态。

```c
// 错误：异步 put 可能在移除路径中被 pm_runtime_disable() 取消
pm_runtime_put(&dev->auxdev.dev);
device_del(&dev->auxdev.dev);

// 正确：同步 put 确保空闲/挂起在删除前完成
pm_runtime_put_sync(&dev->auxdev.dev);
device_del(&dev->auxdev.dev);
```

### 使用 `pm_runtime_put_sync()` 的场景

- 设备移除紧随其后（`device_del()`、`device_unregister()`、`auxiliary_device_delete()`）
- `pm_runtime_disable()` 紧随其后
- 硬件顺序约束要求设备在下一操作前处于空闲/挂起状态

### 故障模式

`pm_runtime_put()` 后跟 `device_del()` 或 `device_unregister()` 应使用 `pm_runtime_put_sync()` 替代。

## IRQ 处理函数中的运行时 PM

### 不变式

在中断处理函数中使用 `pm_runtime_get_noresume()` 允许在设备挂起时访问硬件，导致无效的寄存器读取（通常从断电硬件返回 0xffffffff）。对于共享 IRQ，这会导致当该中断属于同一线路上的另一个设备时产生伪中断处理。

### 正确做法

在中断处理函数中应使用 `pm_runtime_get_if_active()`，它在检查设备为 `RPM_ACTIVE` 时才会原子性地增加使用计数器。

| 函数 | 行为 | 适用场景 |
|------|------|---------|
| `pm_runtime_get_noresume()` | 仅递增使用计数器，不检查运行时状态 | **不适用于 IRQ 处理函数** |
| `pm_runtime_get_if_active()` | 仅在设备为 `RPM_ACTIVE` 时递增计数器 | IRQ 处理函数中正确做法 |

```c
// 正确：在硬件访问前检查设备是否活跃
int ret = pm_runtime_get_if_active(dev);
if (ret <= 0)
    return IRQ_NONE;  // 设备不活跃，不是我们的中断

status = readl(base + STATUS_REG);
if (status == ~0u) {
    pm_runtime_put(dev);
    return IRQ_NONE;
}

// ... 处理中断 ...
pm_runtime_put(dev);
return IRQ_HANDLED;
```

### 共享 IRQ 的特殊要求

使用共享 IRQ（`IRQF_SHARED`）的设备，其运行时挂起回调必须在断电硬件前调用 `synchronize_irq()`，确保没有 IRQ 处理函数正在执行。

### 故障模式

- IRQ 处理函数访问硬件寄存器前使用 `pm_runtime_get_noresume()` 而非 `pm_runtime_get_if_active()`
- 使用 `IRQF_SHARED` 的驱动在运行时挂起回调中未在断电前调用 `synchronize_irq()`

## 快速检查清单

- **`thaw()` 中的 hybrid sleep**：如果使用 `pm_hibernate_is_recovering()` 条件性跳过恢复，验证是否也检查了 `pm_hibernation_mode_is_suspend()`
- **`pm_sleep_ptr()` 包装器**：当 PM sleep API 添加到回调时，验证 `dev_pm_ops` 结构体对这些回调使用了 `pm_sleep_ptr()`，对结构体指针使用了 `pm_ptr()`
- **移除前的同步**：`pm_runtime_put()` 后跟 `device_del()` 或 `device_unregister()` 应使用 `pm_runtime_put_sync()` 替代
- **IRQ 处理函数的 PM 访问**：IRQ 处理函数应使用 `pm_runtime_get_if_active()`，而非 `pm_runtime_get_noresume()`
- **挂起中的 `synchronize_irq()`**：使用 `IRQF_SHARED` 的驱动必须在运行时挂起回调中调用 `synchronize_irq()`
