# ARM64 架构知识

本文覆盖 ARM64 (AArch64) 架构的不变量（invariants）、内存序规则和常见缺陷模式，内容来自历史经验总结和 ARM 架构参考手册（ARM ARM）。

## 内存标签扩展（MTE）与带标签地址

错误处理 MTE 标签或带标签地址会导致 `KASAN invalid-access` 恐慌、虚假标签检查错误和内存权限损坏。

### 不变规则

- **指针运算**：Top Byte Ignore (TBI) 硬件特性允许 MMU 在地址翻译时忽略 bits [63:56]。但是，**软件侧运算**（例如用位移计算页索引）必须显式去除标签（通过 `untagged_addr()`），防止标签位污染计算结果。
  - **注意**：如果实现了 `FEAT_PAuth`，`TCR_ELx.TBIDn` 选择 TBI 是否同时适用于指令获取和数据访问；否则 TBI 无条件地同时适用于两者。
- **标签初始化屏障**：在标签存储（`STG`/`STZG`）和 PTE 更新之间需要一条 `DSB` 指令，确保显式标签存储在页表遍历器（table walker）的隐式 TTD 读取观察到映射之前完成。
- **共享页标签初始化**：过早地将共享页或特殊页（例如大零页 huge zero folio）标记为 MTE 标签，会导致用户在标签被最终清除之前映射该页。标签清除必须在页面可被其他观察者访问之前完成并可见。

### 检查要点

**报告为缺陷：**
- 直接使用虚拟地址进行位移或掩码操作查找页表项，而未调用 `untagged_addr()`。
- 更新 MTE 使能页的 PTE 时，在写入标签后缺少前置 `DSB` 以确保页表遍历器可见。

## 系统寄存器与上下文同步

对架构配置系统寄存器的更新（例如 `GCR_EL1`、`SCTLR_EL1`、`TCR_EL1`）如果没有显式的上下文同步事件（Context Synchronization Event, CSE），不保证对后续指令可见。

缺少同步会导致不可预测行为：CPU 会在几个周期内使用过时的配置运行，破坏内存安全语义或导致意外的陷阱。

### 不变规则

- **上下文同步事件（CSE）**：CSE 确保先前的状态变更已生效。构成 CSE 的事件包括：
  - 执行 `isb` 指令。
  - 异常进入或返回（受 `SCTLR_ELx.{EIS, EOS}` 位和 `FEAT_ExS` 影响）。
- **立即同步**：每次写入控制平面系统寄存器后，必须紧跟 `isb()` 作为**下一条指令**。该屏障必须出现在随后的读回、比较、条件分支、返回或进一步的系统寄存器访问之前，而不仅仅是"在函数的某个地方"。在写入和 `isb()` 之间放置了**任何**指令的代码都是有缺陷的，即使最终执行了 `isb()`，因为中间的指令观察的是架构上未定义的流水线状态。
- **GIC 同步**：
  - 对大多数 `ICC_*_EL1` 寄存器的写入需要 CSE 才能对后续指令可见。值得注意的例外：对 `ICC_PMR_EL1` 的写入和对 `ICC_IAR{0,1}_EL1` / `ICC_NMIAR1_EL1` 的读取（当 `PSTATE.{I,F} == {0,0}` 时）是自我同步的。
  - 对特定内存映射 GIC 寄存器的写入需要轮询 RWP 位。`GICD_CTLR.RWP` 跟踪组使能禁用的 transitions（1→0）、`GICD_CTLR` ARE/DS 字段写入和 `GICD_ICENABLER<n>`。`GICR_CTLR.RWP` 跟踪 `GICR_ICENABLER0`、`GICR_CTLR.EnableLPIs`（1→0）和 DPG 写入。优先级、路由和使能设置写入不被任一个 RWP 位跟踪。
- **自我同步的寄存器与字段（不需要 ISB）**：上述通用规则有架构定义的例外——某些系统寄存器的效果保证对程序序中的后续指令可见，**无需** CSE：
  - **SVE/SME 有效向量长度字段**（`ZCR_ELx.LEN` 和 `SMCR_ELx.LEN`）：写入对后续的 SVE/SME 指令生效，中间不需要 `isb()`。ARM ARM 在字段描述中以"间接读取 `<REG>.<FIELD>` 似乎相对于同一寄存器的直接写入按程序序发生，无需显式同步"的措辞标记。
  - **`FPMR`**（FP8 模式寄存器，`SYS_FPMR`）：在**寄存器**粒度上自我同步——"对此寄存器的直接或间接读取相对于对此寄存器的直接写入按程序序发生，无需显式同步"（ARM ARM C5.2.9）。`FPMR` 写入和随后的 FP8 指令之间不需要 `isb()`。
  - **`ICC_PMR_EL1`**（GIC 优先级掩码）：通过 GIC 架构的独立保证实现自我同步，而非上述系统寄存器措辞。写入后，没有低于新优先级的中断被接收，不需要 `isb()` 或异常边界。这个免 `isb()` 保证仅适用于**掩码**方向（写入 `ICC_PMR_EL1` 阻止较低优先级的中断，如 `local_irq_disable()` 的情况）。**解掩码**方向（放宽掩码以重新允许它们，如 `local_irq_enable()`）确实需要屏障——`pmr_sync()`，一个根据 `ICC_CTLR_EL1.PMHE` 门控的 `dsb`（当 `PMHE == 0` 时在启动时修补为 nop，没有 `CONFIG_ARM64_PSEUDO_NMI` 时完全编译掉），绝不是 `isb()`。
  - 在自我同步字段（如 `ZCR_ELx.LEN`）或寄存器（如 `FPMR`）写入后标记缺少 `isb()` 是误报。

### 检查要点

**报告为缺陷：**
- 写入控制系统寄存器后没有立即跟上 `isb()`。包括将屏障延迟在读回验证、条件分支或任何其他指令之后的模式。缺陷示例：
  ```c
  write_sysreg_s(val, SYS_HFGRTR_EL2);
  if (read_sysreg_s(SYS_HFGRTR_EL2) != val)   /* 观察到流水线状态 */
      return -EIO;
  isb();                                       /* 为时已晚——读回已执行 */
  ```
  `isb()` 存在，但读回已经针对架构未定义的流水线状态执行了。正确的顺序是 `write → isb() → read-back`。
- 对 `ICC_*_EL1` 寄存器（不包括 `ICC_PMR_EL1`）的写入没有 `isb()`。
- 对需要跟踪的内存映射 GIC 寄存器的写入没有轮询适当的 `GICD_CTLR.RWP` 或 `GICR_CTLR.RWP`。

## 自动生成定义与语义漂移

硬件定义日益从手写的 C 宏迁移到自动生成的基础设施（例如被 `gen-sysreg.awk` 消费的 `.sysreg` 文件）。生成器的契约是反映**全局架构真值**，而不是旧 C 宏中嵌入的任何软件上下文。因此，一个声明性变更可以静默地改变自动生成的聚合掩码的**值**，而**名称**保持不变：编译器保持沉默，标准 CI 也保持沉默，因为构建只持有新的快照。发现这种问题本质上是代码审查的责任。

### 典型示例

`<REG>_RES1` 仅从该寄存器 `.sysreg` 块中的字面 `Res1 N` 行生成；它没有特性的概念，当块没有声明 `Res1` 位时默认为 `UL(0)`。所以一个 `.sysreg` 编辑将位在 `Res1 N` 和 `Field N`（或 `Res0`）之间重新分类——添加一个新架构化的 RES1 位，或将现有的 RES1 位变成可写字段——会静默地改变 `<REG>_RES1` 的**值**，而其**名称**保持不变。`SCTLR_EL2_RES1` 是活的消费者：今天它展开为 `UL(0)` 并被 OR 进 EL2 SCTLR 初始化值 `INIT_SCTLR_EL2_MMU_ON` / `INIT_SCTLR_EL2_MMU_OFF`（`arch/arm64/include/asm/sysreg.h`）。如果未来的 `.sysreg` 更改在 `SCTLR_EL2` 块中添加或删除一个 `Res1` 行，这些初始化值将变化，而消费宏无需任何编辑，也没有编译器或 CI 信号。

"RES1 仅在特性不存在时成立"（例如 `SCTLR_ELx.{EIS, EOS}` 在未实现 `FEAT_ExS` 时是 RES1）存在于 KVM 的运行时特性映射中，在 `arch/arm64/kvm/config.c` 中标记为 `AS_RES1`，而不是在 `<REG>_RES1` 中。

### 检查要点

**报告为张力/开放性问题：**
- 一个 `.sysreg` / 声明性变更重新生成了一个被 C 初始化代码消费的聚合掩码，但没有确认消费者对掩码值的变化具有鲁棒性。

## TLB 失效与 Break-Before-Make (BBM)

不遵循正确的失效和同步序列会导致流水线不一致、陈旧的 TLB 使用和 TLB 冲突异常。

### TLB 维护观察者规则

TLB 维护指令（`TLBI`）的完成**只能**由执行该 `TLBI` 的**同一个**处理单元（Processing Element, PE）执行的 `DSB` 来保证。

- **全局可见性**：广播的 `TLBI`（例如 `TLBI VAE1IS`）只有在发起 PE 执行 `DSB ISH` 后才保证对所有其他 PE 完成。
- **远程 DSB 无效**：CPU B 不能用它自己的 `DSB` 来强制 CPU A 广播的 `TLBI` 完成。
- **本地同步**：`isb` 指令不是广播的。每个观察者 PE 必须在发起 PE 的 `DSB` 完成之后，独立地执行它自己的 `isb()`（或经历 CSE），才能确保失效对本地预取路径可见。

### Break-Before-Make (BBM) 要求

当更新一个活动的转换表项（跨多个线程共享时），必须遵循 BBM 序列以防止 TLB 冲突。

**严格需要 BBM 的情况：**
- **改变块或表的大小**：`FEAT_BBML1/2` 放宽了对显式失效中间描述符的要求，但 TLB 维护仍然是必需的。
- **创建与现有非全局条目重叠的全局条目**。
- **改变输出地址（Output Address, OA）**：如果新 OA 处的内存内容与先前 OA 处的内容不匹配，架构严格要求 BBM。
- **改变内存属性**（类型或可缓存性）。

**BBM 序列：**
1. 用无效条目替换旧条目。
2. 执行 `DSB`（确保无效条目全局可见）。
3. 失效相关 TLB 条目（广播 `TLBI`）。
4. 执行另一个 `DSB`（确保失效完成）。
5. 写入新的、更新后的转换表项。
6. 执行最终的 `DSB`。

### 检查要点

**报告为缺陷：**
- 执行 `TLBI` 后没有同时跟随后续的 `DSB` 和 `isb()`（对于可执行映射或需要本地同步的情况）。
- 在模式进入路径中 TLBI 后缺少 `isb()`（例如 `enter_vhe()`、nVHE `__tlb_switch_to_guest()`、`__primary_switch()`）；没有它，TLBI 不会同步到新的执行上下文。
- 更新活动页表项（改变 OA 到不匹配的地址或属性）时没有中间的失效（跳过了 "Break" 步骤）。
- 在辅助 CPU 可能不支持 `FEAT_BBML2` 的系统上更改内核块/页映射，而没有基于 CPU 特性 caps 门控或回退到完整 BBM。

## 指令与数据一致性（PoC 与 PoU）

架构本身不能保证指令缓存和内存之间的一致性。软件必须使用统一点（Point of Unification, PoU）或一致性点（Point of Coherency, PoC）手动管理。

- **自修改代码（PoU）**：当以数据方式写入新指令时（例如 JIT），软件必须：
  1. 将数据缓存清理到 PoU（`DC CVAU`）。
  2. 执行 `DSB ISH`。
  3. 将指令缓存失效到 PoU（`IC IVAU`）。
  4. 执行 `DSB ISH`。
  5. 确保在所有观察 CPU 上发生 `isb()`（例如通过 IPI）。
- **指令修补（CMODX）**：指令的并发修改和执行仅对架构列举的 CMODX 集合安全：`B`、`B.cond`、`BL`、`BRK`、`CB<cc>`、`CBB<cc>`、`CBH<cc>`、`CBNZ`、`CBZ`、`HVC`、`ISB`、`NOP`、`SMC`、`SVC`、`TBNZ`、`TBZ`、`TRCIT` 和 `UDF`。对于所有其他指令，所有观察 CPU 在**执行前**必须有一个显式的 `isb()` 或 CSE。
- **外部代理（PoC）**：与非一致性 DMA 控制器通信或管理不匹配的内存属性时，需要清理/失效到一致性点（PoC）（例如 `DC CVAC`）。

### 检查要点

**报告为缺陷：**
- 修改指令（例如 jump label 修补）时没有确保所有执行修改后代码的 CPU 上发生 `isb()` 或 CSE。

## 无锁页表遍历

无锁遍历器（如 GUP 或快速路径 page fault）必须仔细管理编译器序，以避免观察到不一致的页表状态。

- **原子性和序**：在无锁遍历中，从共享页表加载描述符时，软件必须使用 `READ_ONCE()`，以防止编译器拆分加载或将其相对于后续逻辑重排序。
- **折叠级处理**：当某些页表级被静态折叠时（`PGTABLE_LEVELS ≤ 2`），无锁遍历必须考虑折叠的拓扑结构。在折叠级上应用标准的多级 `READ_ONCE()` 模式将观察到过时或不正确的状态。

### 检查要点

**报告为缺陷：**
- 在无锁遍历中对共享 PTE/PMD/PUD/PGD 指针解引用时没有使用 `READ_ONCE()`。
- 假设所有页表级别都是活动的而未检查折叠级条件的无锁遍历逻辑。

## 异常处理与栈管理

操作栈指针（`SP`）在架构上是有风险的，因为可能破坏异常返回状态（`ELR_ELx`、`SPSR_ELx`）。

- **DAIF 掩码**：在栈转换或切换期间（例如切换到 Shadow Call Stack），必须掩蔽异步异常（IRQ、FIQ、SError）。当 `SP` 正在移动或状态不同步时发生异常将导致致命的递归错误。
- **栈对齐**：`SCTLR_ELx.SA` 强制执行 16 字节 SP 对齐以访问 ELx 处的内存；`SCTLR_EL1.SA0` 控制在 EL0 处的相同检查。检查的是通过 SP 进行的内存访问，而非 SP 的修改。

### 检查要点

**报告为缺陷：**
- 操作 `SP` 或切换栈时没有掩蔽 `DAIF`。

## SVE、SME 与 FPSIMD 寄存器状态

向量长度变更和信号返回路径有遗留陈旧寄存器状态或执行不正确状态合并的历史。

- **VL 变更状态失效**：当任务的 SVE 或 SME 向量长度被改变时，任何从旧 VL 派生的上下文（缓冲区、寄存器视图、ptrace 负载）必须在执行继续之前被失效或重建。不完整的失效会在新的向量宽度上下文中复活陈旧数据。
- **流模式 SVE 负载**：进入流式 SVE 模式时，ptrace/信号接口需要一个显式的 SVE 负载用于流式模式状态；继承先前非流式状态在架构上是不正确的。
- **FPSIMD/SVE 状态在信号返回时的合并**：从信号处理器返回时，FPSIMD 和 SVE 状态必须在单个一致步骤中合并。部分或不正确顺序的合并会静默地破坏 Z 寄存器上半部分。

### 检查要点

**报告为缺陷：**
- VL 变更路径没有为新长度失效或重建 SVE/SME 寄存器上下文。
- 信号返回路径以不正确或多个非原子步骤合并 FPSIMD 和 SVE 寄存器状态。

## 快速检查清单

- **需要固定寄存器的系统指令**：要求特定寄存器的系统指令的内联汇编（例如 GIC CDEOI 要求 `XZR` / register 31）必须在指令字符串中硬编码精确的寄存器。仅依赖编译器约束（如 `r`）可能导致编码错误的指令，如果编译器选择了一个通用寄存器，会触发 `CONSTRAINED UNPREDICTABLE` 行为。
- **CONSTRAINED UNPREDICTABLE**：由无效编码或寄存器重叠触发。硬件可能执行为 `NOP`、视为 `UNDEFINED`，或生成 Alignment/MMU 错误。结果是 **UNKNOWN** 状态，不能依赖。
- **TLBI Range 操作数**：基于范围的失效（例如 `TLBI RVAE1IS`）需要正确的 `SCALE` 和 `NUM` 编码。如果 `TG` 与当前 granule 不匹配，TLBI 是 CONSTRAINED UNPREDICTABLE 的——可能包括没有失效。
- **PTE 屏障批处理**：跨多个内核映射 PTE 更新批处理 DSB/ISB 仅在中批处理不可被中断的上下文中是正确的。在中可中断的上下文中，批处理窗口被破坏，必须在被中断的路径观察到映射之前发出显式屏障。
