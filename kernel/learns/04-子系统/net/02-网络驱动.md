# 网络驱动：统计信息与同步

## 使用 u64_stats_sync 的每设备统计

驱动 pre-NAPI / 每队列 / 每-CPU 的统计数据使用 64 位计数器，这些计数器在 32 位架构上可能撕裂——读取者观察到一次更新的低半部分与下一次更新的高半部分组合在一起。`include/linux/u64_stats_sync.h` 中的 `u64_stats_sync` 辅助函数在 32 位使用 seqcount 来消除竞争，在 64 位编译为空操作。

计数器声明为 `u64_stats_t` 或纯 u64（每个每-CPU 容器配对一个 `struct u64_stats_sync`，通过 `u64_stats_init()` 初始化）。写入者将更新包装在 `u64_stats_update_begin()` / `u64_stats_update_end()` 中；读取者在 `u64_stats_fetch_begin()` / `u64_stats_fetch_retry()` 周围重试。

```c
/* 写入者（每-CPU、BH 禁用或串行化） */
u64_stats_update_begin(&stats->syncp);
u64_stats_add(&stats->bytes, len);
u64_stats_inc(&stats->packets);
u64_stats_update_end(&stats->syncp);

/* 读取者（例如 ndo_get_stats64） */
do {
    start = u64_stats_fetch_begin(&stats->syncp);
    bytes = u64_stats_read(&stats->bytes);
    pkts  = u64_stats_read(&stats->packets);
} while (u64_stats_fetch_retry(&stats->syncp, start));
```

### 容易出错的关键约束

- **写入者必须互斥**：对于给定的 `syncp`，每个 CPU 从不可抢占的上下文（NAPI、softirq）写入自己的副本，每-CPU 或每-NAPI 的统计满足此约束。
- **写入者必须在抢占禁用状态下运行**：每-CPU + BH 禁用（或硬 IRQ）上下文已提供此保证。如果写入者可能被读取者抢占，在 32 位系统上读取者将永远自旋。
- **使用 `_irqsave` 变体**：当 IRQ 处理程序也可能写入或读取同一个 `syncp` 时。`u64_stats_update_begin_irqsave()` / `u64_stats_update_end_irqrestore()` 在 64 位对中断无操作，但在 32 位禁用中断。
- **读取者可以睡眠或被抢占**：它们执行纯读取操作。
- **读取者重试循环必须幂等**：常见错误是使用 `+=`，例如 `retval->rx_bytes += u64_stats_read(&stats->bytes)`，这会在重试时多次累加字节计数器。

## Ethtool 驱动统计与标准统计

向 `ethtool -S` 添加与标准内核 uAPI 已有计数器重复的统计信息会导致混乱，产生巨大的 ethtool -S 列表，并增加维护负担。

- **存在标准 uAPI 的统计信息不得在 `ethtool -S` 中重复**。`ethtool -S` 接口（`get_ethtool_stats()` / `get_sset_count()` / `get_strings()`）仅用于驱动私有统计信息——即特定于硬件或驱动且没有标准表示的计数器。
- 存在标准 uAPI 的类别包括：
  - 网络设备统计（`struct rtnl_link_stats64`，通过 `ip -s link show` 访问）
  - 每队列统计（通过 netlink，使用 `struct netdev_queue_stats_rx`、`struct netdev_queue_stats_tx`）
  - Page pool 统计（通过 netlink，可通过 `ynl` 工具访问）
  - Ethtool 统计（`struct ethtool_ops` 中有专用回调）
  - 通过标准化 netlink 属性暴露的其他计数器
- 当驱动想要暴露适合现有标准类别的统计信息时，应实现相应的标准接口，而不是添加私有 ethtool 字符串。
- `Documentation/networking/statistics.rst` 记录了统计信息层次结构以及使用哪些接口。

**应报告为 bug 的情况**：驱动补丁向 `ethtool -S` 添加存在标准 uAPI 的计数器。在报告前必须找到至少一个此类统计信息。早于标准 uAPI 的已存在 `ethtool -S` 统计在新补丁中不是 bug（迁移它们是单独的清理工作）。

## 使用标志和原子变量的特设同步

使用原子变量、位标志或布尔字段替代真实锁或 RCU 的驱动代码几乎总是包含竞争条件。这些自制的方案不提供实际的同步保证，对 lockdep 不可见，因此它们引入的 bug 逃过标准内核调试工具的检测。

### 常见的错误模式

**原子/标志作为门卫**：读取原子值或标志来决定是否继续，然后不持锁操作共享数据。标志的值在读取后可能立即变化，因此"保护"是虚幻的。

```c
// 错误：intr_sem 可能在读取后立即变化
if (atomic_read(&priv->intr_sem) != 0)
    return;
// ... 在没有持锁的情况下操作共享状态
```

**位标志作为读/写者协议**：使用 `set_bit()` / `test_bit()` / `clear_bit()` 协调读取者和拆除路径之间的访问。多个并发读取者可以进入，一个读取者清除位而另一个仍在操作中，拆除路径释放正在被剩余读取者访问的内存。

```c
// 错误：并发读取者在位上竞争
set_bit(STATE_READ_STATS, &priv->state);
if (!test_bit(STATE_OPEN, &priv->state)) {
    clear_bit(STATE_READ_STATS, &priv->state);
    return;
}
// ... 读取关闭路径可能释放的共享数据
clear_bit(STATE_READ_STATS, &priv->state);
```

**标志上的重试/轮询循环**：在标志上自旋等待另一个上下文清除它，重新实现自旋锁但没有公平性、死锁检测或内存排序保证。

**Trylock 循环以避免死锁**：在循环或重复调用中使用 `mutex_trylock()` 或 `spin_trylock()` 来避免锁顺序问题，表明锁设计本身是错误的。Trylock 仅在狭窄情况下可接受——例如，一个工作项调用 `mutex_trylock()` 并在失败时重新调度自身（通过 `schedule_work()` / `schedule_delayed_work()`）以便稍后再次运行。手写的 trylock 重试循环，或结合"完全跳过工作"回退的 trylock，几乎总是 bug。

### 正确的替代方案

| 访问模式 | 正确方案 |
|---------|---------|
| 读取者重的路径（例如 `ndo_get_stats64`） | RCU |
| 可睡眠的互斥 | `mutex` |
| 原子上下文中的互斥 | `spinlock_t` |
| 防止定时器或工作的并发执行 | `del_timer_sync()` / `cancel_work_sync()` |

**应报告为 bug 的情况**：任何标志、原子变量或位操作用于守卫代码段而非表达状态的模式——即标志在代码区域入口设置、退出清除以防止并发访问，而不是使用适当的锁或 RCU。

## Invariants（不变式）

- `u64_stats_sync` 写入者必须每 `syncp` 互斥，并在抢占禁用状态下运行
- IRQ 上下文触及相同 `syncp` 时使用 `_irqsave` 变体
- 存在标准 uAPI 的统计信息不得在 `ethtool -S` 中重复
- 标志/原子/位不能替代真实的锁机制

## Failure Modes（故障模式）

| 违规操作 | 结果 |
|---------|------|
| 32 位上不正确的 `u64_stats_sync` 使用 | 撕裂的 64 位读取、损坏的计数器 |
| 在 `ethtool -S` 中重复标准统计 | 维护负担、用户混淆 |
| 使用标志/原子代替锁 | 竞争条件、数据损坏、lockdep 无法检测 |
| 读取者重试循环使用 `+=` | 重试时计数器被多次累加 |

## Quick Checks（快速检查清单）

- [ ] `u64_stats_sync` 写入者是否互斥并禁用抢占？
- [ ] 如果 IRQ 也写入，是否使用了 `_irqsave` 变体？
- [ ] 新的 `ethtool -S` 计数器是否覆盖了已存在标准 uAPI 的值？
- [ ] 是否存在标志/原子入口-退出模式替代真实锁的情况？
- [ ] 读取者重试循环是否幂等（不使用 `+=`）？
