# 蓝牙子系统

## 广播实例状态跟踪（Advertisement Instance State Tracking）

使用不正确的状态指示器来确定广播实例是否处于活动状态，会导致广播在不应该时被错误启用，或在暂停/恢复循环后无法重新启用，导致静默功能故障。

蓝牙 HCI 支持多个广播实例（set）。实例 0x00 具有与其他实例不同的特殊处理：

### 实例 0x00（Legacy Instance）的特殊规则

- **不**在 `adv_instances` 链表中跟踪；`net/bluetooth/hci_core.c` 中的 `hci_add_adv_instance()` 拒绝 `instance < 1`
- `hdev->cur_adv_instance == 0` **不**意味着实例 0x00 是活动的；它只指示哪个实例是"当前的"（选中的），而不是哪个是启用的
- 全局的 `HCI_LE_ADV` 标志跟踪是否存在**任何**广播是活动的，而不是特指实例 0x00
- 实例 0x00 的启用状态由 `HCI_LE_ADV_0` 设备标志跟踪

### 常见错误

- 使用 `!hdev->cur_adv_instance` 作为"实例 0x00 是活动的"的代理
- 使用 `hci_dev_test_flag(hdev, HCI_LE_ADV)` 来推断实例 0x00 的状态

查询实例 0x00 启用状态的唯一正确方式是 `hci_dev_test_flag(hdev, HCI_LE_ADV_0)`。该标志在 `net/bluetooth/hci_event.c` 的 `hci_cc_le_set_ext_adv_enable()` 中，当 `set->handle == 0` 且没有 `adv_info` 存在时被设置，并在相应的禁用路径中被清除。

## MGMT 待处理命令生命周期

未能正确管理 `struct mgmt_pending_cmd` 的所有权会导致内存泄漏（命令从未释放）或 use-after-free/double-free（命令被释放两次或在释放后访问）。所有权模型很微妙，因为它基于使用的验证函数而改变。

`mgmt_pending_valid()`（在 `net/bluetooth/mgmt_util.c` 中）原子地检查待处理命令是否仍在待处理列表中，并将其从列表中移除。成功调用 `mgmt_pending_valid()` 后，完成回调**拥有**命令的内存，并且**必须**在所有退出路径上通过 `mgmt_pending_free()` 释放它。

### 关键规则

- `mgmt_pending_valid()` 成功后，在**每个**路径（错误返回、成功返回、提前返回）上都调用 `mgmt_pending_free(cmd)`
- 永远不要在 `mgmt_pending_valid()` 后调用 `mgmt_pending_remove()`——`mgmt_pending_remove()` 调用 `list_del()` 然后 `mgmt_pending_free()`，因此在 `mgmt_pending_valid()` 后使用会导致双重 `list_del` 和 double free
- 如果 `mgmt_pending_valid()` 返回 false 或 `err == -ECANCELED`，回调**不**拥有内存，不能释放它

```c
// 错误
void complete(struct hci_dev *hdev, void *data, int err) {
    struct mgmt_pending_cmd *cmd = data;

    if (err == -ECANCELED || !mgmt_pending_valid(hdev, cmd))
        return;

    if (err) {
        mgmt_cmd_status(...);
        return;  // BUG：cmd 未释放，内存泄漏
    }

    mgmt_pending_remove(cmd);  // BUG：双重 list_del + double free
}
```

```c
// 正确
void complete(struct hci_dev *hdev, void *data, int err) {
    struct mgmt_pending_cmd *cmd = data;

    if (err == -ECANCELED || !mgmt_pending_valid(hdev, cmd))
        return;

    if (err) {
        mgmt_cmd_status(...);
        mgmt_pending_free(cmd);
        return;
    }

    // 成功处理...
    mgmt_pending_free(cmd);
}
```

## 变长 MGMT 命令结构体

将变长 MGMT 命令结构体复制到固定大小的栈变量会导致访问灵活数组成员时发生栈越界。`sizeof()` 应用于带有灵活数组成员的结构体只返回固定字段的大小，不包括变长数据。

一些 MGMT 命令结构体（在 `include/net/bluetooth/mgmt.h` 中）有灵活数组成员：

- `struct mgmt_cp_set_mesh` —— 有 `u8 ad_types[]`
- `struct mgmt_cp_load_irks` —— 有 `struct mgmt_irk_info irks[]`
- `struct mgmt_cp_load_long_term_keys` —— 有 `struct mgmt_ltk_info keys[]`

当完成回调需要处理来自 `cmd->param` 的这些结构体时：

- 使用 `DEFINE_FLEX()` 宏（来自 `include/linux/overflow.h`）在栈上分配空间，为灵活数组留出空间
- 或者直接使用 `cmd->param` 指针而不复制
- 使用 `min(__struct_size(var), len)` 防止读取超出参数缓冲区

```c
// 错误
struct mgmt_cp_set_mesh cp;
memcpy(&cp, cmd->param, sizeof(cp));  // sizeof 排除了 FAM
process(cp.ad_types, len);  // 栈越界
```

```c
// 正确
DEFINE_FLEX(struct mgmt_cp_set_mesh, cp, ad_types, num_ad_types, MAX_SIZE);
memcpy(cp, cmd->param, min(__struct_size(cp), len));
```

## Invariants（不变式）

- 实例 0x00 的启用状态只能通过 `HCI_LE_ADV_0` 标志查询
- `mgmt_pending_valid()` 成功后，必须确保所有退出路径都调用 `mgmt_pending_free()`
- 不要将变长 MGMT 结构体复制到固定大小的栈变量中
- 使用 `DEFINE_FLEX()` 处理带有灵活数组的结构体

## Failure Modes（故障模式）

| 违规操作 | 结果 |
|---------|------|
| 使用 `cur_adv_instance` 判断 0x00 活动状态 | 静默功能故障，广播在错误时启用或未启用 |
| `mgmt_pending_valid()` 后缺少 `mgmt_pending_free()` | 内存泄漏 |
| `mgmt_pending_valid()` 后调用 `mgmt_pending_remove()` | 双重 list_del + double free |
| 将变长结构体复制到固定栈变量 | 栈越界访问 |

## Quick Checks（快速检查清单）

- [ ] 广播实例 0x00 的状态是否使用了 `HCI_LE_ADV_0` 标志？
- [ ] 是否使用了 `!hdev->cur_adv_instance` 或 `HCI_LE_ADV` 来推断 0x00 状态？（这些是错误的）
- [ ] `mgmt_pending_valid()` 成功后，**所有**退出路径上是否都调用了 `mgmt_pending_free()`？
- [ ] 是否在 `mgmt_pending_valid()` 后调用了 `mgmt_pending_remove()`？（这是错误的）
- [ ] 带有灵活数组成员的 MGMT 结构体是否被复制到了固定大小的栈变量？
