# 网络协议核心：SKB、Socket 与数据包流程

## SKB 缓冲区操作

`skb_put()`、`skb_push()` 和 `skb_pull()` 修改 socket buffer 的数据边界。如果传入未受信任或未经检查的长度参数，会导致内核 panic（拒绝服务）。边界检查在内存损坏之前触发，因此结果是崩溃而不是静默溢出，但这仍然是一个 bug。

- **`skb_put(skb, len)`**：扩展尾部。当 `skb->tail > skb->end` 时，通过 `skb_over_panic()` 触发 panic。
- **`skb_push(skb, len)`**：向头部前置数据。当 `skb->data < skb->head` 时，通过 `skb_under_panic()` 触发 panic。
- **`skb_pull(skb, len)`**：从头部消耗数据。如果 `len > skb->len`，返回 NULL。如果 pull 导致 `skb->len` 低于 `skb->data_len`（即线性区域被耗尽），`__skb_pull()` 调用 `BUG()`。

`skb_over_panic()` 和 `skb_under_panic()` 都调用 `skb_panic()`，后者调用 `BUG()`（定义在 `net/core/skbuff.c` 中）。

## SKB 共享与克隆缓冲区

修改共享或克隆的 SKB 会破坏同一缓冲区数据的其他使用者，导致静默数据损坏或在不相关的代码路径中崩溃。

- **`skb_shared(skb)`**：当 `refcount_read(&skb->users) != 1` 时返回 true。
- **`skb_cloned(skb)`**：当数据区域与另一个 SKB 共享时返回 true。

**`skb_unshare(skb, gfp)`**：返回独占副本。如果缓冲区被克隆，通过 `skb_copy()` 复制 SKB 并无条件释放原始 SKB（成功时通过 `consume_skb()`，分配失败时通过 `kfree_skb()`）。如果未被克隆，则原样返回。**始终使用返回的指针**——输入的指针可能已被释放。返回 NULL 表示分配失败且原始 SKB 已被释放。

## 包头线性化（Header Linearization）

数据包头部可能跨越分页片段（paged fragments），在确保字节位于线性区域（`skb->data`）之前不能安全地解引用。对未线性化的头部指针解引用可能导致页错误或从无关内存读取垃圾数据。

**`pskb_may_pull(skb, len)`**：保证线性部分至少有 `len` 字节连续，必要时从片段中拉取。

```c
if (!pskb_may_pull(skb, sizeof(struct iphdr)))
    return -EINVAL;

iph = ip_hdr(skb);  /* 安全：头部现在位于线性区域 */
```

## Socket 加锁与 Socket 释放

混淆 `release_sock()` 和 `sock_release()` 会导致 use-after-free（调用了错误的函数）或死锁（省略了解锁）。

- **`release_sock(sk)`**：释放通过 `lock_sock()` 获取的 socket 锁。处理 backlog 队列并唤醒等待者。socket 仍然存活。
- **`sock_release(sock)`**：关闭并销毁 `struct socket`，通过 `__sock_release()` 释放协议栈和关联的 inode。

内核中没有名为 `socket_release()` 的函数。

调用 `release_sock()` 后，socket 仍然有效但已解锁——其他线程现在可以操作它。调用 `sock_release()` 后，socket 结构已被释放，不得再访问。

## Socket 引用计数

在未持有引用的情况下丢弃 socket 引用，或存储 socket 指针时未获取引用，会导致 use-after-free 崩溃。

Socket 生命周期通过 `sk_refcnt` 管理：

- **`sock_hold(sk)`**：通过 `refcount_inc()` 递增 `sk->sk_refcnt`。
- **`sock_put(sk)`**：递减 `sk->sk_refcnt`，当降至零时调用 `sk_free()`。

Socket 可以比其文件描述符存活得更久。在文件描述符生命周期之外持有 socket 指针的代码必须通过 `sock_hold()` 持有引用，并通过 `sock_put()` 释放。

## Netfilter Hook 所有权

将 SKB 传递给 `NF_HOOK()` 后访问它是 use-after-free。Hook 裁决决定 SKB 的命运：

| 裁决结果 | 含义 | SKB 所有权 |
|---------|------|-----------|
| `NF_ACCEPT` | 继续处理 | `okfn()` 使用 SKB 被调用 |
| `NF_DROP` | 拒绝数据包 | Netfilter 通过 `kfree_skb_reason()` 释放 SKB |
| `NF_STOLEN` | Hook 已消费数据包 | Hook 获取所有权 |
| `NF_QUEUE` | 排队到用户空间 | `nf_queue()` 获取所有权 |

在所有情况下，`NF_HOOK()` 或 `NF_HOOK_COND()` 的调用者失去对 SKB 的所有权，调用后不得再访问。裁决分发在 `nf_hook_slow()`（`net/netfilter/core.c`）中实现。

传递给 `NF_HOOK()` 的设备指针（`in`、`out`）在整个 hook 遍历期间必须保持有效。

## 缓冲区移交安全

将 SKB 传递给另一个子系统后访问它是 use-after-free。一旦 SKB 被传递给另一个子系统（排队、入队、交给协议处理器），调用者即失去所有权。接收方可能随时释放它，包括移交函数返回之前。

## 路由的 RCU 保护

在其 RCU 读端临界区之外访问 dst 条目会导致 use-after-free，因为该条目可能在 RCU 宽限期后被释放。

路由表查找（FIB 查找、dst 条目）由 RCU 保护。`ip_route_input_noref()` 执行 RCU 保护的查找，并在 SKB 上存储一个 noref dst。它管理自己的内部 `rcu_read_lock()` / `rcu_read_unlock()`。如果 dst 需要存活超过该内部 RCU 段，调用者必须持有外部的 `rcu_read_lock()` 并通过 `skb_dst_force()` 升级：

```c
rcu_read_lock();
reason = ip_route_input_noref(skb, dst, src, dscp, devin);
if (!reason) {
    skb_dst_force(skb);  /* 升级为引用计数的 dst */
    if (!skb_dst(skb))
        reason = SKB_DROP_REASON_NOT_SPECIFIED;
}
rcu_read_unlock();
```

`skb_dst_set_noref()` 存储一个 RCU 保护的 dst 条目而不获取引用——如果既未持有 `rcu_read_lock()` 也未持有 `rcu_read_lock_bh()`，它会发出警告。如果 dst 需要存活超过 RCU 读端临界区，使用 `skb_dst_force()` 升级为引用计数的引用。`skb_dst_force()` 如果无法保持 dst（已被释放），返回 false。

## 每-CPU 网络统计信息

在每-CPU 网络统计上错误同步会导致 32 位系统上的 torn reads（64 位计数器被读取为来自不同更新的两个半部分），或被 BH 处理抢占时丢失增量。

`include/net/snmp.h` 中的 SNMP 统计宏处理此问题：

- **`SNMP_INC_STATS()` / `SNMP_ADD_STATS()`**：使用 `this_cpu_inc()` / `this_cpu_add()`，适用于单字（`unsigned long`）计数器
- **`SNMP_ADD_STATS64()` / `SNMP_UPD_PO_STATS64()`**：在 32 位系统（`#if BITS_PER_LONG==32`）上将更新包装在 `local_bh_disable()` / `local_bh_enable()` 中，并使用 `u64_stats` seqcounts，因为 64 位更新不是原子的
- 双下划线变体（`__SNMP_ADD_STATS64()`）省略了 `local_bh_disable()` 包装，只能从 BH 禁用或不可能被 BH 抢占的进程上下文中调用

## 数据包类型常量

误解 `skb->pkt_type` 会导致数据包被传递给错误的处理程序或静默丢弃。该字段对接收到的数据包进行分类：

| 常量 | 值 | 含义 |
|------|-----|------|
| `PACKET_HOST` | 0 | 发往本机 |
| `PACKET_BROADCAST` | 1 | 链路层广播 |
| `PACKET_MULTICAST` | 2 | 链路层多播 |
| `PACKET_OTHERHOST` | 3 | 发往其他主机（混杂模式） |
| `PACKET_OUTGOING` | 4 | 任意类型的出站包 |
| `PACKET_LOOPBACK` | 5 | MC/BRD 帧回环 |

这些定义在 `include/uapi/linux/if_packet.h` 中。

## SKB 控制块生命周期

`skb->cb` 字段是一个 48 字节的暂存区域（`char cb[48]` in `include/linux/skbuff.h`），跨网络层共享。每一层（IP、netfilter、qdisc、驱动）都可能覆盖它。在数据包构建期间将数据存入 `skb->cb`，然后在 SKB 析构函数或其他异步回调中读取它，会导致数据损坏、NULL 指针解引用或 panic，因为 cb 内容会被中间层覆盖。

```c
// 错误：cb 可能在析构函数运行前被破坏
struct my_metadata {
    u32 count;
    struct list_head list;
};
#define MY_CB(skb) ((struct my_metadata *)((skb)->cb))

void my_destructor(struct sk_buff *skb) {
    struct my_metadata *meta = MY_CB(skb);  // cb 可能是垃圾数据
    process_list(&meta->list);               // 崩溃或损坏
}
```

需要存活到销毁的安全替代方案：

- **`skb_shinfo(skb)->destructor_arg`**：在整个 SKB 生命周期内稳定，被 `skb_uarg()` 和 `include/linux/skbuff.h` 中的指针标签辅助函数使用
- **独立分配的内存**，从 `destructor_arg` 引用

```c
// 正确：使用 destructor_arg 存储析构函数可访问的数据
void my_init(struct sk_buff *skb, u64 addr) {
    skb_shinfo(skb)->destructor_arg = (void *)(addr | 1UL);  // tagged
}

void my_destructor(struct sk_buff *skb) {
    uintptr_t arg = (uintptr_t)skb_shinfo(skb)->destructor_arg;
    u64 addr = arg & ~1UL;  // 安全：destructor_arg 被保留
    process_addr(addr);
}
```

`skb->cb` 在单层处理内部是安全的（例如 qdisc 入队/出队过程中），数据在 SKB 移动到下一层之前就被消费。

## UAPI 结构体对齐继承

向嵌入了窄对齐 UAPI 结构体的结构体添加对齐要求更宽的字段，会导致未对齐的内存访问。在某些架构上这会触发异常；在另一些架构上它会静默降低性能（热路径头部吞吐量损失高达 50%）而不产生功能故障，使得通过测试发现该 bug 十分困难。

UAPI 结构体仅使用其定义中存在的类型来确定对齐。当一个结构体嵌入另一个时，外部结构体继承内部结构体的对齐，而不是其后添加的任何新字段的对齐。

virtio 网络头部说明了这种模式。`virtio_net_hdr_v1`（`include/uapi/linux/virtio_net.h`）只包含 `__u8` 和 `__virtio16` 字段，对齐为 2 字节。嵌入链 `virtio_net_hdr_v1` -> `virtio_net_hdr_v1_hash` -> `virtio_net_hdr_v1_hash_tunnel` 通过仅在嵌入式结构体之后使用 `__le16` 字段来保持 2 字节对齐。如果在 12 字节的 `virtio_net_hdr_v1` 之后放置 `__le32` 或 `__u32` 字段，它将位于 2 字节对齐的偏移量上，违反该字段自然的 4 字节对齐要求。

扩展嵌入其他结构体的 UAPI 结构体时：

- 检查嵌入式结构体的对齐（`__alignof__`）——新字段不能要求比嵌入结构体提供的更宽的对齐
- 如果需要更宽的值，将其拆分为与继承对齐匹配的较小字段（例如，两个 `__le16` 替代一个 `__le32`）
- 使用 `BUILD_BUG_ON(__alignof__(outer) != __alignof__(inner))` 在相关头部格式之间转换时捕获编译时对齐不匹配。参见 `drivers/net/virtio_net.c` 中的 `xmit_skb()`
- 验证每个新字段的 `offset % sizeof(field_type) == 0`，其中 offset 考虑的是继承的对齐，而不是期望的字段类型

## XFRM/IPsec 数据包协议族确定

在 XFRM 代码中使用错误的协议族来源会导致协议特定的头部访问器（`ip_hdr()`、`ipv6_hdr()`）在错误类型的数据包上被调用，导致不正确的数据包解析、静默数据损坏或崩溃。

`struct xfrm_state`（`include/net/xfrm.h`）包含多个与族相关的字段，在跨族隧道（如 IPv6-over-IPv4）和双栈配置中可能与实际数据包不匹配：

- `x->props.family`：外部/隧道地址族
- `x->inner_mode.family`：主要内部地址族
- `x->inner_mode_iaf.family`：替代内部地址族（双栈）
- `x->outer_mode.family`：外部模式地址族

实际数据包族最可靠的来源是数据包本身，通过 `skb_dst(skb)->ops->family`（`struct dst_ops` in `include/net/dst_ops.h`）。xfrm state 字段指示配置的族，而不是当前正在处理的数据包的族。

```c
// 错误：依赖可能与实际数据包不匹配的 state 字段
switch (x->inner_mode.family) {
case AF_INET:
    iph = ip_hdr(skb);  /* 如果数据包是 IPv6 则崩溃 */
    ...
}

// 正确：查询实际数据包的目的条目
switch (skb_dst(skb)->ops->family) {
case AF_INET:
    iph = ip_hdr(skb);
    ...
}
```

单个文件或子系统内部不一致的族来源表明可能存在 bug。在隧道模式下访问内部数据包属性时，要特别警惕 `x->props.family`。

## Invariants（不变式）

- 在 `skb_put()` / `skb_push()` / `skb_pull()` 之前验证数据包长度
- 解引用协议头部前调用 `pskb_may_pull()`
- 修改 SKB 数据前检查 `skb_shared()` / `skb_cloned()`
- 路由表查找和 dst 访问期间持有 `rcu_read_lock()`
- 对每-CPU 网络计数器使用 BH 安全的统计更新宏
- 将 SKB 交给另一个子系统后不要再访问它
- 不要在 `skb->cb` 中存储析构函数需要的数据
- 对于嵌入其他结构体的 UAPI 结构体，验证新字段不需要比嵌入式结构体提供的更宽的对齐

## Failure Modes（故障模式）

| 违规操作 | 结果 |
|---------|------|
| `skb_put()` 长度超过容量 | 通过 `skb_over_panic()` 导致 panic |
| `skb_push()` 超出头部 | 通过 `skb_under_panic()` 导致 panic |
| 在未调用 `pskb_may_pull()` 时访问协议头部 | 页错误或静默数据损坏 |
| 修改共享/克隆的 SKB 数据 | 在其他代码路径中导致静默数据损坏或崩溃 |
| 混淆 `release_sock()` 和 `sock_release()` | Use-after-free 或死锁 |
| 在 `NF_HOOK()` 后访问 SKB | Use-after-free |
| 在 RCU 读端临界区外访问 dst | Use-after-free |
| 在 `skb->cb` 中存储析构函数数据 | 数据损坏、NULL 解引用或 panic |
