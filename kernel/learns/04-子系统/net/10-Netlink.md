# Netlink / Generic Netlink uAPI 详解

## 概述

规则来源：`Documentation/userspace-api/netlink/` 和 `Documentation/core-api/netlink.rst`。在审查添加或修改 Netlink 族、命令、属性、dump 回调、扩展 ACK 报告或 `Documentation/netlink/specs/` 下 YAML 规范的变更时适用。

一旦 netlink 消息到达用户空间，其布局即成為 uAPI，此后不能再更改。以下大多数规则之所以存在，是因为错误在第一次发布后就是**不可修复的**。

## 新族的设计规则

以下规则仅适用于**新族**。如果族内已存在违反该规则的情况，则在族的未来扩展中应忽略该规则。

- 第一个属性和第一个命令 ID 应为 `1`。避免使用类型 `unspec`（值 `0`）的属性或命令
- 对给定操作使用**相同的命令 ID 用于请求和回复**
- 为每个通知使用**单独的命令 ID**，以便用户空间能独立路由通知和回复
- 新族必须使用 `unified` 消息 ID 模型。`directional` 模型仅用于传统族
- `do` 操作**绝不能**回复多条消息或使用 `NLM_F_MULTI`。应改用过滤后的 dump
- `kernel-policy` 应为 `per-op`（默认值）或 `split`。**不要**为新族使用 `global`——它阻止了按命令缩小属性范围
- 不要引入对请求类型特定标志（`NLM_F_REPLACE`、`NLM_F_EXCL`、`NLM_F_CREATE`、`NLM_F_APPEND`、`NLM_F_NONREC`、`NLM_F_BULK`、`NLM_F_ATOMIC`、`NLM_F_ROOT`、`NLM_F_MATCH`）的新使用。它们已废弃，仅限于已使用它们的传统族

## 回复、ACK 和通知

- **所有操作**，特别是 `NEW` / `ADD`，**必须回复完整的消息**，携带关于新对象的标识信息（例如分配的 ID）。一旦某个命令只回复 ACK，这就成为 uAPI；宁可多回复信息。不要依赖 `NLM_F_ECHO` 来传递已创建对象的信息
- 当响应请求发出通知时，**将请求信息传递给 `genl_notify()`**，以便 `NLM_F_ECHO` 得到遵守

## Dump

- 如果 dump 迭代可能跳过或重复对象（例如由于无锁数据结构），在受影响的消息上设置 `NLM_F_DUMP_INTR`。这通常通过维护一个 generation 计数器并将其记录在 `netlink_callback.seq` 中实现

## 扩展 ACK

- 在错误**和**成功路径中提供扩展 ACK 信息（在成功路径中作为警告），只要有用即可
- 如可能，优先使用标准属性而非纯文本消息：
  - `NL_SET_BAD_ATTR` —— 错误的属性
  - `NL_SET_ERR_ATTR_MISS` —— 缺失的属性
- 如果属性信息和返回的 errno 已充分解释问题，则**不应**包含纯文本消息

## 属性设计

对于任何新的 `nla_get_*` / `nla_put_*` 调用，**始终**检查类型是否与 YAML 规范、验证策略和其他使用一致。

- **对数组优先使用重复属性（`multi-attr`）**，而不是嵌套或索引编码。不要额外包装 nest，不要使用 `indexed-array`，不要为新族使用 `type-value`
- **避免在属性内使用二进制结构体。** 将每个成员拆分为自己的属性。二进制结构体会损害验证和可扩展性，新属性中强烈不鼓励使用
- **大多数情况下优先使用 `uint` / `sint`（可变宽度 64 位）** 而非固定宽度整数类型
- **避免使用小于 32 位的整数类型**——由于 4 字节属性对齐，它们不节省内存。除非实际承载的值确实保证是 u8 或 u16（例如它是协议头部字段）
- 对于传统固定结构体中的 64 位整数，使用 `pad` 属性（每个属性集只允许一个）
- 字符串默认为 NUL 终止（`NLA_NUL_STRING`）；仅为传统族设置 `unterminated-ok`。`max-len` **不**计算终止符——规范中通常写 `max-len: CONST - 1`

## 验证策略

- 新的 Generic Netlink 族必须拒绝未知属性（这是新族和选择严格检查的族的默认行为）
- 声明正确的属性验证策略强烈优于手写验证。查找本来可以使用的 `NLA_POLICY_*`

## YAML 规范卫生

审查 `Documentation/netlink/specs/` 下的文件时：

- 属性的 `value` 仅在其主集合中定义，绝不在 `subset-of` 的分数集合中定义
- 许可证必须为 `((GPL-2.0 WITH Linux-syscall-note) OR BSD-3-Clause)`
- 规范必须是自包含的：不依赖其他规范或 C 头文件，除了通过 `header` 属性引用共享常量（例如 `IFNAMSIZ`）
- 每个主要属性应有 `doc`
- 优先使用 `notify:`（与 GET 操作共享内容）而不是 `event:`（自定义子集）。事件被认为不太惯用，除非携带的信息不是用户会想直接查询的（GET）
- 对于 `netlink-raw` 子消息：**选择器属性必须在子消息属性之前出现**；解析使用距离选择器**最近**的值。在期望级别缺少选择器是错误
- YAML 结构体隐式为 C-packed。自然对齐需要显式的填充成员——不要假设编译器会添加空洞
- YAML 规范中的名称应包含破折号而不是下划线（代码生成器会转换它们）

## Invariants（不变式）

- 第一个属性/命令 ID 应为 1，不使用 `unspec`（0）
- `do` 操作不能回复多条消息
- 新族必须使用 `unified` 消息 ID 模型
- 所有 `NEW` / `ADD` 操作必须回复完整消息（不只是 ACK）
- 字符串属性默认需要 NUL 终止
- 新族必须拒绝未知属性
- 不能使用小于 32 位的整数类型

## Failure Modes（故障模式）

| 违规操作 | 结果 |
|---------|------|
| 新族使用 `directional` 模型 | 兼容性混乱，无法使用现代功能 |
| `do` 操作回复多条消息 | 用户空间解析错误 |
| 使用小于 32 位的整数类型 | 不节省内存，验证复杂化 |
| 属性中使用二进制结构体 | 损害验证和可扩展性 |
| 命令只回复 ACK 而不回复完整消息 | 后续无法添加完整消息回复（已固化 uAPI） |
| 不对重复/跳过的对象设置 `NLM_F_DUMP_INTR` | 用户空间无法检测不一致的 dump |
| YAML 规范使用下划线而非破折号 | 代码生成器会转换，但规范内部不一致 |

## Quick Checks（快速检查清单）

- [ ] 新族的第一个属性/命令 ID 是否为 1？（而不是 0）
- [ ] 新族是否使用 `unified` 消息 ID 模型？
- [ ] `do` 操作是否只回复单条消息？
- [ ] 所有 `NEW` / `ADD` 操作是否回复包含对象标识信息的完整消息？
- [ ] 属性类型是否与 YAML 规范、验证策略和其他使用一致？
- [ ] 新属性是否避免了二进制结构体？
- [ ] 字符串属性是否使用了 `NLA_NUL_STRING` 并带合理的 `.len`？
- [ ] 新族是否拒绝未知属性？
- [ ] YAML 规范的许可证是否正确？
- [ ] `netlink-raw` 子消息中，选择器属性是否在子消息属性之前？
