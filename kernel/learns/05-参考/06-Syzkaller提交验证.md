# Syzkaller 提交信息验证方法

## 背景与核心理念

syzbot/syzkaller 报告的 bug 需要格外谨慎对待，因为模糊测试触发的崩溃位置往往不是真正的根因。

### 为什么需要专门验证

- syzbot 报告经常具有误导性 — 崩溃位置可能不是根因
- 复现程序可能通过非预期路径触发 bug
- 作者经常在未完全理解的情况下猜测根因
- 代码中的注释可能反映的是错误假设
- 时间压力导致 "看起来够好" 的修复可能并未解决真正的问题

### 核心原则

**提交信息中的每个声明和 patch 添加的每个注释，都应被视为"待验证"而非"已证明"。** 分析者的职责是证明或证伪这些声明，而非盲目相信。

---

## 验证流程

### 阶段 1：提取所有声明

从提交信息中提取每一个事实性声明，按编号列出：

1. **Bug 描述**：作者声称的 bug 是什么
2. **触发路径**：作者声称的触发方式
3. **根因**：作者认为的根因
4. **修复机制**：作者认为修复为什么有效
5. **代码注释**：patch 新增的每一段注释

### 阶段 2：收集上下文

1. 收集提交信息中提到的所有函数名
2. 检查是否存在 `Closes:` 标签或指向原始 syzbot 报告的 message ID
3. 如果找到 message ID，获取原始 bug 报告并与修复方案交叉验证
4. 加载所有涉及符号的定义

### 阶段 3：追踪声明的 bug 路径

对每个声明，通过追踪实际代码路径来验证：

```
声明 1: "XXXXXXXX"

调查过程：
- 调用路径、代码片段、从代码中提取的证据

结论：TRUE / FALSE
- 得出该结论的理由
```

使用调用者/被调用者追踪来重构从触发点到崩溃点的实际路径。对路径中每一步的前提条件进行验证。

### 阶段 4：验证 bug 机制

从声称的根因追踪到实际 bug：

```
声明 4: "XXXXX"

调查过程：
- 代码行、调用追踪等
- 如果 X 发生则崩溃

结论：ROOT CAUSED yes / no
- 如果条件 XYZ 满足，崩溃可能发生
- 但声明说的是 ABC
- 可能是一条不同的路径导致了问题
```

### 阶段 5：验证代码注释

Patch 新增的每一段注释都必须验证：

1. 该陈述是否事实正确？
2. 它是否准确描述了该代码路径何时被触发？
3. 是否存在它未提及的其他场景？

### 阶段 6：误报检查

在报告问题之前，将你的分析结果通过误报消除协议进行验证。修正或丢弃任何不准确之处。

---

## 结论严重性等级

对每个被证伪或无法验证的声明，标注严重性：

| 等级 | 含义 |
|------|------|
| 高 | 核心 bug 描述或根因分析有误 |
| 中 | 修复机制的解释不准确 |
| 低 | 注释或次要描述有误 |

如果一个声明无法被证明为真，就应将其视为回归（regression），原因如下：

- 说明作者未充分验证其解释
- 会使未来修复相关 bug 变得更加困难
- 可能误导其他开发者
- 未经验证的声明会降低代码可维护性

## 输出结果

对于每个验证的提交，应明确评估：提交信息中的声明是否准确？修复方案是否经过充分论证？核心声明是否可被独立验证？

这种验证方法不仅适用于 syzbot 报告，也可推广到任何涉及复杂竞态条件或稀有代码路径的 kernel patch 审查。
