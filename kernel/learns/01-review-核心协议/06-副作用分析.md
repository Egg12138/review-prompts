# 副作用分析：查找未被修改代码中的隐藏 Bug

## 1. 什么是副作用分析

内核代码审查中有一个**极易被忽略的问题**：patch 本身可能是正确的，但 patch 改变了某个行为约定（不变量），而**其他未被修改的代码**可能默默地依赖于这个约定的旧行为。

> **正向问题**："新代码是否遵守了规则？"——这是常规代码审查的工作。
>
> **反向问题**（副作用分析要回答的）：**"有哪些现有代码因为这个变更而被破坏了？"**

副作用分析（side-effect analysis）专门回答这第二个问题。它的核心思想是：

> **对函数 A 的修改，可能破坏所有调用 A 的函数，也可能破坏所有依赖于 A 的旧行为的代码。**

### 典型场景

| 变更类型 | 旧行为 | 新行为 | 谁会被破坏 |
|---------|--------|--------|-----------|
| 锁协议变更 | 使用 spin_lock | 改用 mutex_lock | 所有仍然期望原锁语义的调用者 |
| 返回值语义变更 | 返回 0 表示成功 | 返回正数表示成功 | 所有检查 `if (ret < 0)` 的调用者 |
| 前置条件变更 | 不需要调用者加锁 | 要求调用者已持有锁 | 所有未加锁就调用的调用者 |
| 数据结构变更 | struct 中 field_x 存在 | field_x 被移除或改变类型 | 所有访问 field_x 的代码 |

---

## 2. 为什么要做专门的副作用分析

常规审查有一个盲区：审查者正确地识别了规则、分类了行为变更，但**几乎从不构造和执行能够发现"未修改代码中被破坏假设"的搜索**。这不是能力问题，而是注意力结构问题——正向问题（diff 是否正确）自然占据了全部注意力，反向问题（什么东西被破坏了）需要刻意切换思维方式。

副作用分析的存在意义就是因为反向搜索是**它唯一的工作**——它不能被跳过或降级优先级。

---

## 3. 常见错误（不要犯这些错误）

### 错误 1：做正向分析而非反向分析

- **错误做法**："新代码是否获取了锁 L？"——这是正向问题，常规审查已经回答了。
- **正确做法**："持有旧锁的现有代码是否在没有新锁保护的情况下访问了共享资源？"——这是反向问题。

### 错误 2：只在被修改的文件中搜索

如果 patch 修改了 `foo.c`，只搜索 `foo.c` 是**毫无意义的**——bug 在**未被修改的代码**中。始终进行广泛搜索，不要限制文件路径，或者使用宽泛的子系统模式。

### 错误 3：不看函数体就排除搜索结果

"基于一行 grep 匹配结果就断定这个函数已经正确处理了"是无效的——你还没有阅读函数体。所有匹配到的函数都必须标记出来，进入完整审查。

### 错误 4：将子系统指南的文档视为"已经处理好了"

当指南说"函数 X 需要锁 L"时，这告诉你的是**其他代码的假设**。如果 patch 修改了加锁策略，你必须验证这些假设是否仍然成立。

---

## 4. 检测行为变更（Behavioral Change Detection）

分析的第一步是识别 patch 引入了哪些类型的行为变更。每种变更类型对应不同的搜索策略。

### 行为变更类型表

| 变更类型 | 在 diff 中寻找什么 |
|---------|-------------------|
| `locking_protocol`（锁协议） | 锁获取方式改变、锁类型改变、锁范围缩小/扩大 |
| `return_semantics`（返回值语义） | 函数返回值的含义改变、新增错误码 |
| `precondition_change`（前置条件） | 函数现在要求调用者处于不同的状态 |
| `data_structure`（数据结构） | struct 字段新增/删除/改变类型、布局改变 |
| `resource_lifetime`（资源生命周期） | 分配/释放时机改变、引用计数改变 |
| `global_state`（全局状态） | 全局/静态变量的语义改变 |

对每个检测到的行为变更，记录：

```
变更ID:  区分不同变更的唯一标识
类型:    上述类型之一
描述:    变更了什么
旧行为:   变更前的行为
新行为:   变更后的行为
共享资源: 该变更涉及哪些共享资源（锁、数据、状态等）
```

---

## 5. 构建搜索计划（Search Plans）

对于**每个行为变更**与**每个相关的子系统指南规则**的组合，构造一个具体的搜索计划。一条规则与行为变更"相交"的条件是：该规则记录了一个不变量（invariant），而行为变更恰好修改了这个不变量。

### 搜索计划格式

```
SEARCH PLAN: <change_id> × <rule_name>
  行为变更类型:  <变更类型> —— <变更描述>
  指南规则原文:  "<从加载的指南中引用>"
  需要证明什么: <必须保持为真的具体陈述>
  搜索:
    1. <搜索工具>(<参数>) —— <为什么这个搜索能找到受影响的代码>
    2. <搜索工具>(<参数>) —— <为什么>
  对每个结果检查: <在每个函数体中需要验证什么>
```

### 按变更类型构造搜索

| 变更类型 | 主要搜索 | 检查什么 |
|---------|---------|---------|
| `locking_protocol` | `grep_functions(pattern="<旧锁名>")` 查找锁持有者；`grep_functions(pattern="<共享资源>")` 查找资源访问者 | 这些函数在访问共享资源前是否获得了新的锁？ |
| `return_semantics` | `find_callers(name="<被修改函数>")` | 调用者是否处理了新的返回值？ |
| `precondition_change` | `find_callers(name="<被修改函数>")` | 调用者是否建立了新的前置条件？ |
| `data_structure` | `grep_functions(pattern="<字段名>")` | 函数对字段的假设是否仍然成立？ |
| `resource_lifetime` | `find_callers(name="<分配或释放函数>")` | 调用者是否处理了新的生命周期？ |
| `global_state` | `grep_functions(pattern="<变量名>")` | 函数对状态的假设是否仍然成立？ |

### 关于子系统指南中的搜索指令

如果子系统指南提供了明确的搜索指令（例如"使用 `grep_functions` 或 `find_callers` 搜索 X"），则**必须使用这些精确的搜索**。指南的作者正是为了这个场景而编写了这些指令。

---

## 6. 执行搜索

执行所有搜索计划，并对每个计划：

1. 运行计划中的所有搜索——将并发调用批量处理
2. 收集所有结果
3. **标记所有返回的函数**——不要基于一行 grep 匹配就过滤结果

> `grep_functions` 返回的单行上下文只说明一个函数**包含**某个模式。这**完全不说明**顺序、排除或正确性。每个返回的函数都必须标记出来进入完整审查。

**对于 `locking_protocol` 变更**：每个获取旧锁或访问共享资源的函数都必须被标记。不要根据一行 grep 匹配就假设正确。

---

## 7. 审查标记函数

加载所有被标记的函数的完整函数体，逐函数进行不变量验证。

### 7.1 对于锁协议（locking_protocol）变更：构建竞态时序

这是最重要的分析步骤。锁协议变更的审查方法如下：

**第 1 步：识别共享资源访问。** 这个函数中哪些行读写了共享资源？

**第 2 步：识别互斥机制。** 这个函数是否获取了**新的**互斥机制？还是只有旧的？

**第 3 步：检查顺序。** 互斥是否在所有共享资源访问**之前**？

**第 4 步：构建竞态时间线：**

```
CPU 0 (patch 的新代码路径)          CPU 1 (被标记的函数)
──────────────────────────────         ─────────────────────────
获取新锁
访问共享资源
                                          获取旧锁（仅旧锁）
                                          访问共享资源 ← 没有互斥！
```

**第 5 步：确定后果。** Use-after-free？脏数据？撕裂读？内核 panic？

**关键原则：互斥点之前的有效性检查不是保护。** 如果代码先检查共享状态、然后获得互斥，这个检查是 TOCTOU（time-of-check-to-time-of-use）——标记为潜在 bug。

**竞态排除需要完整路径验证。** 在排除一个竞态时如果说"代码处理了无效状态"，必须枚举从竞态窗口打开点到声明的恢复点之间的**每一条指令**。如果中间有任何指令解引用、加锁或依赖了已经过时的状态，该竞态**没有被处理**——函数后面的 abort 路径不能使之前的解引用变得安全。

### 7.2 对于返回值语义/前置条件变更

1. 在被标记的函数中找到调用点
2. 检查调用者是否处理了新的返回值 / 满足新的前置条件
3. 追踪处理失败的后果

### 7.3 对于数据结构/资源生命周期/全局状态变更

1. 在被标记的函数中找到访问点
2. 检查函数对数据/资源/状态的假设是否仍然成立
3. 追踪旧假设的后果

---

## 8. 子系统指南交叉验证

**子系统指南的指令具有权威性。** 当指南说"将其报告为 bug"时，不能用你自己的推理来覆盖。

验证步骤：

1. 检查是否有任何被标记的函数匹配指南指令的模式——要么直接匹配，要么因为它**调用**了一个指南命名的函数（以有问题的顺序）
2. 如果匹配，确认存在对应的 `POTENTIAL_BUG` 裁决
3. 如果函数被给出 `CLEAR` 裁决但指南指令应该触发：**冲突——升级为 POTENTIAL_BUG**

**你的分析不能覆盖明确的指南指令。** 这些指令编码了已经经过真实 bug 验证的领域专业知识。互斥点之前的有效性检查是 TOCTOU，不是保护——这个原则在这里重申，因为审查者持续地犯这个错误。

---

## 9. 误报消除（False Positive Elimination）

对于审查中发现的每个潜在 bug，按其来源分类，然后应用不同的消除策略。

### 分类

- **Agent-identified**（审查者自行发现）：审查者通过推理找到的，没有对应的指南指令。
- **Guide-sourced**（指南来源）：通过执行指南的"报告为 bug"指令找到的。
- **Guide-escalated**（指南升级）：审查者最初给出 CLEAR，但指南交叉验证发现冲突后升级为 POTENTIAL_BUG 的。

### 按分类应用误报消除

| 来源 | 误报消除策略 |
|------|-------------|
| **Agent-identified** | 应用完整的误报检查清单。仅消除那些被误报指南明确拒绝的问题。 |
| **Guide-sourced / Guide-escalated** | 这些是子系统指南违反。**仅检查以下三点**：① 引用的指南规则是否存在；② 引用的代码是否存在；③ 代码是否确实违反了指南规则。如果以上三点都通过，**保留该问题**。不应用锁分析、竞态分析或其他任何误报分析。 |

**你自己的安全推理不是误报消除。** 仅当误报指南明确说"这是误报"时才能排除。

---

## 10. 结果的记录

每次副作用分析完成后，都需要将结果组织为清晰的结构，记录以下信息：

- 分析了多少个行为变更
- 执行了多少个搜索计划
- 标记了多少个函数
- 误报消除前有多少个问题
- 消除了多少个误报
- 确认了多少个回归问题
- 最高严重级别是多少

对于每个**已确认的回归问题**，记录：

- 出问题的文件、行号、函数名
- 问题类型（regression / potential-issue）
- 是否违反子系统指南
- 严重级别（低/中/高）
- 问题的详细描述（包含竞态时间线）
- 引发问题的源变更
- 涉及到的指南指令（如果有）

> **即使没有发现任何问题，也要记录空的结果。** 空结果本身是有价值的信息——它表明"经过系统的副作用分析，未发现未修改代码被破坏"。

---

## 总结：副作用分析的心智模型

把副作用分析想象成一张"因果关系网络"：

```
patch 修改了函数 A
    │
    ├──→ 影响所有调用 A 的 caller（向上传播）
    │      └──→ 可能继续影响这些 caller 的 caller
    │
    └──→ 影响所有依赖 A 的旧行为约定的代码
           └──→ 锁协议变了？返回值变了？前置条件变了？
                 数据结构变了？生命周期变了？全局状态变了？

你的任务：对每个"变了"的东西，问自己——
"还有谁相信老规矩？他们现在是不是被坑了？"
```

这个反向问题思维，是区分优秀内核审查者和普通审查者的关键能力。
