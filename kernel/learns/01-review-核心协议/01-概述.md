# 第一章：概述 —— 内核补丁深度回归分析协议

## 1.1 什么是深度回归分析

Linux 内核补丁审查远远不止是"看一下代码有没有明显问题"。本协议定义了一套 **深度回归分析（deep regression analysis）** 方法——它不是一次快速检查（quick sanity check），而是一次对变更及其引发的回归问题的**彻底研究（exhaustive research）**。

核心信念是：**每一个变更都有 bug，直到被证明正确为止**。这意味着，不仅代码逻辑需要被验证，连提交信息中的每一句话、注释中的每一个断言，都必须逐一证明其正确性。任何无法证明的内容，都应作为回归问题报告。

## 1.2 设计哲学

这套协议建立在几个关键假设之上：

- **每一行改动都值得怀疑**。哪怕是看起来无害的注释修改，也可能隐藏语义不一致或误导性信息。
- **新 API 必须经过一致性（consistency）和易用性（ease of use）检查**。内核社区对接口设计有极高的要求，不符合惯例的 API 本身就是 bug。
- **任何对 C 语言最佳实践的偏离都被视为回归**。内核代码在长期维护中对编码规范、类型安全、内存安全等有严格约定。

## 1.3 何时使用本协议

本协议适用于需要对内核补丁进行**深度评审**的场景：

- 对功能复杂的补丁进行回归分析
- 审查涉及多个子系统的变更
- 分析 fix 类补丁是否真的解决了问题
- 在合入前对高危变更进行系统性检查

它**不适用于**：
- 简单的风格审查
- 快速 LGTM（Looks Good To Me）式通过
- 对 trivial 补丁的过度分析

## 1.4 整体阶段概览

协议将一次完整的深度分析拆解为若干可执行的阶段（phases），每个阶段有明确的目标和产出：

| 阶段 | 名称 | 核心目标 |
|------|------|----------|
| Task 0 | 上下文规划 (Context Planning) | 阅读完整 diff，理解提交意图，规划上下文收集 |
| Task 1 | 上下文收集与变更分类 (Context & Categorization) | 收集所有涉及的函数/类型/调用关系，对变更进行细粒度分类 |
| Task 2 | 回归分析 (Regression Analysis) | 逐类分析变更的回归风险，包含可达性检查、调用栈分析、邮件讨论审查 |
| Task 3 | 验证 (Verification) | 消除误报，确认真实回归 |
| Task 4 | 报告 (Reporting) | 按内核社区标准输出 review-inline.txt |
| Task 5 | 元数据输出 (Metadata) | 生成结构化的 review-metadata.json |

这种分阶段结构确保了分析过程**系统化、不遗漏**，并且每一步都建立在前一步的基础上。

## 1.5 核心原则

1. **先理解，再分析**。在没有充分理解变更意图和上下文之前，不要提前下结论。
2. **系统化分类**。将所有变更按类型拆解，逐个击破。
3. **可达性优先**。一个代码路径如果根本不会被触发，其正确性就毫无意义。
4. **误报消除**。所有疑似回归都必须经过假阳性检查，只有确认后才能报告。
5. **社区标准输出**。最终报告必须符合 Linux 内核邮件列表（LKML）的沟通规范。
