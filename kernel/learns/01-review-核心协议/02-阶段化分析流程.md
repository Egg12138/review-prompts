# 第二章：阶段化分析流程

## 2.1 为什么需要阶段化

内核补丁分析涉及大量信息：diff 中的每一处改动、被调用函数的实现、调用链上的上下文、子系统约定、配置依赖……如果没有任何结构，分析者很容易在细节中迷失，遗漏关键问题。

阶段化流程（phased workflow）的核心价值在于：

- **避免跳跃式结论**：不要在理解完整上下文之前就下结论——你很可能会错。
- **降低认知负荷**：每个阶段只关注一组特定目标，让注意力集中在当前最重要的事情上。
- **可复现性**：任何人都可以按照相同步骤对同一补丁进行分析，得到一致的结果。

## 2.2 完整流程总览

```
[Task 0]  上下文规划
    │
    ▼
[Task 1]  上下文收集 + 变更分类
    │
    ▼
[Task 2]  回归分析（含可达性检查）
    │
    ├── 有回归 → [Task 3] 误报消除 → [Task 4] 报告生成
    │
    └── 无回归 → [Task 4] 报告生成
                │
                ▼
           [Task 5] 元数据输出
```

## 2.3 各阶段详解

### Phase 0：上下文规划（Context Planning）

**为什么存在这个阶段？** 在没有理解补丁的全貌之前就开始搜索上下文，是低效且容易跑偏的。你需要先回答三个问题：

1. 这个提交的目的是什么？
2. diff 中有哪些类型的变更？
3. 我需要什么样的额外信息才能理解这些变更？

具体做法：
- **逐行阅读完整的 diff**，理解每一个 hunk 的改动含义。不要只读 commit message 就跳过。
- 在阅读过程中，如果发现可疑问题，先记录下来（放入 TodoWrite 暂存），但**不要深入分析**——那是 Task 2 的工作。
- **文档化提交意图**：用一句话记录这个提交想要解决什么问题。
- **对变更进行分类**：识别出控制流变更、资源管理、锁操作等类别（详见第四章）。
- **规划上下文收集方案**：尽量一次性加载所有需要的上下文，避免反复调用工具浪费 token 空间。

### Phase 1：上下文收集与变更分类（Context Gathering & Categorization）

**为什么存在这个阶段？** 没有完整上下文的分析就像盲人摸象。你必须看到完整函数的全貌、调用链的上下层次、相关类型的定义，才能真正判断变更是否正确。

上下文收集的目标是建立对变更代码的**完整理解（complete understanding）**。具体包括：

- 识别所有被修改的函数和类型（通过 diff 分析或工具辅助）
- 获取这些函数和类型的完整定义——永远不要只靠 diff 中的片段做判断
- 追踪调用关系：谁调用了这些函数？这些函数又调用了谁？
- 特别关注错误处理路径和清理路径（cleanup paths）
- 在收集完整上下文之前，**不要跳到分析阶段**，即使你觉得自己已经发现了问题。

完成上下文收集后，需要对所有变更进行**细粒度分类**（详见第四章），这是后续回归分析的基础。

### Phase 2：回归分析（Regression Analysis）

**为什么需要先做可达性检查？** 一个代码路径如果根本执行不到——比如被某个配置选项关闭，或被协议约束阻挡——那么它的正确性没有任何意义。**可达性（reachability）检查是回归分析的闸门**：如果代码路径不可达，这就是一个需要立即报告的阻断性问题（show-stopper），它优先于任何深度分析。

通过可达性检查后，进入完整的回归分析：

1. **调用栈分析**（callstack.md）：对于非 trivial 变更，必须分析调用栈，验证注释与行为一致、commit message 声明准确、设计决策合理。
2. **逐一分析每个变更类别**：使用已加载的上下文，针对 Task 1 中识别的每个 CHANGE-N 类别进行分析。
3. **邮件讨论审查**（如果可用）：搜索内核邮件列表（lore）中关于此补丁的讨论线程，检查是否有未解决的 reviewer 意见。来自自动化机器人（如 Sashiko、CI bots）的反馈不计入审查证据。
4. **Fixes: tag 验证**：对于重大 bug 修复，检查提交是否缺少 Fixes: tag。
5. **Kconfig 依赖验证**：如果补丁涉及配置选项，验证没有循环依赖或"静默禁用"问题。

### Phase 3：误报消除（False Positive Elimination）

**为什么需要这个阶段？** 深度分析是怀疑导向的，这意味着你会产生大量"疑似问题"。但其中一部分可能是误报——分析者因为对上下文理解不充分而产生的错误判断。如果将这些误报提交到内核邮件列表，会严重损害你的信誉。

具体操作：
- 加载 `false-positive-guide.md`（假阳性检测指南）
- 对每一个疑似回归逐一验证
- 只有通过验证的问题才能进入最终报告

### Phase 4：报告生成（Reporting）

**为什么需要这个阶段？** 分析结果需要以 Linux 内核社区可接受的方式传达。随意格式化的分析输出不仅会被忽略，还可能引发争议。

关键要求：
- 加载 `inline-template.md`，严格按照模板格式输出
- 创建 `review-inline.txt` 文件（在当前工作目录）
- **禁止**在报告中出现全大写的关键词（如 "REGRESSION:"）——这不符合内核社区沟通规范
- 不要包含已被判定为假阳性（false positive）的问题
- 不要引用、总结或复述自动化机器人的审查反馈
- 最终输出回归数量、token 使用量、模型版本等信息

### Phase 5：元数据输出（Metadata）

生成 `review-metadata.json` 文件，包含作者、SHA、主题、问题数量、严重等级等结构化信息。这个文件会被其他工具解析，因此**字段名称和格式必须严格匹配**，不允许自定义新增字段。

```json
{
  "author": "<提交作者>",
  "sha": "<提交 SHA>",
  "subject": "<提交主题>",
  "issues-found": <数字>,
  "issue-severity-score": "none/low/medium/high/urgent",
  "issue-severity-explanation": "<严重性说明>"
}
```

## 2.4 阶段之间的依赖关系

| 依赖 | 说明 |
|------|------|
| Task 0 → Task 1 | 必须先规划再收集，否则收集的方向不明确 |
| Task 1 → Task 2 | 必须先有完整上下文和分类，分析才有依据 |
| 可达性检查 → 其余 Task 2 | 如果代码路径不可达，后面的分析都是徒劳 |
| Task 2 → Task 3 | 发现问题后需要验证，而不是直接报告 |
| Task 3 → Task 4 | 只有验证通过的问题才能进入最终报告 |
| Task 4 → Task 5 | 报告完成后输出结构化元数据 |

## 2.5 重要的实践原则

- **不要在 Task 1 完成之前开始分析**。即使你一眼就看到了问题，也请先忍住——你很可能是错的。
- **保持上下文的焦点**。在处理每个任务时，丢弃非核心的中间细节以节省 token 空间，但保留与当前分析阶段直接相关的函数和类型上下文。
- **如果发现回归，保留所有上下文直到报告完成**——在报告生成阶段你还需要回顾分析细节。
