# 07 — 误报消除检查清单

## 核心原则

**如果你无法用至少一条执行路径上的具体证据证明问题的存在，就不要报告它。**

**推论（来自 callstack.md）：** 对于死锁、无限等待、崩溃和数据损坏，"具体证据"意味着证明代码路径在结构上是可能的——而不是证明它在每次运行时都一定会执行。一个没有超时、没有备用唤醒条件的 `wait_event`，如果其唤醒条件依赖于可能停止的外部事件，那就是一个死锁 bug。不要以"实际中不太可能发生"为由放过此类 bug。

这个原则是整个内核审查工作的基石。如果你不能放下"找到越多 bug 越厉害"的心态，转而追求"每条报告都必须有铁证"，你的审查反而会成为维护者的负担。

---

## 15+ 类常见误报模式

每一类都来自真实审查中反复出现的错误。请逐类理解，并在每次审查结束时用它们来检验自己的发现。

---

### 0. 上下文保持（Context Preservation）

在开始误报检查之前，先确认以下内容是否在上下文窗口中：

- 如果正在分析一个 git commit，确认完整的 commit message 仍在上下文中；如果已被移出，请重新加载。
- 如果正在处理一个 patch（而非 commit），确认完整的 patch 描述仍在上下文中；如果不在，请重新读取。
- 确认以上信息在误报检查阶段仍然可用。
- **在上下文就绪之前，不要进行误报验证。**

---

### 1. 防御性编程请求（Defensive Programming Requests）

**永远不要建议添加防御性检查**，除非你能证明：

- 输入来自不可信源（例如用户空间/网络）
- 存在一条实际路径，让无效数据能够到达这段代码
- 当前代码确实会因此失败

**错误示例（不要这样做）：**
- "为了安全，这里加个边界检查吧"
- "这个索引应该做一下验证"

**正确示例（可以这样做）：**
- "funcA() 传入的用户输入在到达这里之前没有经过任何校验"

---

### 1.1 未处理错误（Failure to Handle Errors）

**永远不要报告"未处理错误"**，除非：

- 你能证明这个错误确实可能发生
- 你已经确认函数参数没有阻止该错误的发生

---

### 2. API 误用假设（API Misuse Assumptions）

**永远不要报告基于理论上的 API 误用的问题**，除非你能证明：

- 存在一条实际的调用路径会触发该问题
- 函数名或文档没有明确指出其使用约束
- 内核中类似的 API 确实会验证相同的前置条件

---

### 3. 不可验证的假设（Unverifiable Assumptions）

**核心方法论：先假设作者是错的**，然后要求自己拿出证据证明他是对的。

- 不可信来源（网络/用户空间）的任何假设都需要具体代码证据来证实
- 对于 commit message、注释和代码中的断言和声明，逐一验证其是否成立
- 如果作者做出了未经代码验证的声明，视其为"未经验证"，不要直接采信
- 设计决策必须通过代码或文档来证明其合理性
- **阅读完整的 commit message。** 如果 commit message 对某种行为做了解释，请用代码证据验证该解释是否正确。
- **阅读周围的代码注释。** 验证注释是否准确地描述了代码行为。

**在以下情况下可以放过：**
- 你找到了具体的代码，证明作者的假设是正确的
- 你可以用具体的代码路径验证所有假设
- 行为是**被证明正确**的，而不仅仅是**被声称正确**

---

### 3.1 基于注释的误放行（Comment-Based Dismissals）——强制检查

**关键：** 当你因为一段注释或文档说代码如何工作而决定放过一个问题时，你**必须用实际实现来验证**。

1. **读函数体，不要只读注释**
   - 注释可能被复制粘贴到多个语义不同的实现中
   - 同一个注释可能出现在 `#ifdef` / `#else` 的两侧
   - 输出要求：引用实际的实现代码，而非仅仅注释

2. **检查条件编译**
   - 如果代码有 `#ifdef CONFIG_FOO` / `#else` 分支，判断哪个分支适用
   - 一个分支中描述行为的注释可能不适用于另一个分支
   - 输出要求：说明哪个配置分支适用以及原因

3. **验证辅助函数的行为**
   - 如果你说"函数 X 返回 Y 所以没问题"，请实际阅读函数 X 的实现
   - 检查函数 X 是否有依赖于配置的行为
   - 输出要求：引用函数 X 的实现，证明它确实保证了所声称的行为

4. **如有疑问，报告问题**
   - 如果你无法验证注释在所有配置下都与实现一致，就报告它
   - **一个因错误文档而被放过的 bug，比一次误报要糟糕得多**

---

### 4. 锁误报（Locking False Positives）

**在报告锁问题之前：**

- 检查所有调用函数是否已持有锁
  - 输出要求：列出每个调用者及其持有的锁（例如 "caller() 在 file:line 持有 mutex_x"）
- 向上追溯 2-3 层调用链，找到锁的上下文
  - 输出要求：从入口点到问题现场的完整锁链
- 验证实际的锁需求
  - 输出要求：引用锁的文档或约定（例如 "must hold rcu_read_lock"）
- 考虑 RCU 及其他无锁机制
  - 输出要求：找到的 RCU/无锁机制，或 "不适用"

**常见错误：**
- 忽略了调用者已经持有所需锁
- 没有识别出 RCU 保护区间
- 假设所有共享数据都需要传统锁

---

### 5. Use-After-Free 混淆（Use-After-Free Confusion）

**区分以下三种情况：**

- **Use-After-Free（访问已释放的内存）** ← **报告这个**
- Use-Before-Free（使用完之后再释放）← **不报告**（这是正常的）
- Free-After-Use（用完再释放的正常清理）← **不报告**（这是正常的）

**验证方法：**
- 追踪操作的确切时序
  - 输出要求：序列如 "alloc@loc → use@loc → free@loc → use@loc" 或 "未发现 UAF"
- 检查对象所有权是否已经转移
  - 输出要求：所有权转移点，或 "所有权未转移"

---

### 6. 资源泄漏误解（Resource Leak Misconceptions）

**以下情况**不是泄漏**：

- 所有权已经转移给另一个子系统
- 对象已经被添加到链表/队列中等待后续处理
- 清理操作会在回调或延迟工作中执行
- 代码位于测试代码中，不影响系统

**验证方法：**
- 追踪对象所有权变化
  - 输出要求：所有权链 "alloc@loc → 存储到 X@loc → 由 Y@loc 释放" 或 "确认泄漏"
- 检查异步清理机制
  - 输出要求：清理回调或 workqueue handler，或 "未发现异步清理"
- 了解子系统的所有权模型
  - 输出要求：引用子系统约定，或 "无文档化模型"

---

### 7. 顺序变更（Order Changes）

**不要报告顺序变更问题**，除非你能证明：

- 引入了竞态条件（race condition）
- 破坏了某种依赖关系
- 出现了 ABBA 死锁模式
- 状态变得无效

---

### 8. 竞态条件（Races）

报告竞态条件的正确方法：

1. **确定涉及的数据结构名称和定义**
   - 输出要求：struct 名称及其位置
2. **确定应该保护它们的锁**
   - 输出要求：锁的名称及其定义位置
3. **用代码片段证明竞态存在**
   - 输出要求：两条可以并发执行的代码路径及其位置

---

### 8.1 竞态条件免除的完整路径验证（Race Dismissal: Full-Path Verification）——强制检查

当你因为"代码会检测到无效状态并中止"而决定放过一个竞态条件时，你**必须**验证从竞态窗口到恢复点之间的**全部指令序列**。函数后面某处有一个中止路径，并不能让前面的解引用操作变得安全。

在接受竞态条件免除之前，回答**所有**以下问题：

1. **哪一条确切的指令打开了竞态窗口？**
   - 输出要求：函数、file:line、什么状态变得过期
2. **哪一条确切的指令关闭了它（drain/barrier/lock）？**
   - 输出要求：函数、file:line、同步机制
3. **你声称的"优雅处理程序"是什么？**
   - 输出要求：函数、file:line、它如何检测无效状态
4. **列出 #1 和 #3 之间所有访问该争议资源的指令。如果资源被竞态线程无效化了，它们全部安全吗？**
   - 输出要求：逐条列出每条指令及其判定（安全/不安全）

如果你不能对问题 #4 中**每一条**中间指令都给出肯定的回答，那么这个免除就是无效的。报告这个竞态条件。

---

### 9. 性能权衡（Performance Tradeoffs）

**以下情况不是回归：**

- 性能降低是有意的权衡
- commit message 解释了性能影响
- 优先选择了简洁性/可维护性
- 是在为不同的使用场景做优化

---

### 10. 有意向后兼容（Intentional Backwards Compatibility）

- 保留过时的 sysfs 或 procfs 文件不是必需的，也不是回归
- 即使废弃的 sysfs 文件仍然存在并返回任意常量值（0、空字符串、某个固定的字符串都可以），只要返回的值在废弃之前的接口中是合法的，就不算回归

**只有当你能证明资源契约被破坏时，才需要报告。**

---

### 11. 主观审查模式（Subjective Review Patterns）

- SR-* 模式标记的问题不是 bug，而是**观点**
- 但观点本身也可能出错。重点关注与 commit message、附近代码、附近注释以及"自我辩论"部分的交叉验证

---

### 12. 未初始化变量（Uninitialized Variables）

- **给变量赋值就等于初始化**
- 将未初始化的变量传给函数是没问题的——只要该函数在读取之前写入它
- **只报告读取未初始化变量**的问题，不要报告写入的问题
- `kzalloc()` / `kcalloc()` 会将所有字节清零。如果零值就是正确的值（NULL 指针、零计数、初始值为 `{NULL}` 或 `{0}` 的空链表头），不要标记缺少显式初始化

---

### 13. 隐式守卫条件（Implicit Guard Conditions）

**在报告 NULL 解引用之前：**
- 复习 technical-patterns.md 中 "NULL Pointer Dereference" 部分的内容
- 对于**每一个** NULL 指针，加载并完整分析 pointer-guards.md

---

### 14. 补丁系列中的误报排除（Patch Series False Positive Removal）

大型变更被拆分为小的逻辑单元，目的是让它们更容易理解和审查。

**正确的补丁系列示例：**
- PATCH 1：添加一个新 API
- PATCH 2：将一个子系统或一个文件改为使用新 API
- PATCH 3-N：将所有其他子系统或文件改为使用新 API
- PATCH N+1：删除旧 API

不要对大型变更拆分的合理性做评判。只按照审查提示和误报指南寻找**客观 bug**。

如果我们发现的潜在 bug 只是**稍后在系列中完成的工作中的一部分**，那就是误报，应该忽略。

**不正确的补丁系列示例：**
- PATCH 1：引入回归（崩溃、溢出、各种 bug）
- PATCH 2：修复该回归

我们期望系列中的每个 patch 都在朝着一个更大的目标前进，但**我们要求每个 patch 都是自包含且正确的**。具体来说：
- 每个 patch 必须能编译
- 不能引入新的 bug

系列中的中间 patch 可能有意引入后续 patch 会修复的性能问题。commit message 或代码中的注释应说明这是有意的。

**如果你发现了一个确凿的回归，而它在后续的 patch 中已被修复，你仍然必须报告这个回归。**
- 但是，你必须在 bug 报告中说明你在系列后面找到了修复
- 报告时，同时包含修复 commit 的 SHA 和 subject 行

**补丁系列强制验证：**
- 提示中是否提供了 git range？[ 是 / 否，range 内容 ]
- 你是否使用它做了向前搜索？[ 是 / 否 ]

---

### 15. 子系统指南违规的幻觉检查（Subsystem Guide Violations: Hallucination Check Only）

被标记为 `subsystem_guide_violation: true`、类别为 `guide-directive`、或 `issue_type: "potential-issue"` 且含有 `guide_directive` 字段的问题，属于子系统指南违规。子系统指南是**权威的**——违规本身被视为事实正确。

**注意：对于这类问题，只做以下三项幻觉检查。不要做其他任何事情。不要应用第 1-14 节。不要做 10 步验证检查清单。**

1. **引用的指南规则是否存在？** 重新读取子系统指南，确认引用的指令确实出现在指南文本中。如果 agent 编造或误引了规则，移除该问题。

2. **引用的代码是否存在？** 确认 agent 引用的函数、变量或代码模式是真实的。如果 agent 幻想了代码（错误的函数名、不存在的变量、编造的代码路径），移除该问题。

3. **代码是否确实违反了指南规则？** 并排阅读被引用的代码和指南规则。确认代码确实做了指南说不该做的事（或没有做指南要求的事）。如果 agent 将规则和代码错误地匹配了——例如指南禁止模式 X 但代码做的是模式 Y，或指南要求锁 L 但代码已经持有锁 L——移除该问题。

**如果所有三项检查都通过，保留该问题。你完成了。**

**对于子系统指南违规的明确禁令：**
- 不要分析这个 bug 是"真的"还是"理论上的"
- 不要检查代码是否"优雅地处理了它"
- 不要评估锁、竞态、可达性或安全性
- 不要运用你自己的推理来判断这个模式是否危险
- 不要检查调用者、被调用者或者除了确认代码存在之外的上下文
- 不要进行自我辩论
- **移除问题的唯一理由就是幻觉：编造的规则或编造的代码**

## 10 步验证检查清单

以下是从 agent 指令转化的学习版验证清单。每一步都是必须完成的，不能跳过。**不要在未产生要求输出的情况下声称完成。**

在报告任何回归之前，依次完成以下所有检查。

---

### 检查项 0：NULL 解引用预处理

对于 NULL 解引用问题，先复习 technical-patterns.md，然后加载并分析 pointer-guards.md。

- **输出要求：** "已完成审查" 或 "不适用——不是 NULL 解引用问题"

---

### 检查项 1：我能证明这条路径会执行吗？

- 找到可以到达这里的调用代码
  - **输出要求：** 引用带有位置的调用链（例如 "caller@file:line → target@file:line"）
- 检查是否存在阻止路径执行的不可达条件
  - **输出要求：** 列出检查的条件及其评估结果
- 确认不在死代码或已禁用功能中
  - **输出要求：** 启用该功能的 config 选项，或 "始终启用"

---

### 检查项 2：不良行为在结构上是可能的吗？

- 证明代码路径存在，且触发条件在结构上并非不可能
  - **输出要求：** 逐步展示执行路径，包含函数名和位置，说明失败是如何发生的
- 证明失败模式是具体的（崩溃、死锁、数据损坏、泄漏），而不仅仅是"增加了风险"
  - **输出要求：** 具体的失败模式和触发条件
- **注意：** 一个依赖于运行时条件（时序、内存压力、关闭状态、分配模式）的死锁、无限等待或崩溃，如果代码没有结构性的防范措施（超时、备用唤醒条件、有限重试），就是真正的 bug。不要以"这些条件不太可能发生"来辩驳。

---

### 检查项 3：我检查了完整的上下文吗？

- 检查调用函数（向上 2-3 层）
  - **输出要求：** 列出每个检查过的调用者，并从每个调用者中引用一行代码
- 检查初始化和清理路径
  - **输出要求：** 检查过的 init/cleanup 函数及其位置
- 验证子系统的约定
  - **输出要求：** 找到的约定以及代码是否遵循它们

---

### 检查项 4：这真的是错的吗？

- 检查是否有意的设计选择
  - **输出要求：** 如果 commit message 或注释表明作者已经考虑过同样的问题，引用原文；否则 "未找到解释"
- 检查是否是文档化了的限制
  - **输出要求：** 如果找到文档则引用；否则 "未文档化"
- 确认不是测试代码中的可容忍问题
  - **输出要求：** "生产代码" 或 "测试代码——严重性已调整"
- 确认 bug 在当前就存在，而不仅仅是"如果以后代码变了"才会出现
  - **输出要求：** 当前触发路径，或 "仅理论上的未来问题"
- **注意：** "理论上的"意味着代码路径今天不可能到达。一个依赖于运行时条件（时序、系统状态）的 bug 不是理论上的——它是一个有条件触发的真实 bug。

---

### 检查项 5：我检查了 commit message 和周围注释吗？

- 阅读完整的 commit message
  - **输出要求：** 引用任何解释该行为的文本，或 "未找到解释"
- 阅读周围的代码注释
  - **输出要求：** 引用相关注释，或 "无相关注释"

---

### 检查项 6：当 bug 需要多个复杂条件才能触发时

- 证明这些条件确实可能同时成立
  - **输出要求：** 展示每个条件可以同时为真的代码路径

---

### 检查项 7：我是否幻觉了一个根本不存在的问题？

- 验证 bug 报告与实际代码一致
  - **输出要求：** 引用文件中的确切代码片段
- 重新读取文件，确认代码与你的分析一致
  - **输出要求：** file:line 和逐字的代码
- 检查你的数学运算（除零需要分母为零等）
  - **输出要求：** 算术验证，或 "不涉及算术"

---

### 检查项 8：我检查了同一补丁系列中后续的修复吗？

- 在 git 历史中向前搜索（不是向后），仅在该分支上
  - **输出要求：** 检查过的 commits，或 "未提供 git range"
- 如果在系列后面找到了修复
  - **输出要求：** "在 [commit] 中找到修复——作为有后续修复的真实 bug 报告" 或 "未找到修复"

---

### 检查项 9：如果基于注释或文档免除了问题，验证实现

- 你是否阅读了实际函数实现，而不仅仅是注释？
  - **输出要求：** 引用证明注释准确性的实现代码
- 函数是否有 `#ifdef` / `#else` 分支，且行为不同？
  - **输出要求：** 列出影响行为的 config 选项，说明哪个适用
- 你是否验证了辅助函数的行为与其注释一致？
  - **输出要求：** 引用辅助函数的实现，或 "不涉及辅助函数"
- 如果你无法验证实现与文档一致，**不要免除**
  - **输出要求：** "实现已验证" 或 "无法验证——报告问题"

### 检查项 10：自我辩论（Debate Yourself）

这一项分为两个子步骤，顺序重要。**第 10.1 步生成的是反面假设供调查，而不是调查结论。** 只有当 10.2 步找到了具体的代码证据时，一个反面论证才能推翻一个 bug。

#### 10.1 扮演作者，生成反面论证

**针对 NULL 安全性，以作者的视角追问：**
- 审查者是否搜索过我的子系统中访问这个指针的类似代码？
- 如果报告缺少 NULL 检查，他们是否解释过为什么我子系统中的**其他**代码有那个检查？
- 他们验证了生命周期依赖关系，还是仅仅做了语法分析？
- 守卫条件和指针有效性之间是否存在他们遗漏的语义耦合？
- 鉴于已有的不变量，添加他们建议的检查是否冗余/过度谨慎？
- 他们比较过守卫模式吗——为什么路径 A 检查了 NULL 而路径 B 没有？

**针对锁问题，以作者的视角追问：**
- 审查者检查了我的调用者持有哪些锁吗？
- 他们理解了锁的上下文吗（process / softirq / hardirq / RCU）？
- 调用链中更高层是否有他们遗漏的锁？

**针对资源泄漏，以作者的视角追问：**
- 审查者追踪了所有权转移吗？
- 他们检查了异步清理机制吗？
- 资源是否被存储在某处等待后续清理？

**针对所有问题，以作者的视角追问：**
- 他们是否检查过这是否是**有意为之**（基于 commit message 或注释）？
- 他们验证了 bug 的条件是否真的可能吗？
- 他们是否混淆了"结构上可能的 bug"和"防御性编程建议"？

**输出要求：** 反对报告这个 bug 的最强论证。

**重要提示：** "实际中不太可能发生"不能作为放过死锁、崩溃或数据损坏的有效论证。只有"结构上不可能"（代码根本到达不了那个状态）才是有效的。参见 callstack.md 中的 "Reachability Dismissals"。

#### 10.2 回到审查者角色，反驳自己

现在扮演回审查者。极其仔细地思考你在 10.1 中生成的作者论证，然后决定审查是否正确。

- 用代码证据逐一回应作者的反面论证
- **输出要求：** 用代码证据反驳作者的代码，或 "无法用代码反驳——很可能是误报"

---

### 强制验证

- 如果以上任何输出要求为空或被跳过，重复该步骤
- 如果你无法为自己的结论提供代码证据，这个 bug 很可能是误报

## 特殊情况

### 测试代码
- 测试程序中的内存泄漏 → 通常可以接受
- 测试中的文件描述符泄漏 → 通常可以接受
- 但如果导致系统崩溃或挂起 → **报告它**

### 断言和警告
- 移除 `WARN_ON` / `BUG_ON` → 不是回归
- 移除 `BUILD_BUG_ON` → 不是回归
- 但如果移除了关键的运行时检查 → **报告它**

### Reverts（回退提交）
- 审查 revert 时，重点关注**新问题**
- 假设原始 bug 已被知晓/处理
- 不要重新报告原始问题

### 子系统排除
- `fs/bcachefs` → **跳过所有问题**
- Staging 驱动 → 适用较低标准
- 示例/测试代码 → 只关注系统影响

## 最终过滤器

在将问题加入报告之前，问自己以下四个问题：

1. **我是否有证据，而不仅仅是怀疑？** [ 是 / 否 ]
   - 展示触发 bug 所需所有组件的代码片段可以算作证据
     - 但前提是这些条件也被证明是可能发生的
   - 针对同一条件的现有防御性检查模式也算证据
     - 但前提是你能证明该条件确实可能发生
   - 现有的 `WARN_ON()` / `BUG_ON()` **不**算证据
   - 对于死锁/挂起：展示一个等待没有超时、也没有备选唤醒条件，**就是**证据。你不需要另外证明系统一定会进入那个状态。

2. **专家会认为这是一个真正的问题吗？** [ 是 / 否 ]

3. **这值得维护者的时间吗？** [ 是 / 否 ]

4. **我是在建议防御性编程，还是在报告具体的 bug？** [ 是 / 否 ]
   - 防御性编程："为了安全，这里加个 NULL 检查" → 丢弃
   - 具体 bug："这个 `wait_event` 没有超时也没有备选唤醒条件" → 报告

### 最终过滤器强制验证

如果你没有对全部 4 个问题都回答"是"，请进一步调查或**丢弃这个发现**。

## 牢记在心

- **没有明确证据的报告浪费所有人的时间。**
- **遗漏 bug 同样浪费所有人的时间——生产环境中的死锁比审查中的误报更糟糕。**
- **真正的 bug 有真正的证据**——但证据意味着证明代码路径存在且没有结构性防范措施，而不是证明该 bug 一定会在每次执行时都触发。
