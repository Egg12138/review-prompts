# 第三章：上下文建立

## 3.1 什么是"上下文"？

在 Linux 内核补丁分析中，**上下文（context）** 是指理解一个变更的完整正确性所需的所有信息。这远远不止是 diff 本身。

一个完整的上下文包括：

| 上下文层次 | 包含内容 |
|-----------|---------|
| 代码层 | 被修改函数的完整实现、调用者和被调用者的签名与逻辑、相关数据结构的定义 |
| 语义层 | 函数的预期行为（contract/semantics）、错误处理约定、锁的持有规则 |
| 子系统层 | 子系统特有的 API 使用惯例、配置选项的依赖关系、维护者的偏好 |
| 历史层 | 补丁的演化过程（邮件列表讨论）、之前版本中的反馈、相关的 Fixes: tag |

**没有完整上下文的分析是内核审查中最常见的错误来源。** 审查者在只看 diff 片段的情况下，很容易误判某个改动的正确性。

## 3.2 上下文建立的流程

### 第一步：完整阅读 diff

这是所有后续工作的起点。在做任何工具调用、任何搜索之前，你需要：

- **逐行阅读完整的 diff**，理解每一个 hunk 的作用
- **理解提交的意图（commit intent）**——这个提交想要修复什么问题？实现什么功能？
- 如果发现可疑问题，**先记录下来但不要深入分析**。过早分析会导致方向偏差。

> 注意：永远不要只读 commit message 就跳到下一步。深度分析要求你系统性地通过所有变更。

### 第二步：识别变更涉及的元素

阅读完 diff 后，你需要识别出所有被影响的代码元素：

- **被修改的函数**：哪些函数的实现被修改了？
- **被修改的类型**：哪些 struct、union、enum 的定义被改变了？
- **新增的函数/类型**：补丁引入了哪些新定义？
- **被删除的函数/类型**：如果补丁删除了某些函数，需要通过父 commit（parent commit）才能找到它们的定义——当前 diff 中已经不存在了。
- **调用关系**：修改的函数被谁调用？它们又调用了谁？

### 第三步：获取完整的定义

**这是最关键也最容易被忽略的步骤。** 永远不要依赖 diff 中的代码片段来分析问题。diff 只显示上下文中的几行——但你需要的可能是整个函数体，甚至是跨文件的多个函数。

```c
// 错误做法：只看 diff 中的这 3 行就下结论
+       if (IS_ERR(ptr))
+               return PTR_ERR(ptr);

// 正确做法：找到整个函数的完整实现，看看调用约定是什么
static int example_function(struct device *dev, void *arg)
{
        void *ptr;
        int ret;

        ptr = get_some_resource(dev, arg);
        if (IS_ERR(ptr))
                return PTR_ERR(ptr);  // ← 这行来自 diff

        // ... 函数的其他部分也需要看到才能理解完整逻辑
}
```

完整定义包括：
- 函数体（function body）的全部代码
- struct/类型定义的完整成员列表
- 相关的宏定义和枚举值

### 第四步：追踪调用关系

修改一个函数可能产生的影响远不止该函数本身。你需要追踪：

- **向上追踪（callers）**：谁调用了这个函数？上层调用者是否依赖于修改后的行为？例如，如果修改了返回值语义，所有调用者的错误检查逻辑都需要重新验证。
- **向下追踪（callees）**：这个函数调用了哪些子函数？修改可能通过函数指针或内联函数间接影响下层行为。
- **深度控制**：至少检查一级向上和一级向下。对于关键路径（如错误处理、资源释放），需要追踪更深。

### 第五步：特别关注关键路径

某些代码路径天然具有更高的回归风险：

- **错误处理路径（error handling paths）**：goto cleanup、错误码返回——这些路径在正常测试中往往覆盖不足
- **清理/释放路径（cleanup paths）**：资源释放、锁释放——错误路径中的释放逻辑是否与分配路径匹配
- **边界条件**：空指针检查、数组边界、整型溢出

## 3.3 如何高效获取上下文

在实际分析中，有两种主要方式来获取上下文：

### 首选方式：使用语义代码分析工具（semcode MCP）

语义代码分析工具可以直接理解代码结构，而不需要你手动 grep：

1. **diff_functions**：直接从 diff 中提取所有被修改的函数和类型
2. **find_function / find_type**：按名称搜索函数或类型的完整定义——支持正则表达式
3. **find_callchain**：追踪调用链关系，可以控制向上和向下的深度
4. **find_callers / find_calls**：分别查询"谁调用我"和"我调用谁"
5. **grep_functions**：在函数体内搜索特定模式（如特定 API 的用法）

### 备用方式：传统工具

当语义工具不可用时，可以使用 git 和 grep：

- 使用 `git show <sha>` 查看变更（不要使用 `git diff`，因为在 worktree 模式下 diff 的结果是空的）
- 使用 grep 手动查找函数定义和调用关系
- 记录任何因上下文不足而影响分析质量的情况

## 3.4 上下文管理策略

由于工具调用有 token 限制，合理安排上下文的加载顺序很重要：

1. **批量加载**：尽量一次性规划好所有需要的上下文，一次加载完成，避免反复调用
2. **阶段丢弃**：完成一个任务后，丢弃与该任务无关的中间细节——但保留后面还会用到的函数和类型上下文
3. **异常保留**：如果发现回归问题，保留所有相关上下文直到 Task 4 报告完成
4. **优先完整上下文**：始终优先获取完整函数/类型定义，而不是依赖 diff 片段——片段中的代码可能缺少关键的前置条件或后置条件

## 3.5 常见陷阱

- **陷阱 1**：看到几行改动就自以为理解了全部逻辑 → 解决：找到完整函数体
- **陷阱 2**：只关注被修改的函数，忽略调用者 → 解决：追踪至少一级向上调用
- **陷阱 3**：忽略被删除的函数 → 解决：从父 commit 中查找被删除的定义
- **陷阱 4**：在上下文收集完成前就开始分析 → 解决：严格执行阶段化流程
