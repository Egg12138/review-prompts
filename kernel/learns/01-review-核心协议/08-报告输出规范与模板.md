# 08 — 报告输出规范与模板

## 总纲

内核邮件列表（LKML）上的审查报告有自己独特的格式和文化。本文档将告诉你如何让你的报告看起来像是来自一位有经验的审查者，而不是一个自动化的机器人。

一条黄金法则：**你写的每一句话，都应该像是准备当面说给作者听的一样。**

---

## 格式铁律

### 1. 纯文本，绝对不要 Markdown

LKML 上只有纯文本。没有加粗、没有斜体、没有代码块标记、没有列表符号。

```
正确:
Can this corrupt memory?  Looking at funcA(), the refcount is decremented
before the lock is released here:

    refcount_dec(&obj->ref);
    spin_unlock(&lock);

错误（像是机器人写的）:
**Can this corrupt memory?**
Looking at `funcA()`, the refcount is decremented...
```

### 2. 绝不用全大写（ALL CAPS）——除了引用代码

全大写在邮件列表中等于大喊大叫。唯一可以使用全大写的地方是**直接引用源代码中的标识符**。

**错误示例：**
```
SYZKALLER-1: 在 commit message 中发现了不准确的竞态图
```
全大写的标签既没有用，也没有改善报告的格式。

**正确示例：**
```
在 commit message 中，竞态图显示 CPU2 两次调用了
bt_accept_unlink(sk)，第二次调用是 use-after-free。
```

### 3. 所有问题都写成技术性问题，而非指控

不要说"你在这里破坏了内存"，而是说"这段代码是否会破坏内存？"

**错误写法（像在指责作者）：**
```
你在这里泄漏了 folio。bt_accept_unlink() 在持有锁的情况下
调用了 kfree，但没有将指针置 NULL。
```

**正确写法（像在讨论技术问题）：**
```
这段代码是否会泄漏 folio？bt_accept_unlink() 在持有锁的
情况下调用了 kfree，但指针没有置 NULL。
```

**更多对比：**

| 不要这么说 | 要这么说 |
|---|---|
| 你在这里破坏了内存 | 这段代码是否会破坏内存？ |
| 你没有处理错误 | 这里缺少错误处理吗？ |
| 这个锁用错了 | spin_lock() 在调用前是否已经持有了？ |

### 4. 变换提问句式

不要让每个问题都以"Does this code..."开头。变化问法：

- "Is it safe to..."
- "Could this race with..."
- "What happens when..."
- "Should this be protected by..."
- "Is there a missing..."

### 5. 绝不用行号引用代码位置

你在审查环境中看到的行号只对你的代码库设置有意义。你的受众（邮件列表上的维护者）看不到同样的行号，所以行号对他们毫无意义。

**错误写法：**
```
在 line 2327 的 __get_cur_name_and_parent() 中...
在 line 2407-2409 的 __get_cur_name_and_parent() 中...
```

**正确写法——用函数名 + 代码片段：**
```
这可能在 LRU 缓存驱逐条目时发生：

fs/btrfs/send.c:__get_cur_name_and_parent() {
    ...
    nce = name_cache_search(sctx, ino, gen);
    if (nce) {
        if (ino < sctx->send_progress && nce->need_later_update) {
            btrfs_lru_cache_remove(&sctx->name_cache, &nce->entry);
            nce = NULL;
    ...
}

也可能在初始缓存存储失败时发生：

fs/btrfs/send.c:__get_cur_name_and_parent() {
    ...
    nce_ret = btrfs_lru_cache_store(&sctx->name_cache, &nce->entry, GFP_KERNEL);
    if (nce_ret < 0) {
        kfree(nce);
        return nce_ret;
    }
    ...
}
```

任何时候你想说一个行号，就用一小段代码片段来代替。

### 6. 引用资源时具体命名

不要笼统地说"资源泄漏"。要说具体泄漏了什么。

| 不要这么说 | 要这么说 |
|---|---|
| 这段代码有资源泄漏吗？ | 这段代码会泄漏 folio 吗？ |
| 这里有边界检查问题吗？ | 这段代码会溢出 xyz[] 吗？ |

## 段落与结构规范

### 短段落，清晰的问题

**永远不要写又长又密的段落。** 提问要简短，用代码片段或调用链来支撑。

**错误写法——一个密不透风的段落：**
```
Can this sequence actually occur?  Looking at bt_accept_dequeue() in
af_bluetooth.c, if CPU1 already called bt_accept_unlink() which sets
bt_sk(sk)->parent = NULL, wouldn't CPU2 check parent at line 284,
detect it is NULL, and take the 'already unlinked' path with
release_sock/sock_put/goto restart instead of calling bt_accept_unlink()
again?
```

**正确写法——分开展示，逐段说明：**
```
Can this sequence actually occur?  Looking at bt_accept_dequeue() in
af_bluetooth.c, if CPU1 already called bt_accept_unlink() and set
bt_sk(sk)->parent = NULL:

CPU1
bt_accept_unlink()
   bt_sk(sk)->parent = NULL;

CPU2 would see this in bt_accept_dequeue():
    if (!bt_sk(sk)->parent) {
        BT_DBG("sk %p, already unlinked", sk);
        release_sock(sk);
        sock_put(sk);
        ...
        goto restart;
    }

and take the goto restart path instead of calling bt_accept_unlink() again?
```

### 逻辑分组

如果你有一系列事实陈述，用空行将它们分成逻辑组。如果你有一系列陈述后面跟一个问题，在问题前加一个空行。

**错误写法：**
```
The commit message states the pending_release flag is used "to avoid
racing with vgic_put_irq() and causing a double-free." Is this
description accurate? Looking at vgic_put_irq(), it uses
refcount_dec_and_test() which atomically handles concurrent decrements
and returns false when refcount is already zero, so another
vgic_put_irq() call wouldn't trigger a double-free even without this
flag. The pending_release flag appears to be primarily for tracking
which LPIs need cleanup in vgic_release_deleted_lpis(), rather than
preventing races with vgic_put_irq(). Could the commit message be more
precise about what the flag actually protects against?
```

**正确写法——逻辑分组 + 问题前的空行：**
```
The commit message states the pending_release flag is used "to avoid
racing with vgic_put_irq() and causing a double-free." Is this
description accurate?

Looking at vgic_put_irq(), it uses refcount_dec_and_test() which atomically
handles concurrent decrements and returns false when refcount is already zero,
so another vgic_put_irq() call wouldn't trigger a double-free even without this
flag.

The pending_release flag appears to be primarily for tracking
which LPIs need cleanup in vgic_release_deleted_lpis(), rather than
preventing races with vgic_put_irq().

Could the commit message be more precise about what the flag actually protects
against?
```

## 引用规范和内容裁剪

### Diff 引用

引用 patch 的 diff 时（如同在邮件回复中引用）：

1. **逐 hunk 检查相关性。** 对于与审查无关的 hunk，整块剪掉。
2. **保留你保留了 hunk 的文件的 diff header。** 完全删除的文件连 header 也不要保留。
3. **剪掉的内容用 `[ ... ]` 标记。**
4. **激进地剪裁。** 只保留审查所需的最少量引用内容。
5. **尾部内容也要剪。** 在最后一个审查意见之后，如果不再需要，剪掉后面的所有 hunks 和 files。

**示例——只保留与审查相关的 hunk：**

### 引用 commit message

对于 commit message 中的问题：

1. 保持 commit header 和 summary
2. 直接引用 commit message 中不正确的部分

**示例：**
```
commit 535a36aad18ce99e3270486fdb073bb5eb1f1c59
Author: SeongJae Park <sj@kernel.org>

Docs/mm/damon/maintainer-profile: fix wrong MAITNAINERS section name

This commit fixes the documentation to reference the correct MAINTAINERS
section name after commit 9044cbe50a70 renamed the DAMON section from
"DATA ACCESS MONITOR" to "DAMON".

Link: https://lkml.kernel.org/r/20260118180305.70023-8-sj@kernel.org

> Docs/mm/damon/maintainer-profile: fix wrong MAITNAINERS section name

This isn't a bug, but there's a typo (MAITNAINERS) in the subject line.
```

如果问题只在 commit message 中，不需要包含 diff hunks。引用整个 commit message 作为第一个引用块，这符合正常的邮件列表回复惯例，也避免了审查问题出现在被审文本之前。

## 长度把控

有些 bug 极其微妙，需要大量细节来解释。有些 bug 则非常明显——特别是复制粘贴错误，或者作者明显忘了更新某处代码。

如果你预计一个合理的维护者在简短的解释下就能理解，就用简短的解释。**不要过度解释。**

---

## 禁止提及自动化审查工具

报告中绝不能提及、引用、总结或指代自动化审查或机器人评论。

大小写不敏感地，最终报告中不能出现以下关键词作为问题证据：

- `sashiko`、`sashiko.dev`、`sashiko-bot`
- `BPF CI prior reviews`、`bot+bpf-ci`
- `kernel-patches-review-bot`
- `Claude`、`AI review`、`AI review output`
- `GitHub Actions CI run summaries`
- `netdev-ai.bots.linux.dev`
- 任何其他 bot

如果一个问题的依据、内容或表述**依赖于**自动化审查反馈，或与之重叠、重复，**整个问题都不报告**。不要试图将"Sashiko found this"改写成中性措辞。只有基于源代码、commit message 或人工审查评论的独立发现才能被报告。

## 报告结构模板

以下是一个完整的报告结构，按顺序逐项填写。

### 报告头

```
commit <完整的 git SHA>
Author: <作者名> <<作者邮箱>>

<commit subject 行>

<最多 3 句话的 commit 简要总结>

Link: <来自 commit header 的 Link: 标签>
```

### Diff 引用 + 审查意见

```
> diff --git a/<文件路径> b/<文件路径>
> index <hash>..<hash> <mode>
> --- a/<文件路径>
> +++ b/<文件路径>

[ ... ]     ← 剪掉无关 hunk 时使用

> @@ -<起始行>,<行数> +<起始行>,<行数> @@ <函数名>
> <上下文行>
> <上下文行>
> <被删行>
> <被删行>
> <新增行>    ^^^^

<你的问题——不带 > 引用的新文本>

> <上下文行>
> <新增行>
> <新增行>

<你的问题——紧贴在相关代码附近>
```

### 关键规则总结

| 规则 | 说明 |
|---|---|
| 纯文本 | 绝对不用 Markdown、特殊字符 |
| 行宽 78 字符 | diff 中的长行保留原样，你的评论/问题要换行在 78 字符内 |
| 不做全大写 | 除引用代码外，永远不用 ALL CAPS |
| 不引用行号 | 用函数名 + 代码片段 + 文件路径代替 |
| 提问题而非指控 | "这段代码会破坏内存吗？" 而非 "你破坏了内存" |
| 第一个引用块在前 | 问题要出现在被审文本**之后** |
| 紧凑放在相关代码附近 | 问题紧贴引起它的代码行 |
| 激进剪裁 | 只保留审查所需的引用内容 |
| 结尾空行 | 报告末尾留一个空行 |
| 覆盖所有问题 | 即使 bug 在后续 patch 中被修复，也要报告（同时注明后续修复） |
| 禁止 bot 证据 | 报告中的每一条问题都必须基于源码/commit 消息/人工评论 |
| 每种资源具体命名 | "folio 泄漏"而非"资源泄漏"；"xyz[] 溢出"而非"边界检查问题" |

## 报告前自检清单

在发送（或提交）报告之前，逐项检查以下内容：

- [ ] 报告全是纯文本，没有任何 Markdown 标记
- [ ] 没有 ALL CAPS 的词（除了引用的代码标识符）
- [ ] 所有问题都写成了技术性问题，而非指控
- [ ] 没有引用行号——全部用函数名 + 代码片段代替
- [ ] 段落简洁、逻辑分组清晰
- [ ] 没有又长又密的段落
- [ ] diff 引用经过了激进剪裁，只保留相关部分
- [ ] 剪掉的部分用 `[ ... ]` 标记
- [ ] 被审代码在前，审查问题在后
- [ ] 问题紧贴在相关的代码行旁边
- [ ] 报告末尾有空白行
- [ ] 报告中没有提及任何 bot/自动化审查证据
- [ ] 每条问题都有具体证据支撑
- [ ] 包含每种资源的精确名称（如 folio、xyz[]），而非泛称
- [ ] commit message 问题已正确引用 commit message
- [ ] 系列中的后续修复已经注明（如适用）
