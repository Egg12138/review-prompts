# 调用链遍历与回归分析

## 1. 概述

对函数进行变更时，bug 不仅会出现在被修改的函数本身，还可能出现在它**调用**的函数（被调用者，callee）和**调用它**的函数（调用者，caller）中。调用链分析（callstack analysis）通过**双向遍历**——既向上（caller）也向下（callee）——来发现副作用、意外后果以及那些孤立地审查修改函数时看不到的回归问题。

所有非平凡（non-trivial）变更都必须完成调用链分析。

> **核心洞察**：修改一个函数等于修改了它所在调用链的每一条路径。只看 diff 本身是不够的。

---

## 2. 两条铁律

### 2.1 撤回怀疑需要极端怀疑主义（Retraction Rule）

如果你在分析中得出"这是一个 bug"的结论，后来又推翻了这个结论，你必须**以极端怀疑的态度重新审视本次撤回**。具体做法：

1. 明确陈述你撤回的是什么
2. 重新检查你的驳回理由是否存在逻辑错误
3. 采用更高的举证标准

"调用者通常会阻止这个"或者"正常情况下会被处理"——这些理由**不充分**。你必须用具体的代码引用**证明触发条件是结构上不可能发生的**。

### 2.2 可达性驳回（Reachability Dismissals）

一条代码路径如果会导致无限循环、死锁、崩溃或数据损坏，即使你认为前置条件使其"不太可能发生"，它**仍然是一个 bug**。不允许使用以下理由来驳回：

- "调用者正常情况不会传入这种输入"
- "这只有在某个上游函数失败时才会发生"
- "旧代码在同样路径上有一个更糟的 bug"
- "实践中极不可能发生"

**唯一有效的驳回理由**：触发条件在**结构上不可能发生**——也就是说，无论时序、内存压力或并发操作如何，代码在结构上**根本无法到达**该状态。

---

## 3. 变更分类遍历

在开始调用链分析之前，首先需要明确你正在分析哪些变更。

- 如果已经提供了变更分类（change categories），则逐一遍历
- 如果未提供，则将整个待分析单元视为一个变更分类
- **对每一个变更分类**，独立执行第 4-14 节的分析流程
- 必须在完成所有变更分类的分析后才能结束

记录格式：

```
Category N of M: 分类名称, 简要描述
  callers loaded: [ 函数列表，附带每行的随机代码行 ]
  callees loaded: [ 函数列表，附带每行的随机代码行 ]
```

---

## 4. 被调用者遍历（Callee Traversal）

**目标**：查找被修改函数调用的所有函数（callee），分析变更对它们的影响。

即使是微小的变更也可能在被调用函数中引入 bug。唯一确认的方法就是实际阅读调用链中的函数。

### 步骤 1：识别所有直接被调用者

对每个被修改的函数，找出它调用的所有函数。记录每个被调用者及调用时传入的参数。

### 步骤 2：加载每个被调用者的完整函数定义

对于上一步找到的每个被调用者，加载其完整的函数体并阅读。输出被调用函数名和每个函数中的一个随机代码行——这证明你确实阅读了它。

### 步骤 3：向下追踪 2-3 层

调用链上层的小变更可以逐层向下传播，在深层函数中引入 bug。根据需要继续加载更下层的被调用者，批量化加载所有需要的函数。

### 步骤 4：对每一层应用分析

对调用链中的每个被调用者，应用第 6-12 节中的所有检查（锁分析、资源传播、循环控制、初始化验证等）。

### 步骤 5：完成被调用者分析后

被调用者分析完成不等于分析结束——你**还必须**完成调用者分析。

---

## 5. 调用者遍历（Caller Traversal）

**目标**：查找所有调用被修改函数的函数（caller），分析变更对它们的影响。

被修改函数的行为变化会向上传播，影响所有调用它的函数。

### 步骤 1：识别所有直接调用者

找出所有调用被修改函数的函数。记录每个调用者及调用时传入的参数。

### 步骤 2：加载每个调用者的函数定义

加载每个调用者的完整函数体并阅读。输出调用者名、函数体大小（行数）、以及每个函数中的一个随机代码行。

### 步骤 3：追踪返回值传播

对于调用者中**传播返回值**的情况（即将被修改函数的返回值再返回给它的调用者），需要继续向上追踪：

- 在调用者中搜索返回值向上传播的路径
- 如果对调用者的调用者有潜在影响，加载并阅读调用者的调用者的完整定义
- 继续递归向上追踪，**最多 3 层**

### 步骤 4：对每个调用者应用检查

对调用链中的每个调用者，应用第 6-12 节中的所有检查。

### 步骤 5：继续锁需求分析

即使你认为已经找够了足够的数据来完成分析，也要继续进入锁分析。

---

## 6. 锁需求分析（Mandatory Lock Requirements）

### 6.1 验证锁持有状态

确认调用链中每个被追踪函数的锁持有状态是否正确。**必须包含**被修改函数的调用者和被调用者，即使它们未被修改。修改过的函数常常在调用链的其他地方产生意外的副作用——你的分析必须主动搜索这些副作用。

### 6.2 验证锁的范围

不要把锁的存在当作二元判断（有/无）。一把锁有一个**范围**——在某处获得，在某处释放。你必须确认**每一次**对受保护资源的访问都在该范围之内。

当一个函数在函数体的中间才获取锁时，检查获取锁之前执行的所有被调用者——它们可能在锁范围之外访问受保护资源。

### 6.3 验证锁的获取和释放

确认每个函数按照调用者的预期获取和释放锁。

### 6.4 验证锁变更后的状态重校验

如果在调用过程中锁被变更或释放，确认代码正确地重新校验了共享状态（因为锁释放后，其他执行者可能已经修改了受保护的状态）。

## 7. 错误路径锁验证（Mandatory Locking in Error Path Validation）

对于每个获取的锁，追踪所有错误路径（error path），确保在错误路径中锁被正确释放或移交。**必须包含**调用者和被调用者。记录所有错误路径的位置。

> **常见 bug**：正常路径上锁释放正确，但错误路径（goto out、early return）上忘记释放锁。

---

## 8. 资源传播验证（Mandatory Resource Propagation Validation）

### 8.1 追踪资源所有权跨函数边界

当资源（内存、引用计数等）被分配时，确保在它们被覆盖之前被正确返回或处理。**必须包含**调用者和被调用者。

### 8.2 检查空大小分配

对于 `kmalloc()` / `kcalloc()` / `kzalloc()` / `vmalloc()` 等分配，如果 size 参数可能为 0，报告潜在的 `ZERO_SIZE_PTR` 崩溃。

### 8.3 追踪指向同一内存的多个指针

当多个指针指向同一块内存时，追踪通过一个指针的写入如何影响其他指针。利用这一点来理解被操作对象与用于修改对象的指针之间的关系。

### 8.4 验证资源的初始化、加锁和释放

> **注意事项**：在内核中，有些"分配"只是从列表或数组中移除对象。**每次指针赋值**都可能是潜在的分配——检查泄漏和误用。这包括 `void *` 指针，它通常将内存返回给调用者。

---

## 9. RCU 排序验证（Mandatory RCU Ordering Validation）

**重要性**：此步骤捕获 RCU 保护数据结构中的 use-after-free bug。

### 9.1 识别 RCU 回调

如果 diff 中包含 `call_rcu()`、`synchronize_rcu()` 或 `kfree_rcu()`：

- 确认已经加载了 RCU 子系统指南
- 识别对象属于哪些数据结构（rhashtable, hlist, list, rb-tree 等）

### 9.2 验证移除操作在回调之前

确认**从所有查找结构中移除对象**的操作发生在 `call_rcu()` **之前**。

- 移除是在调用 `call_rcu()` 的函数中完成的，还是在回调（callback）中完成的？
- **如果移除在回调中**：这是错误的模式——标记为 use-after-free。在新的宽限期（grace period）结束后、对象被移除之前，新的读者仍然可以找到该对象。回调释放内存时，读者仍在访问它。

### 9.3 查找与引用计数之间的内存访问

检查在查找操作与 `refcount_inc_not_zero()` 之间是否存在内存访问。如果存在字段访问在 `refcount_inc_not_zero()` 之前，这些访问**不受保护**。

---

## 10. 调用者/被调用者参数分析

有些 bug 只在特定参数下才会被触发或消除。考虑以下问题：

- 调用者传入的参数是否改变了 bug 的可达性？
- 被修改函数的参数是否以新的方式传递给被调用者？
- 参数的含义是否有变化？

---

## 11. 循环控制分析（Loop Control Analysis）

### 11.1 循环控制流分析

仔细检查循环控制流，特别是当多个循环嵌套在一起时。同时考虑使整个循环机制重新开始的 goto 目标。

需要分析的内容：

- 控制循环流程的变量
- 内部循环中修改这些控制变量的操作
- 允许循环正常退出的条件
- 尚未加载到上下文中、但控制循环迭代和退出的函数

> **重要警告**：你可能会想跳过这一步。跳过这一步会导致你遗漏正确判断循环退出条件安全性所需的关键信息。**不要以任何理由跳过此步骤。**

### 11.2 典型陷阱示例

```c
start = some_val;
while (current < limit) {
    current++;
    for (i = 0; i < SOME_COUNT; i++) {
        if (func())
            current = start;  /* 内部循环将 current 重置为 start */
    }
}
```

在这个例子中，内层循环在特定条件发生时将 `current` 重置为 `start`。如果 `func()` 频繁返回 true，外层循环可能永远不会退出——这是一个潜在的死循环 bug。

### 11.3 循环控制流验证

- 追踪持有资源的变量在循环迭代之间的变化
- **假设所有循环都会多次迭代**，检查指针赋值的泄漏和逻辑错误——注意外层和内层两个循环都要追踪
- 如果指针在不消耗/释放旧值的情况下被重新赋值，仔细考虑潜在的泄漏——检查整个函数上下文，不仅是内部循环
- 比较并行代码路径（debug 与非 debug、错误路径与成功路径）中的循环退出条件是否一致——在一个条件分支中找到单个 `break` 不等于检查了所有路径

## 12. 初始化验证（Initialization Validation）

对于加载到上下文中的**每个函数**，即使未被 patch 修改——**必须包含**调用者和被调用者——检查是否存在变量和对象在未初始化的情况下被访问。

输出每个函数名、一个随机代码行、以及已正确初始化的变量列表。

---

## 13. 代码质量检查（Code Quality Checks）

### 13.1 注释与行为一致性

验证 diff 中**每条注释**与实际行为是否匹配：

- 检查每条注释是否存在逻辑反转（例如注释说"if true"但代码检查的是 `if !true`）
- 检查每条注释中对条件的描述是否准确
- 标记注释与代码之间的任何不匹配为回归问题

### 13.2 Commit Message 验证

验证 commit message 中的声明是否准确。

### 13.3 设计决策审查

质疑所有的设计决策——要求提供正确性的证明。

### 13.4 新 API 的命名规范

检查新 API 的命名是否符合内核约定。

### 13.5 C 语言最佳实践

对照内核中的 C 最佳实践进行检查。

### 13.6 死代码与未使用变量

死代码和未使用的变量/函数都应报告。

### 13.7 拼写与语法

检查注释和 commit message 中的拼写和语法。除非大小写改变句子的含义，否则不要标记大小写问题。只标记那些使句子难以理解的拼写或语法错误。

### 13.8 子系统风格规则

如果已加载子系统指南，检查新增或修改的代码是否遵循指南中定义的编码风格规则（如注释风格、宏约定、API 偏好）。**只标记新增或修改的行**，不要标记已有代码。

---

## 14. 潜在回归汇总与前瞻搜索

### 14.1 汇总已排除的回归

输出一条描述你发现并排除了的潜在回归。对于每个被排除的潜在回归：

```
Ruled out regression N: Task N <一句话描述>
```

然后反过来思考这些排除——对照第 2 节的撤回怀疑规则和可达性驳回规则——排除它们是否错了？

### 14.2 前瞻性搜索潜在问题

对于因为"该代码路径尚未可达"或"尚无调用者"而被排除的回归：补丁系列通常在一个 commit 中搭建基础设施，在后续 commit 中才将其连接起来。基础设施中的 bug 仍然是 bug。

- 如果提供了 git 范围（`current_sha..series_end_sha`），搜索后续 commit 中启用该被排除代码路径的变更——如果找到，**恢复该问题为已确认**。
- 如果未提供 git 范围，报告该问题并注明"后续 commit 可能启用它"——**不要**仅仅因为当前 commit 未触发就排除。

### 14.3 最终确认

- 是否对所有变更分类完成了第 4-14 节的分析？是/否
- 在专注于排除的问题时，是否忽略了其他可能的问题？重新考虑那些因过度关注排除的问题而被隐藏的问题。
