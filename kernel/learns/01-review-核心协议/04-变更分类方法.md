# 第四章：变更分类方法

## 4.1 为什么要对变更进行分类？

一个补丁可能同时修改多个函数，每个函数可能包含多种不同类型的变更。将这些变更混在一起分析，很容易遗漏特定类型的问题。

**变更分类（change categorization）** 的核心思想是：将 diff 中的所有修改按**类型维度**拆解为细粒度的类别（CHANGE-1, CHANGE-2, ...），然后对每一个类别分别进行回归分析。

这样做的原因：

- 不同类型的问题需要不同的分析视角（pattern prompts）
- 不同类别之间可能产生叠加效应（combination effects）
- 分类本身迫使你仔细阅读每一行变更，避免遗漏

> 重要提示：在完成上下文收集和变更分类之前，**不要开始分析**。即使你觉得自己已经发现了问题，也很可能是错的。深度分析需要时间，不要跳过步骤。

## 4.2 变更的八大类别

### 1. 控制流变更（Control Flow Changes）

**范围**：每个被修改的 `if/else`、`switch/case`、`for/while` 循环、`return`、`break`、`continue`、`goto`

**为什么重要**：
- 控制流变更直接影响代码执行的路径选择
- 错误的条件判断（如用 `||` 代替了 `&&`）可能导致完全相反的语义
- 循环条件错误可能导致无限循环或过早退出

**分析方法**：
- **每个循环单独作为一个类别**，内层循环和外层循环要分开，不要合并
- **每个被修改的 return/break/continue 单独作为一个类别**
- 对于每个控制流变更，理解：哪些路径可以到达这里？这些路径对应的前置条件是什么？

**示例**：
```c
// 原代码
if (flags & GFP_KERNEL) {
        ptr = kmalloc(size, flags);
}

// 修改后
if (flags & (GFP_KERNEL | GFP_ATOMIC)) {
        ptr = kmalloc(size, flags & ~GFP_ATOMIC);
}
// 问题：条件放宽后的行为是否与调用的 kmalloc 语义一致？
// 需要作为 CHANGE-1（控制流：if 条件放宽）分类分析
```

### 2. 返回值语义变更（Return Value / Condition Semantics）

**范围**：函数返回值的变化、条件表达式的变化、错误码的变化

**为什么重要**：
- 返回值的改变可能在调用链上产生连锁反应——所有调用者都依赖于原来的返回值约定
- 错误码的变化可能导致调用者的错误处理逻辑失效（如调用者检查 `IS_ERR()` 但函数开始返回 NULL）
- 布尔条件的反转（如从 `if (!condition)` 改为 `if (condition)`）可能在上下游产生级联影响

**分析方法**：
- 对比修改前后的返回值语义是否一致
- 检查所有调用者是否能够正确处理新的返回值
- 注意 PTR_ERR / ERR_PTR / IS_ERR / NULL / 负错误码之间的转换

**常见陷阱**：
- 一个函数从返回 NULL 改为返回 ERR_PTR(...)，但调用者继续用 `if (!ptr)` 检查错误 —— 这会导致错误被忽略
- 函数开始返回一个新的错误码，调用者只有 `-EINVAL`/`-ENOMEM` 的处理分支

### 3. 资源管理变更 —— 分配与释放（Resource Management: Allocations & Frees）

**范围**：内存分配（kmalloc, kzalloc, alloc_pages）、引用计数（get/put）、文件描述符、DMA buffer、IRQ 等所有内核资源的分配和释放路径

**为什么重要**：
- 多了一个分配少了一个释放 = 内存泄漏
- 少了一个分配多了一个释放 = use-after-free 或 double-free
- 分配函数从一个变到另一个（如 kmalloc 变为 kzalloc）可能改变初始化语义

**分析方法**：
- 为每个分配找到对应的释放路径
- 检查所有错误路径：如果在错误处理中提前返回，对应的资源是否已释放？
- 检查引用计数的 get/put 是否成对出现
- 特别关注 goto cleanup 模式中的释放顺序是否与分配顺序相反

### 4. 资源管理变更 —— 对象初始化（Resource Management: Object Initialization）

**范围**：struct 字段赋值、构造函数、初始化列表、`= {0}` 或 `= {}`、memset 初始化

**为什么重要**：
- 未初始化的字段可能包含栈上的垃圾数据，在内核中这可能导致信息泄露（information leak）或未定义行为
- 新增字段忘记初始化，而旧代码使用 `= {0}` 这种整体初始化方式——新字段会被自动清零吗？
- 初始化顺序可能影响依赖关系：如果字段 B 的初始化依赖字段 A，而 A 在 B 之后初始化，就会出问题

**分析方法**：
- 检查所有新添加的 struct 字段是否被正确初始化
- 对于通过 kmalloc 分配的结构体（非 kzalloc），检查是否所有字段都被显式初始化
- 验证初始化顺序是否符合依赖关系

### 5. 锁与并发边界变更（Locking / Concurrency Boundaries）

**范围**：spin_lock/mutex 的获取与释放、RCU 读端/写端、原子操作、内存屏障（memory barriers）、per-CPU 变量的访问

**为什么重要**：
- 锁是内核并发控制的核心，错误的锁语义可能导致死锁（deadlock）、数据竞争（data race）或性能退化
- 改错锁类型（如 mutex 改为 spin_lock 但临界区中有睡眠操作）可能导致系统崩溃
- 减少锁的持有范围可能引入数据竞争
- 增加锁的持有范围可能引入死锁

**分析方法**：
- 验证锁的获取和释放在所有路径上都成对出现 —— 特别关注错误处理路径
- 检查锁类型与临界区操作是否匹配（是否在 spin_lock 临界区中调用了 might_sleep 的函数）
- 验证新的加锁顺序是否与已有代码一致（锁顺序反转是死锁的常见原因）
- 对于 RCU 变更，检查读端是否在 rcu_read_lock 保护之内，写端是否使用了正确的同步原语

### 6. 子系统 API 使用变更（Subsystem API Usage）

**范围**：特定子系统的 API 调用方式变化，如设备驱动模型（device model）、DMA API、中断管理（IRQ）、文件系统接口（VFS）、网络协议栈（networking stack）等

**为什么重要**：
- 每个内核子系统都有其特定的 API 使用约定（contract），违反这些约定会导致微妙的 bug
- 某些 API 有隐式的前置条件（如必须在特定上下文中调用、必须在持有某锁时调用）
- 新版本的内核可能弃用了某些 API 调用（deprecated API），需要关注替代方案

**分析方法**：
- 查阅子系统指南（subsystem guides）以了解正确的 API 使用模式
- 验证 API 调用的前置条件是否满足（锁是否已持有、中断是否已禁用等）
- 检查函数指针类型、回调函数签名是否与子系统定义一致
- 注意新旧 API 的兼容性——修改后的代码是否还能在老版本内核上编译？

### 7. 配置依赖变更（Kconfig / Configuration Changes）

**范围**：Kconfig 文件的 `depends on` / `select` 修改、defconfig 更新、源码中新增的 `CONFIG_*` 使用

**为什么重要**：
- `select` 使用不当会创建循环依赖（circular dependency），导致 Kconfig 解析失败
- 新增的 `CONFIG_*` 如果在 Kconfig 中没有对应的定义，编译会报错
- "静默禁用"（silent disable）问题：某个选项看起来被启用，但它的依赖条件不满足，导致实际未被启用

**分析方法**：
- 验证新 `CONFIG_*` 符号在 Kconfig 中确实存在
- 检查 `select` 没有引入循环依赖
- 优先使用 `depends on` 而非 `select`（对于可见符号）
- 验证 defconfig 中启用的选项其所有依赖都可满足

### 8. 提交信息与注释变更（Commit Message & Comment Changes）

**范围**：提交信息中的声明、代码注释的修改或新增

**为什么重要**：
- 提交信息中的声明（如"修复了 XXX 问题"）必须与代码修改一致
- 误导性的注释比没有注释更糟糕——它们会误导未来的维护者
- 注释与实际代码不符说明开发者可能没有完全理解自己的修改

**分析方法**：
- 验证提交信息中的每个声明都能在 diff 中找到对应
- 验证代码注释描述的语义与实际代码一致
- 检查注释中是否有拼写错误或过时的引用

## 4.3 分类实践方法

### 如何为每个修改函数建立分类

对于 diff 中每个被修改的函数：

1. **逐行检查**：每一行修改属于哪个类别？
2. **建立类别清单**：将同一类别的变更归组，为每个类别分配一个 CHANGE-N 编号
3. **记录随机代码行**：为每个类别记录一行代表性的代码，便于后续引用

### 使用 TodoWrite 记录

```
CHANGE-1: 控制流 — example_func() 中 GFP_KERNEL 条件放宽
  if (flags & (GFP_KERNEL | GFP_ATOMIC)) {

CHANGE-2: 返回值语义 — example_func() 返回 PTR_ERR 代替 NULL
  return PTR_ERR(ptr) != 0;

CHANGE-3: 资源释放 — new_func() 中的 kfree 路径变更
  kfree(obj->buffer);
```

### 需要特别注意的叠加效应

当同一个函数包含多个不同类别的变更时，需要额外关注它们之间的交互：

- 控制流变更 + 资源管理变更 → 错误路径上是否少了释放？
- 锁变更 + 返回值变更 → 返回值路径上锁是否都已释放？
- 控制流变更 + 初始化变更 → 新路径上的对象是否都已初始化？

## 4.4 分类示例：一个简单的补丁分析

假设有一个补丁修改了 `kernel/sched/core.c` 中的 `sched_setaffinity` 函数：

```c
// 变更 1：加入新的错误检查（控制流变更）
+       if (unlikely(!pid_valid(pid)))
+               return -EINVAL;

// 变更 2：使用新 API（子系统 API 变更）
-       cpus_allowed = task_cpu_possible_mask(p);
+       cpus_allowed = cpu_valid_mask(p);

// 变更 3：新增资源分配（资源管理变更）
+       new_mask = alloc_cpumask_var();
+       if (!new_mask)
+               return -ENOMEM;
```

分类结果：

| 编号 | 类别 | 描述 |
|------|------|------|
| CHANGE-1 | 控制流变更 | 新增 `pid_valid()` 检查，添加了提前返回路径 |
| CHANGE-2 | 子系统 API 变更 | `task_cpu_possible_mask` → `cpu_valid_mask` 的 API 替换 |
| CHANGE-3 | 资源管理变更 | 新增 `alloc_cpumask_var()` 分配，需要追踪释放路径 |

在后续的回归分析中，每个 CHANGE 会使用对应的 pattern prompts 进行分析。这种分类方式确保了没有遗漏任何类型的潜在问题。
